SQL Window Functions: A Practice Guide

5 recipe categories covering ranking, running aggregates, rolling windows, row offsets, and distribution functions with a diagnostic process, decision tree, business scenarios, and practice problems with full solutions.

Last updated: April 2026

What are window functions?

Window functions let you compute a value for every row using data from other rows in the same result set, without collapsing anything. Unlike GROUP BY, which reduces rows into summary groups, a window function keeps all your original rows and adds a new computed column alongside them.

Why do we need them?

Standard SQL has a gap: you can filter rows or collapse them into groups, but you cannot easily do things like:

  • Pick the top 3 salaries per department without losing the employee detail rows
  • Show a running total that accumulates as you go down the table
  • Compare each row to the row before it (yesterday's revenue vs today's)
  • Compute each product's percentage of total sales in a single query

Window functions solve all of these. They compute their result across the final row set your query produces, and they never change the number of rows returned. No GROUP BY is required.

Four Step Window Function Diagnostic

Before writing a window function, work through these four steps. They clarify which function you need, how to partition and order the data, and whether a frame specification is required.

Step 1: What Are You Computing?

▼

Identify the category of computation. This determines which function family to use.

Ask yourself:

  • Position or rank? → You need a ranking function (ROW_NUMBER, RANK, DENSE_RANK)
  • Running total or cumulative count? → You need a running aggregate (SUM/COUNT/AVG OVER with ORDER BY)
  • Moving average or sliding window? → You need a rolling window (aggregate with ROWS/RANGE BETWEEN)
  • Value from a specific other row? → You need an offset function (LAG, LEAD, FIRST_VALUE, LAST_VALUE)
  • Percentage of total, percentile, or bucket? → You need a distribution function (SUM OVER for ratios, PERCENT_RANK, NTILE)

Step 2: Define the Window

▼

Determine what PARTITION BY and ORDER BY should be for your window clause.

Mnemonic for deciding PARTITION BY

Ask yourself: "Do I want a winner per something, or one winner overall?" — per (top salary per department, most recent order per customer) means PARTITION BY; overall (the question with the highest answer rate across ALL questions) means no PARTITION BY.

Two decisions:

  • PARTITION BY: What column(s) should the calculation reset on? Each unique combination of partition columns creates an independent window. Omitting PARTITION BY means the entire result set is one window.
  • ORDER BY: What determines the row sequence within each partition? Required for ranking, running aggregates, and offset functions. Not needed for simple ratios (percentage of total).
-- Template FUNCTION() OVER ( PARTITION BY group_column -- reset for each group ORDER BY sort_column -- row sequence within group )

Step 3: Do You Need a Frame?

▼

Most window functions use the default frame. Override it only for rolling windows or when you need the full partition.

Default behavior:

  • With ORDER BY: Default frame is RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW (running total from start to current row)
  • Without ORDER BY: Default frame is the entire partition (all rows)

When to override:

  • Rolling N-row window: ROWS BETWEEN 6 PRECEDING AND CURRENT ROW (7-day rolling average)
  • Date-based window: RANGE BETWEEN INTERVAL '7 days' PRECEDING AND CURRENT ROW
  • Full partition with ORDER BY: ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING

ROWS vs RANGE

ROWS counts physical rows (row 1, row 2, row 3). RANGE uses logical values (all rows with the same date count as one unit). Use ROWS for fixed-size sliding windows. Use RANGE for date-based windows where ties should be grouped.

Step 4: Pick the Function, Wrap if Filtering

▼

Choose the specific function, then check if you need a CTE or subquery wrapper.

Function selection: Once you know the category (Step 1), window (Step 2), and frame (Step 3), pick the specific function from the Decision Tree or Signal Words table.

Filtering rule: Window functions execute after WHERE, so you cannot filter on a window function result directly. If your query needs to filter (e.g., WHERE rn = 1, WHERE running_total > 1000), wrap the window in a CTE or subquery first.

-- Wrong: window function in WHERE SELECT *, ROW_NUMBER() OVER (...) AS rn FROM t WHERE rn = 1; -- ERROR: rn not yet computed -- Right: wrap in CTE WITH ranked AS ( SELECT *, ROW_NUMBER() OVER (...) AS rn FROM t ) SELECT * FROM ranked WHERE rn = 1;

Example Worked Example: Top 3 Salaries per Department

▼

A fully filled out diagnostic using #185 Department Top Three Salaries, with gray context notes explaining each decision.

-- ============================================
-- STEP 1: What Am I Computing?
-- ============================================

-- I need the top 3 highest-paid employees in each department.
-- "Top N per group" = ranking category.

--     CONTEXT: The phrase "top 3 per department" immediately
--     signals a ranking function. The question is which one:
--     ROW_NUMBER (unique), RANK (gaps), or DENSE_RANK (no gaps).
--     Since "top 3 salaries" means ties at the same salary
--     should all be included, DENSE_RANK is the right choice.


-- ============================================
-- STEP 2: Define the Window
-- ============================================

-- PARTITION BY: department (reset ranking for each department)
-- ORDER BY: salary DESC (highest salary gets rank 1)

--     CONTEXT: If you omit PARTITION BY, you get the top 3
--     across the entire company, not per department. Always
--     ask: "what should the calculation reset on?"


-- ============================================
-- STEP 3: Do I Need a Frame?
-- ============================================

-- No. Ranking functions (ROW_NUMBER, RANK, DENSE_RANK)
-- ignore frame specifications entirely. The frame clause
-- only matters for aggregate window functions.


-- ============================================
-- STEP 4: Pick the Function, Wrap if Filtering
-- ============================================

-- Function: DENSE_RANK() (allows ties, no gaps)
-- Filtering: Yes, I need WHERE rnk <= 3, so I must wrap
-- the window function in a CTE or subquery first.

--     CONTEXT: This is the most common trap. You cannot write
--     WHERE DENSE_RANK() OVER (...) <= 3 directly in the query.
--     Window functions run after WHERE, so the filter would fail.
--     Always wrap in a CTE when you need to filter on the result.


-- SOLUTION

WITH ranked AS (
  SELECT
    d.name AS Department,
    e.name AS Employee,
    e.salary AS Salary,
    DENSE_RANK() OVER (
      PARTITION BY e.departmentId
      ORDER BY e.salary DESC
    ) AS rnk
  FROM Employee e
  JOIN Department d ON e.departmentId = d.id
)
SELECT Department, Employee, Salary
FROM ranked
WHERE rnk <= 3;

Window Function Anatomy

FUNCTION(args) OVER ( PARTITION BY col -- optional: groups (like GROUP BY but keeps all rows) ORDER BY col -- optional: row sequence within partition ROWS BETWEEN ... -- optional: frame (which rows the function sees) )

Key difference from GROUP BY: Window functions add a computed column to every row without collapsing rows. GROUP BY reduces rows to one per group. If you need to keep all original rows AND compute an aggregate, use a window function.

Window Function Recipes

5 recipe categories covering all major window function patterns. Each recipe includes the syntax template, a business scenario, practice problems with full solutions, and the most common trap.

Recipe 1: Rank & Position 4 examples

▼

ROW_NUMBER, RANK, DENSE_RANK — assign sequential positions within partitions for top-N selection, deduplication, or ordered numbering.

Syntax Template

WITH ranked AS ( SELECT *, ROW_NUMBER() OVER ( -- or RANK() / DENSE_RANK() PARTITION BY group_col ORDER BY sort_col DESC ) AS rn FROM source_table ) SELECT * FROM ranked WHERE rn <= N;

When to Use Which

Function Ties (80, 80, 70) Output Use When
ROW_NUMBER 1, 2, 3 Always unique Top-N, dedup, keep latest per group
RANK 1, 1, 3 Gaps after ties Competitive ranking where gaps matter
DENSE_RANK 1, 1, 2 No gaps "Top 3 salaries" (include all ties)

Business Scenario: Top 3 Products per Category by Revenue

Your product team wants to know the top 3 revenue-generating products in each category to decide where to invest marketing budget.

WITH ranked AS ( SELECT category, product_name, SUM(revenue) AS total_revenue, DENSE_RANK() OVER ( PARTITION BY category ORDER BY SUM(revenue) DESC ) AS rnk FROM sales GROUP BY category, product_name ) SELECT category, product_name, total_revenue FROM ranked WHERE rnk <= 3 ORDER BY category, rnk;

#185 Department Top Three Salaries (Hard)

▼

Find employees who earn one of the top three unique salaries in their department. Uses DENSE_RANK to handle ties.

View on LeetCode
WITH ranked AS ( SELECT d.name AS Department, e.name AS Employee, e.salary AS Salary, DENSE_RANK() OVER ( PARTITION BY e.departmentId ORDER BY e.salary DESC ) AS rnk FROM Employee e JOIN Department d ON e.departmentId = d.id ) SELECT Department, Employee, Salary FROM ranked WHERE rnk <= 3;

Why DENSE_RANK: "Top three salaries" means the 3rd-highest unique salary, not the 3rd person. DENSE_RANK groups ties under the same rank number without gaps, so all employees at the 3rd-highest salary are included.

#1070 Product Sales Analysis III (Medium)

▼

For each product, find the first year it was sold and the quantity and price in that year. Uses RANK to identify the earliest year.

View on LeetCode
WITH ranked AS ( SELECT product_id, year AS first_year, quantity, price, RANK() OVER ( PARTITION BY product_id ORDER BY year ASC ) AS rn FROM Sales ) SELECT product_id, first_year, quantity, price FROM ranked WHERE rn = 1;

#196 Delete Duplicate Emails (Easy)

▼

Delete duplicate emails keeping the row with the smallest id. ROW_NUMBER partitioned by email identifies duplicates.

View on LeetCode
DELETE FROM Person WHERE id IN ( SELECT id FROM ( SELECT id, ROW_NUMBER() OVER ( PARTITION BY email ORDER BY id ASC ) AS rn FROM Person ) ranked WHERE rn > 1 );

Pattern: ROW_NUMBER + PARTITION BY duplicated column + ORDER BY tie-breaker. Rows with rn > 1 are duplicates.

Common Trap: RANK vs DENSE_RANK vs ROW_NUMBER

With values (80, 80, 70): ROW_NUMBER gives 1,2,3 (arbitrary tiebreak). RANK gives 1,1,3 (gap at 2). DENSE_RANK gives 1,1,2 (no gap). When the problem says "top 3 salaries," DENSE_RANK is usually correct. When it says "top 3 employees," ROW_NUMBER or RANK may be more appropriate.

Recipe 2: Running & Cumulative Aggregates 2 examples

▼

SUM, COUNT, AVG with OVER(ORDER BY) — accumulate values from the first row to the current row for running totals, cumulative counts, and progressive averages.

Syntax Template

SELECT date_col, value_col, SUM(value_col) OVER ( PARTITION BY group_col -- optional: reset per group ORDER BY date_col -- required: defines accumulation order ) AS running_total -- default frame: start to current row FROM source_table;

Business Scenario: Cumulative Monthly Revenue Toward Annual Target

Finance needs a report showing how monthly bookings accumulate toward the $12M annual revenue target, with percentage progress.

SELECT month, monthly_revenue, SUM(monthly_revenue) OVER ( ORDER BY month ) AS cumulative_revenue, ROUND( SUM(monthly_revenue) OVER (ORDER BY month) / 12000000.0 * 100, 1 ) AS pct_of_annual_target FROM monthly_bookings ORDER BY month;

#1204 Last Person to Fit in the Bus (Medium)

▼

Find the last person who can board the bus without exceeding the 1000kg weight limit. Running SUM to track cumulative weight.

View on LeetCode
WITH cumulative AS ( SELECT person_name, SUM(weight) OVER ( ORDER BY turn ) AS total_weight FROM Queue ) SELECT person_name FROM cumulative WHERE total_weight <= 1000 ORDER BY total_weight DESC LIMIT 1;

Pattern: Running SUM ordered by turn, then filter to rows within the limit and take the last one. The CTE is needed because you cannot filter on the window function in WHERE directly.

Common Trap: Default Frame Surprises

When you add ORDER BY to a window aggregate, the default frame changes from "entire partition" to "start to current row." This means SUM(x) OVER (ORDER BY date) gives a running total, not a grand total. If you want the grand total alongside each row, either omit ORDER BY: SUM(x) OVER (), or explicitly set the frame: ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING.

Recipe 3: Rolling & Sliding Windows 2 examples

▼

Aggregate functions with ROWS BETWEEN or RANGE BETWEEN — compute moving averages, rolling sums, or trailing period metrics over a fixed-size sliding window.

Syntax Template

SELECT date_col, value_col, AVG(value_col) OVER ( PARTITION BY group_col ORDER BY date_col ROWS BETWEEN 6 PRECEDING AND CURRENT ROW ) AS rolling_7day_avg FROM source_table;

Frame Specification Reference

Frame Meaning Use Case
ROWS BETWEEN 6 PRECEDING AND CURRENT ROW Current row + 6 rows before (7 rows total) 7-day rolling average (if 1 row per day)
RANGE BETWEEN INTERVAL '7 days' PRECEDING AND CURRENT ROW All rows within 7 calendar days before current Date-based window (handles gaps in dates)
ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW All rows from partition start to current Running total (this is the default with ORDER BY)
ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING Entire partition Grand total alongside each row (with ORDER BY)

Business Scenario: 7-Day Rolling Average of Daily Signups

The growth team monitors a 7-day rolling average of daily signups to smooth out day-of-week effects and spot real trends vs. noise.

SELECT signup_date, daily_signups, ROUND( AVG(daily_signups) OVER ( ORDER BY signup_date ROWS BETWEEN 6 PRECEDING AND CURRENT ROW ), 1 ) AS rolling_7day_avg FROM daily_signups ORDER BY signup_date;

#1321 Restaurant Growth (Medium)

▼

Compute the 7-day moving average of restaurant customer spending. Uses SUM and AVG with ROWS BETWEEN 6 PRECEDING AND CURRENT ROW.

View on LeetCode
WITH daily AS ( SELECT visited_on, SUM(amount) AS day_total FROM Customer GROUP BY visited_on ), rolling AS ( SELECT visited_on, SUM(day_total) OVER ( ORDER BY visited_on ROWS BETWEEN 6 PRECEDING AND CURRENT ROW ) AS amount, ROUND( AVG(day_total) OVER ( ORDER BY visited_on ROWS BETWEEN 6 PRECEDING AND CURRENT ROW ), 2 ) AS average_amount, ROW_NUMBER() OVER (ORDER BY visited_on) AS rn FROM daily ) SELECT visited_on, amount, average_amount FROM rolling WHERE rn >= 7;

Key insight: First aggregate daily totals (multiple customers per day), then apply the rolling window. Filter out the first 6 rows since they have fewer than 7 days of data.

Common Trap: ROWS vs RANGE for Date Windows

ROWS BETWEEN 6 PRECEDING counts exactly 6 physical rows back. If your data has gaps (no row for Saturday/Sunday), the window covers more than 7 calendar days. Use RANGE BETWEEN INTERVAL '6 days' PRECEDING for true calendar-based windows, or pre-fill gaps with a date spine.

Recipe 4: Offset & Neighbor Access 4 examples

▼

LAG, LEAD, FIRST_VALUE, LAST_VALUE, NTH_VALUE — access values from specific other rows in the partition for period-over-period comparisons, consecutive detection, and boundary lookups.

Syntax Template

SELECT date_col, value_col, LAG(value_col, 1) OVER ( PARTITION BY group_col ORDER BY date_col ) AS prev_value, value_col - LAG(value_col) OVER ( ORDER BY date_col ) AS change FROM source_table;

Function Reference

Function Returns Default for First/Last Row
LAG(col, n, default) Value from n rows before current NULL (or specify default as 3rd arg)
LEAD(col, n, default) Value from n rows after current NULL (or specify default as 3rd arg)
FIRST_VALUE(col) First value in the window frame Works with default frame
LAST_VALUE(col) Last value in the window frame Needs explicit UNBOUNDED FOLLOWING frame!
NTH_VALUE(col, n) Nth value in the window frame NULL if fewer than n rows in frame

Business Scenario: Month-over-Month Revenue Change

Leadership reviews monthly revenue changes to track growth trajectory and flag months with declining trends early.

SELECT month, revenue, LAG(revenue) OVER (ORDER BY month) AS prev_month, revenue - LAG(revenue) OVER (ORDER BY month) AS change, ROUND( (revenue - LAG(revenue) OVER (ORDER BY month)) * 100.0 / LAG(revenue) OVER (ORDER BY month), 1 ) AS pct_change FROM monthly_revenue ORDER BY month;

#197 Rising Temperature (Easy)

▼

Find dates where the temperature was higher than the previous day. Uses LAG to compare each row to its predecessor.

View on LeetCode
WITH compared AS ( SELECT id, recordDate, temperature, LAG(temperature) OVER (ORDER BY recordDate) AS prev_temp, LAG(recordDate) OVER (ORDER BY recordDate) AS prev_date FROM Weather ) SELECT id FROM compared WHERE temperature > prev_temp AND recordDate - prev_date = 1;

Key insight: LAG both the temperature and the date. The date check (recordDate - prev_date = 1) ensures you only compare consecutive calendar days, not rows that are adjacent after gaps.

#180 Consecutive Numbers (Medium)

▼

Find numbers that appear at least three times consecutively. Uses LAG to check the previous two values.

View on LeetCode
WITH neighbors AS ( SELECT num, LAG(num, 1) OVER (ORDER BY id) AS prev1, LAG(num, 2) OVER (ORDER BY id) AS prev2 FROM Logs ) SELECT DISTINCT num AS ConsecutiveNums FROM neighbors WHERE num = prev1 AND num = prev2;

Pattern: Use LAG with offset 1 and 2 to bring in the previous two rows. If all three values match, you have three consecutive occurrences. DISTINCT handles cases where the streak is longer than 3.

#626 Exchange Seats (Medium)

▼

Swap adjacent student seats. A simpler approach uses CASE with arithmetic on id, but this can also be solved with LAG/LEAD.

View on LeetCode

Efficient approach (no window function needed):

SELECT CASE WHEN id % 2 = 1 AND id = (SELECT COUNT(*) FROM Seat) THEN id WHEN id % 2 = 1 THEN id + 1 ELSE id - 1 END AS id, student FROM Seat ORDER BY id;

Why arithmetic beats LAG/LEAD here: The swap only involves renumbering ids, not accessing neighbor values. CASE + modulo is a single-pass operation with no window function overhead.

Common Trap: LAST_VALUE Needs an Explicit Frame

With ORDER BY, the default frame is "start to current row," so LAST_VALUE(col) OVER (ORDER BY date) just returns the current row's value (useless). To get the actual last value in the partition, add ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING. FIRST_VALUE does not have this problem since the first row is always in the default frame.

Recipe 5: Ratio & Distribution 3 examples

▼

SUM() OVER() for percentage of total, PERCENT_RANK, CUME_DIST, NTILE — compute each row's share, relative standing, or bucket assignment within a partition.

Syntax Templates

-- Percentage of total SELECT category, revenue, ROUND( revenue * 100.0 / SUM(revenue) OVER (), 1 ) AS pct_of_total FROM source_table; -- Percentage within group SELECT category, product, revenue, ROUND( revenue * 100.0 / SUM(revenue) OVER (PARTITION BY category), 1 ) AS pct_of_category FROM source_table; -- Percentile rank and quartile bucketing SELECT employee, salary, ROUND(PERCENT_RANK() OVER (ORDER BY salary), 2) AS pct_rank, NTILE(4) OVER (ORDER BY salary) AS quartile FROM employees;

Function Comparison

Function Formula Range Use Case
PERCENT_RANK (rank - 1) / (total_rows - 1) 0 to 1 Relative standing; first row = 0
CUME_DIST count(rows ≤ current) / total_rows >0 to 1 Proportion at or below; never zero
NTILE(n) Divide into n roughly equal groups 1 to n Quartiles, deciles, custom buckets

Business Scenario: Salary Percentiles by Department

HR needs to see where each employee's salary falls relative to their department for compensation benchmarking and equity reviews.

SELECT employee_name, department, salary, ROUND( PERCENT_RANK() OVER ( PARTITION BY department ORDER BY salary ), 2 ) AS pct_rank, NTILE(4) OVER ( PARTITION BY department ORDER BY salary ) AS quartile FROM employees ORDER BY department, salary;

Business Example: Each Region's Share of Total Revenue

▼

Compute each region's revenue as a percentage of company-wide total using SUM() OVER() without PARTITION BY.

SELECT region, SUM(revenue) AS region_revenue, ROUND( SUM(revenue) * 100.0 / SUM(SUM(revenue)) OVER (), 1 ) AS pct_of_total FROM sales GROUP BY region ORDER BY region_revenue DESC;

Key pattern: SUM(SUM(revenue)) OVER () is a window function on top of a GROUP BY aggregate. The inner SUM aggregates per region; the outer SUM OVER() computes the grand total across all regions. This works because window functions execute after GROUP BY.

#1174 Immediate Food Delivery II (Medium)

▼

Find the percentage of first orders that were immediate (order date = customer preferred date). Combines ranking with ratio calculation.

View on LeetCode
WITH first_orders AS ( SELECT delivery_id, customer_id, order_date, customer_pref_delivery_date, ROW_NUMBER() OVER ( PARTITION BY customer_id ORDER BY order_date ) AS rn FROM Delivery ) SELECT ROUND( AVG(CASE WHEN order_date = customer_pref_delivery_date THEN 1.0 ELSE 0.0 END) * 100, 2 ) AS immediate_percentage FROM first_orders WHERE rn = 1;

Composite pattern: First, use ROW_NUMBER to isolate each customer's first order (ranking recipe). Then, compute the percentage using conditional AVG (ratio recipe). Two window function categories in one problem.

Common Trap: PERCENT_RANK vs CUME_DIST

With 4 rows ranked 1,2,3,4: PERCENT_RANK gives 0, 0.33, 0.67, 1.0 (first row is always 0). CUME_DIST gives 0.25, 0.5, 0.75, 1.0 (first row is never 0). Use PERCENT_RANK when you want "what percentage of rows are below me." Use CUME_DIST when you want "what percentage of rows are at or below me."
