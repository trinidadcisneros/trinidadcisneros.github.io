JOIN Checklist

  1. Identify the join key(s) — columns that connect the tables
  2. Choose join type: INNER (default), LEFT (keep all from first table), CROSS (all combinations)
  3. Check for duplicates in keys — many-to-many creates row explosion (Cartesian product)
  4. Handle NULL join keys — NULLs never match in a standard JOIN
  5. After joining: verify row count to ensure no unexpected multiplication

SQL Execution Order (How the Engine Processes Your Query)

Understanding this order helps you predict which clauses can reference which aliases and columns:

  1. FROM / JOIN — Tables are loaded and joined first
  2. WHERE — Row-level filtering (no aggregates allowed here)
  3. GROUP BY — Rows are grouped
  4. HAVING — Group-level filtering (aggregates allowed here)
  5. SELECT — Columns are computed (window functions run here)
  6. DISTINCT — Deduplication
  7. ORDER BY — Sorting (can reference SELECT aliases)
  8. LIMIT / OFFSET — Final row restriction
Pattern Recognition: Row-Level Filtering

What Filtering Problems Have in Common

All filtering problems ask you to identify rows that meet certain conditions and return only those rows. The key is translating the business requirement into a WHERE clause.

Key Signals in Problem Text

  • "Find rows where..." → Simple AND/OR conditions
  • "Filter by..." → Column values or patterns
  • "Exclude..." → NOT conditions or inequality
  • "Matching pattern..." → LIKE or regex for strings
  • "At least... or more than..." → Threshold comparisons (>=, >, etc.)

The Shared Strategy

  1. Read the condition: What rows should be included?
  2. Translate to WHERE: Convert text into boolean logic
  3. Handle edge cases: NULL values, case sensitivity, string boundaries
  4. Return relevant columns: SELECT only what's asked for

Common Traps

  • NULL Handling: WHERE col = NULL returns no rows. Use IS NULL or col != 2 OR col IS NULL
  • String Functions: LIKE patterns treat '%' and '_' as wildcards. Use escape characters if needed
  • Regex Boundaries: Regex patterns must match the entire string or specify anchors (^ for start, $ for end)
  • Case Sensitivity: Some databases are case-sensitive for comparisons; use LOWER() if needed
  • Boolean Logic: Remember De Morgan's laws: NOT (A AND B) = (NOT A) OR (NOT B)

Easy #1757 Recyclable and Low Fat Products

+

Find product IDs that are both low fat AND recyclable.

Tables: Products (product_id, low_fats, recyclable)

→

Decision Tree Path

Master Tree: Single-Table Queries → Pattern A: Row-Level Filtering

Real-World Example

An e-commerce company maintains a product database and needs to create a "sustainable choices" catalog highlighting products that are both environmentally friendly (recyclable) and healthy (low fat). This query extracts the product IDs for marketing campaigns.

▶ 1 Simple AND Condition
-- Most efficient: direct AND condition SELECT product_id FROM Products WHERE low_fats = 'Y' AND recyclable = 'Y';

Why this is best: Direct WHERE condition on two columns. Single table scan, no joins or subqueries needed.

Performance: O(n) single table scan. If low_fats and recyclable are indexed, the database engine can use indexes to short-circuit evaluation.

▶ 2 Boolean Expression (Alternative Style)
-- Alternative: using boolean expressions SELECT product_id FROM Products WHERE (low_fats, recyclable) = ('Y', 'Y');

Why this works: Row value comparison compares tuples directly. Some databases support this; PostgreSQL does.

Performance: Same as AND, but slightly less portable across database systems.

Easy #584 Find Customer Referee

+

Find customer names who are either not referred (NULL) or referred by someone other than customer ID 2.

Tables: Customer (id, name, referee_id)

→

Decision Tree Path

Master Tree: Single-Table Queries → Pattern A: Row-Level Filtering (Note: NULL handling)

Real-World Example

A CRM system tracks customer referrals. To identify customers for a retention campaign, you exclude referrals from a competitor (customer ID 2) but include both organic sign-ups (NULL referee_id) and referrals from other sources.

▶ 1 OR with IS NULL (Correct NULL Handling)
-- Most efficient: OR condition with IS NULL SELECT name FROM Customer WHERE referee_id != 2 OR referee_id IS NULL;

Why this is best: Correctly handles NULL values. In SQL, NULL != 2 evaluates to NULL (unknown), not TRUE, so you must explicitly check for NULL.

Performance: Single table scan. Both conditions are fast; OR allows short-circuit evaluation.

▶ 2 COALESCE to Default Value
-- Using COALESCE to replace NULL with a safe value SELECT name FROM Customer WHERE COALESCE(referee_id, 0) != 2;

Why this works: COALESCE converts NULL to 0, which is always != 2. Simpler than OR but assumes no one is referred by ID 0.

Performance: Single table scan. Slightly slower than OR if many rows are non-NULL (function call on every row).

▶ 2 NOT with Negation
-- Using NOT to exclude referee_id = 2 SELECT name FROM Customer WHERE NOT (referee_id = 2);

Why this works: NOT (referee_id = 2) correctly treats NULL rows as included because NOT(NULL) = NULL, which is falsy.

Performance: Equivalent to the first solution, but less readable for this scenario.

Easy #595 Big Countries

+

Find countries with either area >= 3 million km² OR population >= 25 million.

Tables: World (name, continent, area, population, gdp)

→

Decision Tree Path

Master Tree: Single-Table Queries → Pattern A: Row-Level Filtering

Real-World Example

A geographic analysis tool filters a world dataset to identify "major" countries by economic or demographic significance. Threshold-based filtering on numeric columns is a common pattern in data warehousing and business intelligence.

▶ 1 Simple OR on Two Conditions
-- Most efficient: direct OR on numeric thresholds SELECT name, population, area FROM World WHERE area >= 3000000 OR population >= 25000000;

Why this is best: Single pass through table. Both conditions are simple numeric comparisons. OR allows early exit (if area is large, skip population check).

Performance: O(n) single scan. Indexes on area and population enable fast filtering.

▶ 2 UNION of Two Queries
-- Alternative: UNION of two separate queries SELECT name, population, area FROM World WHERE area >= 3000000 UNION SELECT name, population, area FROM World WHERE population >= 25000000;

Why this works: Each query uses a single index independently. UNION removes duplicates (e.g., countries meeting both criteria).

Performance: Slower: scans table twice plus UNION overhead. Use only if index selectivity heavily favors one condition over OR.

Easy #1148 Article Views I

+

Find all authors who viewed at least one of their own articles (author_id = viewer_id). Return distinct author IDs sorted by ID.

Tables: Views (article_id, author_id, viewer_id, view_date)

→

Decision Tree Path

Master Tree: Single-Table Queries → Pattern A: Row-Level Filtering + DISTINCT

Real-World Example

A content platform detects "self-view" behavior to identify authors who are artificially inflating view counts on their own content. This metric is used for fraud detection or engagement analysis.

▶ 1 WHERE + DISTINCT + ORDER BY
-- Most efficient: filter, deduplicate, sort SELECT DISTINCT author_id AS id FROM Views WHERE author_id = viewer_id ORDER BY id;

Why this is best: Single pass filtering, then DISTINCT removes duplicates (same author viewed multiple articles). ORDER BY on a small result set is cheap.

Performance: O(n) filter + O(k log k) sort (where k = distinct authors). DISTINCT uses a hash set or sort underneath.

▶ 2 GROUP BY with MIN/MAX
-- Alternative: GROUP BY to get unique authors SELECT author_id AS id FROM Views WHERE author_id = viewer_id GROUP BY author_id ORDER BY id;

Why this works: GROUP BY guarantees one row per author. No aggregate function needed; just grouping handles deduplication.

Performance: Similar to DISTINCT. GROUP BY may be slower if the database uses a sort-based grouping algorithm instead of a hash.

Medium #620 Not Boring Movies

+

Find movies with odd-numbered IDs and descriptions that are not "boring". Return sorted by rating descending.

Tables: Cinema (id, movie, description, rating)

→

Decision Tree Path

Master Tree: Single-Table Queries → Pattern A: Row-Level Filtering + Modulo arithmetic

Real-World Example

A movie recommendation engine filters out low-quality or "boring" content while also applying a weighting bias (odd IDs get higher priority). This combines business rules (genre exclusion) with technical filters (ID-based sampling).

▶ 1 Modulo (%) for Odd ID + NOT EQUAL String
-- Most efficient: modulo for odd check, NOT EQUAL for string SELECT id, movie, description, rating FROM Cinema WHERE id % 2 = 1 AND description != 'boring' ORDER BY rating DESC;

Why this is best: Modulo (id % 2 = 1) checks for odd IDs efficiently. String inequality is a fast comparison. Both conditions can use indexes if available.

Performance: O(n) filter + O(k log k) sort (k = result rows). Short-circuit evaluation: if id is even, skip string check.

▶ 2 MOD() Function (Alternative)
-- Alternative: using MOD() function SELECT id, movie, description, rating FROM Cinema WHERE MOD(id, 2) = 1 AND description != 'boring' ORDER BY rating DESC;

Why this works: MOD() is a standard SQL function equivalent to %. Slightly more portable across databases than %.

Performance: Identical to %. Some databases optimize % better than MOD() or vice versa; benchmark if critical.

▶ 3 CAST and Bitwise AND (Advanced)
-- Advanced: bitwise AND to check last bit SELECT id, movie, description, rating FROM Cinema WHERE (id & 1) = 1 AND description != 'boring' ORDER BY rating DESC;

Why this works: Bitwise AND (id & 1) checks if the least significant bit is set (odd). Fastest on many CPUs but less readable.

Performance: Microscopically faster than %, but negligible in practice. Use only for extreme optimization or in low-level code.

Easy #1527 Patients With a Condition

+

Find patients who have Type I Diabetes (conditions containing DIAB1 prefix). DIAB1 can appear at the start or after a space.

Tables: Patients (patient_id, patient_name, conditions)

→

Decision Tree Path

Master Tree: Single-Table Queries → Pattern A: Row-Level Filtering + Pattern L: String/Text Operations

Real-World Example

Clinical data systems store diagnoses as space-separated ICD codes. To extract patients with Type I Diabetes for a clinical trial, you filter the conditions column by the DIAB1 prefix, which may appear at the start or after other codes.

▶ 1 LIKE with % Wildcards
-- Most efficient for this data: LIKE pattern matching SELECT patient_id, patient_name, conditions FROM Patients WHERE conditions LIKE 'DIAB1%' OR conditions LIKE '% DIAB1%';

Why this is best: LIKE is fast for pattern matching and handles both cases: DIAB1 at the start or after a space. Easy to understand and maintain.

Performance: O(n) scan. LIKE with leading '%' is slower than without, but checking 'DIAB1%' first (no leading %) can short-circuit many rows. Indexes on conditions help if supported.

▶ 2 Regular Expression (PostgreSQL)
-- Alternative (PostgreSQL): regex for precise matching SELECT patient_id, patient_name, conditions FROM Patients WHERE conditions ~ '(^| )DIAB1';

Why this works: Regex (^| ) means "start of string OR space". Matches DIAB1 at start or after a space. More precise than multiple LIKE clauses.

Performance: Regex can be slower than LIKE for simple patterns, but on this query is comparable. Regex indexes (GIN/GIST) in PostgreSQL accelerate this further.

▶ 2 String Position Check (INSTR/POSITION)
-- Alternative: check position of DIAB1 SELECT patient_id, patient_name, conditions FROM Patients WHERE conditions LIKE 'DIAB1%' OR POSITION(' DIAB1' IN conditions) > 0;

Why this works: POSITION returns 0 if not found, > 0 if found. Handles both start and middle cases.

Performance: Slightly slower than LIKE due to function calls, but clearer intent. Use if code readability is a priority.

Easy #1517 Find Users With Valid E-Mails

+

Find users with valid emails where the email is at domain @leetcode.com and the prefix starts with a letter and contains only alphanumeric, underscore, period, or dash characters.

Tables: Users (user_id, name, mail)

→

Decision Tree Path

Master Tree: Single-Table Queries → Pattern A: Row-Level Filtering + Pattern L: String/Text Operations

Real-World Example

An email marketing system validates user emails before sending campaigns. Data quality checks filter out invalid formats and domains not matching the organization. This prevents bounces and ensures message delivery to the right audience.

▶ 1 Regular Expression (PostgreSQL)
-- Most precise: PostgreSQL regex validation SELECT user_id, name, mail FROM Users WHERE mail ~ '^[A-Za-z][A-Za-z0-9._-]*@leetcode\\.com$';

Why this is best: Regex precisely validates the format: must start with letter, contain allowed chars only, end with @leetcode.com. Single condition, clear intent.

Performance: O(n) scan. Regex matching is efficient in PostgreSQL. More precise than LIKE, avoiding false positives.

▶ 2 LIKE with Domain Check
-- Alternative (less precise): LIKE pattern SELECT user_id, name, mail FROM Users WHERE mail LIKE '[A-Za-z]%@leetcode.com';

Why this works: LIKE pattern checks domain and that the prefix starts with a letter. However, LIKE allows invalid characters (!, #, etc.) between the letter and @.

Performance: Slightly faster than regex but much less accurate. Only use if the data is pre-validated.

▶ 3 String Function Composition
-- Advanced: using string functions for validation SELECT user_id, name, mail FROM Users WHERE mail LIKE '%@leetcode.com' AND SUBSTRING(mail, 1, 1) ~ '[A-Za-z]' AND mail !~ '[^A-Za-z0-9._\-@]';

Why this works: Breaks validation into steps: domain check, first-char check, and no-invalid-chars check. Verbose but readable for teams unfamiliar with complex regex.

Performance: Slower: multiple function calls and regex checks. Use only if maintainability trumps performance.

Pattern Recognition: Join Problems

Join problems share a common theme: data lives across two or more tables, and you need to combine them based on a relationship. The key is identifying which rows from each table should be matched together.

Key signals to watch for: "for each X show Y from another table", "who has no...", "all combinations", "attended but", "attended or". Shared strategy: (1) Identify the join key relationship, (2) choose join type (INNER, LEFT, RIGHT, CROSS), (3) handle NULL values carefully. Common traps: accidental CROSS JOIN, NULL join keys breaking matches, duplicate rows from one-to-many relationships, forgetting GROUP BY after LEFT JOINs.

#1378 — Replace Employee ID With The Unique Identifier

Easy
+

Show the unique ID of each employee. If an employee has no unique ID, show null instead.

Problem: Show the unique ID of each employee. If an employee has no unique ID, show null instead.

Tables: Employees (id, name) and EmployeeUNI (id, unique_id)

Decision Tree Path

This is a LEFT JOIN pattern — all employees appear in output, with matching unique IDs or NULL.

Real-World Example

HR system merging internal employee IDs with SSO (Single Sign-On) identifiers. Not every employee has migrated to SSO yet, so some have NULL.

▶ 1 Most Efficient — LEFT JOIN with SELECT Order
SELECT eu.unique_id, e.name FROM Employees e LEFT JOIN EmployeeUNI eu ON e.id = eu.id ORDER BY eu.unique_id;

Why this is best: LEFT JOIN ensures all employees appear. Selecting unique_id first shows NULLs naturally for unmatched employees.

Performance: O(n + m) with index on EmployeeUNI.id. Clean, readable, minimal intermediate rows.

▶ 2 Alternative — COALESCE for Explicit NULL Handling
SELECT COALESCE(eu.unique_id, NULL) AS unique_id, e.name FROM Employees e LEFT JOIN EmployeeUNI eu ON e.id = eu.id;

Why this works: COALESCE explicitly handles NULL, making the intent clear (though redundant here since LEFT JOIN already produces NULLs).

When to use: If you need fallback values or multiple NULL coalescing logic.

Report product_name, year, and price for each sale. Join Sales and Product tables.

#577 — Employee Bonus

Easy
+

Report name and bonus for employees with bonus = 1000.

Problem: Report name and bonus for employees with bonus < 1000 OR no bonus. Filter out employees with bonus >= 1000.

Tables: Employee (empId, name, supervisor, salary) and Bonus (empId, bonus)

Decision Tree Path

This is an anti-join variant using LEFT JOIN with NULL detection. Keep unmatched rows (no bonus) and filter matched rows by condition.

Real-World Example

Payroll processing identifying employees due for bonus review: those with small bonuses (< 1000) or missing bonuses entirely.

▶ 1 Most Efficient — LEFT JOIN with NULL-aware WHERE
SELECT e.name, b.bonus FROM Employee e LEFT JOIN Bonus b ON e.empId = b.empId WHERE b.bonus < 1000 OR b.bonus IS NULL;

SELECT e.name, b.bonus FROM Employee e LEFT JOIN Bonus b ON e.empId = b.empId WHERE COALESCE(b.bonus, 0) < 1000;

Why this works: COALESCE treats NULL as 0, so NULL < 1000 is TRUE. One WHERE condition instead of OR.

#1075 — Project Employees I

Easy
+

Report average experience years for employees on each project, rounded to 2 decimals.

Problem: Report average experience years for employees on each project, rounded to 2 decimals.

Tables: Project (project_id, employee_id) and Employee (employee_id, name, experience_years)

Decision Tree Path

JOIN + GROUP BY aggregation. INNER JOIN connects projects to employees, then aggregate experience per project.

Real-World Example

Resource management calculating average team seniority per project to assess project complexity or team strength.

▶ 1 Most Efficient — INNER JOIN + GROUP BY + ROUND
SELECT p.project_id, ROUND(AVG(e.experience_years), 2) AS average_years FROM Project p INNER JOIN Employee e ON p.employee_id = e.employee_id GROUP BY p.project_id;

Why this is best: INNER JOIN merges projects and employees. GROUP BY aggregates by project. ROUND ensures 2 decimal precision.

SELECT p.project_id, CAST(AVG(e.experience_years) AS DECIMAL(10, 2)) AS average_years FROM Project p INNER JOIN Employee e ON p.employee_id = e.employee_id GROUP BY p.project_id;

Why this works: CAST to DECIMAL(10, 2) guarantees output type. Useful if you need exact decimal type downstream.

Difference: ROUND is simpler for display; CAST is stricter for storage or type requirements.

#1581 — Customer Who Visited but Did Not Make Any Transactions

Easy
+

Find customer IDs and count of visits where NO transaction occurred. Filter for NULL transactions.

Problem: Find customer IDs and count of visits where NO transaction occurred. Filter for NULL transactions.

Tables: Visits (visit_id, customer_id) and Transactions (transaction_id, visit_id, amount)

Decision Tree Path

This is a classic anti-join: LEFT JOIN then filter WHERE transaction IS NULL, then GROUP BY and COUNT.

Real-World Example

Retail analytics identifying "window shoppers" — customers who visited but didn't buy. Helps improve conversion tactics.

▶ 1 Most Efficient — LEFT JOIN + IS NULL Filter + GROUP BY
SELECT v.customer_id, COUNT(*) AS count_no_trans FROM Visits v LEFT JOIN Transactions t ON v.visit_id = t.visit_id WHERE t.transaction_id IS NULL GROUP BY v.customer_id;

Why this is best: LEFT JOIN keeps all visits. WHERE t.transaction_id IS NULL filters to unmatched visits only. COUNT(*) tallies them per customer.

Performance: O(n + m + k log k) where k = result size. Index on Transactions.visit_id and GROUP BY column speeds execution.

▶ 2 Alternative — NOT EXISTS Subquery
SELECT v.customer_id, COUNT(*) AS count_no_trans FROM Visits v WHERE NOT EXISTS ( SELECT 1 FROM Transactions t WHERE t.visit_id = v.visit_id ) GROUP BY v.customer_id;

Why this works: NOT EXISTS explicitly checks no transaction row exists for each visit. Can be faster on large datasets with good indexing.

Caveat: More verbose; correlated subqueries can be slower without proper indexing. LEFT JOIN + NULL is usually clearer.

#1280 — Students and Examinations

Medium
+

For each student-subject pair, count exam attempts. Ensure ALL student-subject combinations appear, even if 0 exams attended.

Problem: For each student-subject pair, count exam attempts. Ensure ALL student-subject combinations appear, even if 0 exams attended.

Tables: Students (student_id, student_name), Subjects (subject_name), Examinations (student_id, subject_name)

Decision Tree Path

Combined pattern: CROSS JOIN (all student-subject combos) + LEFT JOIN Examinations + GROUP BY + COUNT. Forces complete result set.

Real-World Example

Learning Management System (LMS) grade report: every student appears for every course, showing exam count or 0 if they haven't taken it yet.

▶ 1 Most Efficient — CROSS JOIN + LEFT JOIN + GROUP BY + COUNT
SELECT s.student_id, s.student_name, sub.subject_name, COUNT(e.student_id) AS attended_exams FROM Students s CROSS JOIN Subjects sub LEFT JOIN Examinations e ON s.student_id = e.student_id AND sub.subject_name = e.subject_name GROUP BY s.student_id, s.student_name, sub.subject_name ORDER BY s.student_id, sub.subject_name;

Why this is best: CROSS JOIN creates all student-subject pairs. LEFT JOIN matches exams; unmatched pairs get COUNT = 0. Guarantees complete output.

Performance: O(n * m + e log(n*m)) where n = students, m = subjects, e = exam records. Be careful with large student/subject counts.

▶ 2 Alternative — COALESCE on COUNT for Readability

Pattern Recognition: Subqueries

What subquery problems share: The answer depends on a computed intermediate result. A subquery lets you compute that result once (uncorrelated) or repeatedly for each row (correlated).

Key signals to spot a subquery problem:

  • "compared to average" or "vs. the max" — you need a scalar subquery
  • "second highest" or "Nth ranked" — use DISTINCT + ORDER BY LIMIT OFFSET

  • "who has ALL items" — NOT IN or subquery in WHERE
  • "employees whose manager left" — subquery to find missing IDs

Key strategy: Identify what the subquery computes (a scalar value, a list of IDs, or a temporary table), then decide where it goes (WHERE for filtering, FROM for a temp table, SELECT for a single-column result). Watch out for correlated subqueries (slow, runs per row) vs. uncorrelated (fast, runs once).

▶ 1 STRING_AGG with DISTINCT and ORDER BY
SELECT sell_date, COUNT(DISTINCT product) AS num_sold, STRING_AGG(DISTINCT product, ',' ORDER BY product) AS products FROM Activities GROUP BY sell_date ORDER BY sell_date;

Why this is best: PostgreSQL's STRING_AGG with ORDER BY internally sorts products before concatenation. DISTINCT eliminates duplicates within the aggregation. Clean, readable, one pass.

Gotcha (Critical): ORDER BY inside STRING_AGG uses positional references only in some PostgreSQL versions. Always test. In MySQL/SQLServer, STRING_AGG equivalent (GROUP_CONCAT or STRING_AGG) may not support ORDER BY in the aggregate; use a subquery or window function instead.

Performance: O(n log n) due to internal sort within aggregation. Indexes on (sell_date, product) help GROUP BY. Overall fast for typical daily summaries.

▶ 2 Subquery with DISTINCT and ORDER BY
SELECT sell_date, COUNT(DISTINCT product) AS num_sold, STRING_AGG(product, ',') AS products FROM ( SELECT DISTINCT sell_date, product FROM Activities ) AS unique_products GROUP BY sell_date ORDER BY sell_date;

Why this works: Reduces duplicates early (inner DISTINCT), then STRING_AGG concatenates without ORDER BY. If needed, use LISTAGG or ORDER subquery after.

Note: Products will NOT be sorted in output unless you use a second subquery or window function. Less elegant than approach #1 for PostgreSQL.

Performance: Extra subquery scan adds cost, but deduplication reduces rows for aggregation. Trade-off: slower than direct STRING_AGG but works across more SQL dialects.

▶ 3 Window Function with Sorted Aggregation (MySQL/SQLServer)
WITH ranked_products AS ( SELECT DISTINCT sell_date, product, ROW_NUMBER() OVER (PARTITION BY sell_date ORDER BY product) AS rn FROM Activities ) SELECT sell_date, COUNT(*) AS num_sold, STRING_AGG(product, ',') AS products FROM ranked_products GROUP BY sell_date ORDER BY sell_date;

Why this works: ROW_NUMBER enforces sort order before aggregation. Works in MySQL 8.0+ and SQLServer where STRING_AGG ORDER BY is unsupported or limited.

Performance: Window function adds complexity. Three scans: distinct, window, then aggregate. Slower than approach #1, use only if dialect forces it.

+

For each row with three lengths (x, y, z), determine if they form a valid triangle using the triangle inequality theorem.

Tables: Triangle (x, y, z)

→

Decision Tree Path

Master Tree: Single-Table Queries → Pattern I: Conditional Logic (CASE)

Real-World Example

Engineering validation checks dimensional constraints for manufactured parts. Three measurements are validated against triangle inequality (x+y>z, x+z>y, y+z>x) to ensure geometric feasibility before production sign-off.

▶ 1 CASE with Triangle Inequality All Conditions
SELECT x, y, z, CASE WHEN x + y > z AND x + z > y AND y + z > x THEN 'Yes' ELSE 'No' END AS triangle FROM Triangle;

Why this is best: Triangle inequality theorem: all three conditions must hold (x+y>z, x+z>y, y+z>x). Single CASE with AND logic is clear and efficient.

Gotcha: Must include ELSE clause. Without it, NULL is returned for false cases, not 'No'. This is a common mistake.

Performance: O(n) row-by-row evaluation. Short-circuit AND: if x+y≤z fails, remaining conditions skip (in most optimizers).

▶ 2 CASE with Negation (Simpler Logic)
SELECT x, y, z, CASE WHEN x + y <= z OR x + z <= y OR y + z <= x THEN 'No' ELSE 'Yes' END AS triangle FROM Triangle;

Why this works: Inverts logic: if ANY condition fails (≤ instead of >), return 'No', else 'Yes'. Equivalent to approach #1, sometimes easier to reason about.

Performance: Identical to approach #1. Choice is stylistic.

▶ 3 CASE with GREATEST (Less Common)
SELECT x, y, z, CASE WHEN GREATEST(x, y, z) < LEAST(x, y, z) + MEDIAN(x, y, z) THEN 'Yes' ELSE 'No' END AS triangle FROM Triangle;

Why this works: Triangle inequality reduces to: largest side < sum of two smaller sides. GREATEST finds the longest; LEAST and MEDIAN find the two shorter. One comparison only.

Caveat: MEDIAN is not standard SQL. PostgreSQL has percentile_cont; MySQL lacks it. Portable version uses manual sorting with multiple conditions—not simpler.

Performance: If MEDIAN exists, marginally faster (fewer comparisons). Otherwise, less portable and not worth it.
