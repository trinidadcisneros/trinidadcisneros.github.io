Six-Step Diagnostic Process

Before writing any SQL, work through these six steps. They take 2-3 minutes and prevent the most common mistakes: wrong JOIN type, missing GROUP BY column, or picking the wrong window function.

Step 1: Map Inputs and Output

▼

Read the problem statement and write down what you start with and what you need to produce.

What to write down:

  • Input table(s): Name each table and its columns. Note primary keys and foreign keys.
  • Output columns: List exactly what the result set should contain.
  • Output grain: What does one row in the output represent? (one user? one month? one department?)
  • Row count direction: Will the output have fewer rows, the same rows, or more rows than the input?

Step 2: Classify Inputs

▼

Pick one of three source types: Single table, Join 2+ tables, or Union queries.

Decision checklist:

  • How many tables? Count the FROM/JOIN tables you will need.
  • Joining or stacking? If 2+ tables, do they share a key (JOIN) or do you need to stack independent results (UNION)?
  • Self-join or scalar subquery? Self-joins and subqueries against the same table involve a virtual second copy — treat as Join 2+. Common self-join shapes: employee/manager (managerId → id), category/parent (parent_id → id), user/referrer (referee_id → id). The recipe for these is enrich-join, not row-compare (row-compare is reserved for sequential LAG/LEAD comparisons, not foreign-key lookups).
  • Post-join is single-table: After a JOIN the result is one set of rows, so any single-table shape recipe (filter, aggregate, scalar, rank, transform, compare, window) applies to the joined result.

Step 3: Name the Shape

▼

Use the signal words reference to identify which recipe category this problem matches.

Scan the problem statement for signal words and match them to a recipe shape. Use the reference table below this section for the full mapping. Common shapes:

  • Fewer rows, filtered: row-filter (WHERE conditions)
  • Fewer rows, grouped: group-aggregate (GROUP BY + SUM/COUNT/AVG)
  • Same rows, new column: row-transform (CASE WHEN) or row-compare (LAG/LEAD)
  • Single scalar value: scalar-extract (MAX, Nth value, overall percentage)
  • Multi-table enrichment: enrich-join or enrich-aggregate
  • Ranked per group: rank-partition (DENSE_RANK PARTITION BY)

Composite problems: Some problems chain two recipe moves in sequence (e.g., enrich-join then group-aggregate). If you see two shapes, plan for a CTE or subquery to handle the first shape, then apply the second.

▼

Each recipe card lists:

  • Signal words — confirm this is the right recipe
  • Technique — the SQL pattern to use (GROUP BY, LAG, JOIN, etc.)
  • Example problems — expand any problem to see full ranked solutions

Write your SQL skeleton based on the technique, filling in your specific table and column names.

Step 6: Sanity Check

▼

Before submitting, verify your query against common SQL traps.

Checklist:

  • Row count: Does SELECT COUNT(*) match your expectation from Step 1?
  • NULL handling: Did you account for NULLs in JOIN keys, WHERE filters, and aggregates?
  • Integer division: Did you cast to NUMERIC before dividing? (PostgreSQL: col::numeric)
  • GROUP BY completeness: Every non-aggregated column in SELECT must be in GROUP BY.
  • ORDER BY + LIMIT: If using LIMIT, is ORDER BY deterministic? (add a tiebreaker column)
  • Edge cases: Empty tables, single-row tables, all NULLs, ties in ranking.

SELECT
  TO_CHAR(trans_date, 'YYYY-MM') AS month,
  country,
  COUNT(*) AS trans_count,
  SUM(amount) AS trans_total_amount,
  SUM(CASE WHEN state = 'approved' THEN 1 ELSE 0 END) AS approved_count,
  SUM(CASE WHEN state = 'approved' THEN amount ELSE 0 END) AS approved_total_amount
FROM Transactions
GROUP BY TO_CHAR(trans_date, 'YYYY-MM'), country
ORDER BY month, country;

SQL Execution Order (How the Engine Processes Your Query)

Understanding this order helps you predict which clauses can reference which aliases and columns:

  1. FROM / JOIN — Tables are loaded and joined first
  2. WHERE — Row-level filtering (no aggregates allowed here)
  3. GROUP BY — Rows are grouped
  4. HAVING — Group-level filtering (aggregates allowed here)
  5. SELECT — Columns are computed (window functions run here)
  6. DISTINCT — Deduplication
  7. ORDER BY — Sorting (can reference SELECT aliases)
  8. LIMIT / OFFSET — Final row restriction

JOIN Checklist

  1. Identify the join key(s) — columns that connect the tables
  2. Choose join type: INNER (default), LEFT (keep all from first table), CROSS (all combinations)
  3. Check for duplicates in keys — many-to-many creates row explosion
  4. Handle NULL join keys — NULLs never match in a standard JOIN
  5. After joining: verify row count to ensure no unexpected multiplication

A quick lookup for the SQL techniques used across all 9 single table recipe categories, with explanations of when each method applies.

Technique What It Does When to Reach for It
Filtering Techniques
WHERE Keeps or removes rows based on a condition before any grouping happens The condition can be evaluated row by row without needing an aggregate
HAVING Filters groups after GROUP BY, using aggregate results The condition depends on a count, sum, or other aggregate (e.g., "groups with more than 1 row")

Reduce a Table to a Single Value 12 problems

▼

A single table (possibly grouped first) → one row, one column: a scalar result.

Signal words: "the single," "the highest," "second highest," "the one," "overall percentage"

Technique: MAX of filtered set, OFFSET for Nth value, MIN subquery + percentage

Common Trap: WHERE Returns 0 Rows Instead of NULL

Many scalar-extract problems expect NULL when nothing qualifies (e.g., "second highest salary" when there is only one salary, or the table is empty). If you use WHERE rank = 2 and no row has rank 2, your query returns 0 rows — not a row containing NULL. That fails the test case.

Why it breaks: WHERE can only remove rows. If every row gets removed, the result set is empty. There is no row left to hold a NULL value.

The fix: Move the filter into a subquery inside SELECT. The outer SELECT has no FROM clause, so it always produces exactly 1 row. The subquery fills in the value — if nothing matches, it returns NULL.

-- BREAKS: returns 0 rows when nothing qualifies
SELECT salary FROM rankings WHERE rank = 2;

-- WORKS: always returns 1 row, NULL if nothing qualifies
SELECT (SELECT salary FROM rankings WHERE rank = 2) AS result;

How to spot this: If the problem says "return NULL if no result exists" or the expected output includes a NULL row, you need the subquery-in-SELECT pattern. Look for phrases like "if there is no second highest," "if no such value exists," or an empty table test case.

MySQL Variant: DELETE p1 FROM Person p1 JOIN Person p2 ON p1.email = p2.email AND p1.id > p2.id;

Gotcha: Self-join can be slow if table is large. O(n²) worst case for full cross join before filter.

Performance: Hash join on (email) reduces complexity. Still slower than approach #1 for very large tables.

▶ 3 DELETE with ROW_NUMBER Window Function
DELETE FROM Person WHERE id NOT IN ( SELECT id FROM ( SELECT id, ROW_NUMBER() OVER (PARTITION BY email ORDER BY id) AS rn FROM Person ) ranked WHERE rn = 1 );

Why this works: ROW_NUMBER ranks rows per email (ordered by id). rn=1 is the lowest id. Keep all rn=1 rows, delete rest.

Caveat: Window functions require nested subqueries. More complex syntax. Marginally clearer intent ("keep first per group") but overkill for this problem.

Performance: Window function scan, then subquery filter, then DELETE. Similar to approach #1 in cost but more overhead.

Join Techniques

▼

UNION two queries: (1) User with most ratings (tie: lexicographically smaller name), (2) Movie with highest average rating in Feb 2020 (tie: lexicographically smaller title). Return results column.

Business Context: Platform Recognition Reports

Entertainment platforms recognize "Top Reviewer of the Month" and "Movie of the Month" to drive engagement and surface quality content.

▶ Rank 1: Two Separate Queries UNIONed Clear separation of concerns
-- Top reviewer (most ratings) SELECT u.name AS results FROM Users u INNER JOIN MovieRating mr ON u.user_id = mr.user_id GROUP BY u.user_id, u.name ORDER BY COUNT(*) DESC, u.name ASC LIMIT 1 UNION ALL -- Top movie in Feb 2020 SELECT m.title AS results FROM Movies m INNER JOIN MovieRating mr ON m.movie_id = mr.movie_id WHERE YEAR(mr.created_at) = 2020 AND MONTH(mr.created_at) = 2 GROUP BY m.movie_id, m.title ORDER BY AVG(mr.rating) DESC, m.title ASC LIMIT 1;

Why this ranks first: Two separate queries are easy to understand and maintain. Each has its own sorting logic. UNION ALL preserves order. No complicated joins or conditionals.

▶ Rank 2: CTEs + Single Query Combines both with CTEs
WITH top_reviewer AS ( SELECT u.name AS results, 1 AS query_order FROM Users u INNER JOIN MovieRating mr ON u.user_id = mr.user_id GROUP BY u.user_id, u.name ORDER BY COUNT(*) DESC, u.name ASC LIMIT 1 ), top_movie AS ( SELECT m.title AS results, 2 AS query_order FROM Movies m INNER JOIN MovieRating mr ON m.movie_id = mr.movie_id WHERE EXTRACT(YEAR FROM mr.created_at) = 2020 AND EXTRACT(MONTH FROM mr.created_at) = 2 GROUP BY m.movie_id, m.title ORDER BY AVG(mr.rating) DESC, m.title ASC LIMIT 1 ) SELECT results FROM top_reviewer UNION ALL SELECT results FROM top_movie ORDER BY query_order;

Tradeoff: CTEs add clarity (labeled queries), but increase complexity. Two separate table scans (one per CTE). EXTRACT is more portable than YEAR/MONTH in some databases.

▶ Rank 3: Subqueries in FROM (Complex) Avoid this approach
SELECT * FROM ( SELECT u.name AS results, ROW_NUMBER() OVER (ORDER BY cnt DESC, u.name ASC) AS rn FROM Users u INNER JOIN ( SELECT user_id, COUNT(*) AS cnt FROM MovieRating GROUP BY user_id ) mr ON u.user_id = mr.user_id ) reviewer WHERE rn = 1 UNION ALL SELECT * FROM ( SELECT m.title AS results, ROW_NUMBER() OVER (ORDER BY avg_rating DESC, m.title ASC) AS rn FROM Movies m INNER JOIN ( SELECT movie_id, AVG(rating) AS avg_rating FROM MovieRating WHERE YEAR(created_at) = 2020 AND MONTH(created_at) = 2 GROUP BY movie_id ) mr ON m.movie_id = mr.movie_id ) movie WHERE rn = 1;

Two separate UNION queries (Rank 1) each run their logic independently, then combine. CTEs (Rank 2) materialize both results. Nested subqueries (Rank 3) force multiple scans. For small result sets (LIMIT 1 each), Rank 1 is simplest. For larger result sets, CTEs may cache results better.
