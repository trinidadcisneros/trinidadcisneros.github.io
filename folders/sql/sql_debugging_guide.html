How to Read a PostgreSQL Error

PostgreSQL error messages follow a consistent structure. Knowing where to look saves you from guessing.

ERROR: column "department_name" must appear in the GROUP BY clause or be used in an aggregate function LINE 3: department_name, ^ DETAIL: ... HINT: Add department_name to the GROUP BY clause.

Anatomy of the Error

Part What It Tells You Where to Look
ERROR: The main error type and description Read this first — it's the classification
LINE N: The exact line number where the error was detected Jump to this line in your query
^ (caret) Points to the exact character position The problem is at or just before the caret
DETAIL: Additional context about the cause Not always present; read when available
HINT: PostgreSQL's suggested fix Often exactly right — don't ignore it

The 3-Second Read

When you see an error in an interview, read it in this order:

  1. ERROR line — What category of problem is this? (syntax? type? reference?)
  2. LINE number — Where in the query?
  3. HINT — Does PostgreSQL already know the fix?

Interview Tip

Read the error message out loud to the interviewer. It shows you're systematic, not guessing. Say: "The error says column X must appear in the GROUP BY clause, on line 3 — so I need to either add it to GROUP BY or wrap it in an aggregate."

Key Insight

Errors fall into two buckets — hard errors (the query won't run) and silent errors (the query runs but returns wrong results). Silent errors are harder and more common in interviews.

Syntax Errors (Pattern A)

Error messages: syntax error at or near "...", unexpected token

These are the most common errors — a missing comma, misplaced keyword, or unclosed parenthesis.

A1. Missing comma between SELECT columns

+

syntax error at or near "employee_name"

-- BROKEN SELECT employee_id employee_name -- <- missing comma after employee_id FROM Employees;
ERROR: syntax error at or near "employee_name" LINE 3: employee_name ^

Fix: Add the comma. Verify: Query runs and returns expected columns.

SELECT employee_id, employee_name FROM Employees;

A2. Using a reserved keyword as an alias

+

syntax error at or near "order"

-- BROKEN SELECT COUNT(*) AS order, -- <- "order" is a reserved keyword customer_id FROM Orders GROUP BY customer_id;

Fix: Quote the alias or choose a different name.

SELECT COUNT(*) AS "order", -- quoted (works but awkward) COUNT(*) AS order_count -- better: just rename it FROM Orders GROUP BY customer_id;

A3. Misplaced or missing keyword

+

syntax error at or near "INNER"

-- BROKEN: WHERE before JOIN SELECT e.name, d.department_name FROM Employees e WHERE e.salary > 50000 INNER JOIN Departments d ON e.dept_id = d.dept_id;

Why: SQL clause order is FROM → JOIN → WHERE → GROUP BY → HAVING → ORDER BY → LIMIT.

Fix:

SELECT e.name, d.department_name FROM Employees e INNER JOIN Departments d ON e.dept_id = d.dept_id WHERE e.salary > 50000;

A4. Unclosed parenthesis

+

syntax error at or near ";"

-- BROKEN SELECT * FROM Orders WHERE status IN ('active', 'pending'; -- <- missing closing )

Fix: Count your parentheses. The caret points to the `;` because PostgreSQL was still expecting `)`.

SELECT * FROM Orders WHERE status IN ('active', 'pending');

Error points to a keyword (JOIN, GROUP, ORDER) Wrong clause order
Error points to ; Unclosed parenthesis or quote
Error mentions a common word (order, table, user, group) Reserved keyword used as alias
Column & Table Reference Errors (Pattern B)

Error messages: column "X" does not exist, relation "X" does not exist, column reference "X" is ambiguous

B1. Ambiguous column in a JOIN

+

column reference "customer_id" is ambiguous

-- BROKEN SELECT customer_id, name, order_date -- <- customer_id exists in both tables FROM Customers c JOIN Orders o ON c.customer_id = o.customer_id;

Fix: Prefix every column with its table alias.

SELECT c.customer_id, c.name, o.order_date FROM Customers c JOIN Orders o ON c.customer_id = o.customer_id;

B2. Using a SELECT alias in WHERE

+

column "annual_salary" does not exist

-- BROKEN SELECT salary * 12 AS annual_salary FROM Employees WHERE annual_salary > 100000; -- <- alias not available in WHERE

Why: PostgreSQL evaluates WHERE before SELECT, so the alias doesn't exist yet. Repeat the expression or use a CTE.

Option 1: Repeat the expression

SELECT salary * 12 AS annual_salary FROM Employees WHERE salary * 12 > 100000;

Option 2: CTE (cleaner for complex expressions)

WITH emp AS ( SELECT *, salary * 12 AS annual_salary FROM Employees ) SELECT * FROM emp WHERE annual_salary > 100000;

B3. Referencing a column from a table not in FROM

+

missing FROM-clause entry for table "d"

-- BROKEN: forgot to join the Departments table SELECT e.name, d.department_name FROM Employees e WHERE e.salary > 50000;

Fix: Either add the JOIN or remove the reference.

SELECT e.name, d.department_name FROM Employees e INNER JOIN Departments d ON e.dept_id = d.dept_id WHERE e.salary > 50000;

Type Mismatch & Casting Errors (Pattern C)

Error messages: operator does not exist: varchar = integer, cannot cast type, invalid input syntax for type

C1. Comparing a string column to an integer

+

operator does not exist: character varying = integer

-- BROKEN: zip_code is VARCHAR but compared to integer SELECT * FROM Customers WHERE zip_code = 90210;

Fix: Match the type — use a string literal.

SELECT * FROM Customers WHERE zip_code = '90210';

C2. Aggregating a non-numeric column

+

function sum(character varying) does not exist

-- BROKEN SELECT SUM(status) FROM Orders; -- status is VARCHAR

Fix: You probably want COUNT not SUM, or you need CASE to convert to numeric first.

-- Count occurrences SELECT COUNT(*) FROM Orders WHERE status = 'active'; -- Or sum a derived numeric value SELECT SUM(CASE WHEN status = 'active' THEN 1 ELSE 0 END) FROM Orders;

C3. Date format mismatch

+

Ambiguous date format causes unpredictable results

-- BROKEN: ambiguous date format SELECT * FROM Orders WHERE order_date = '03/04/2024'; -- Is this March 4 or April 3? Depends on locale settings.

Fix: Always use ISO 8601 format ('YYYY-MM-DD').

SELECT * FROM Orders WHERE order_date = '2024-03-04';

C4. Integer division returning 0 instead of decimal

+

Silent error: 3 / 5 = 0, not 0.6

-- BROKEN (silent error — query runs but result is wrong) SELECT completed_tasks / total_tasks AS completion_rate FROM Projects; -- If both are integers: 3 / 5 = 0, not 0.6

Fix: Cast one operand to a decimal type.

SELECT completed_tasks::DECIMAL / total_tasks AS completion_rate FROM Projects; -- Or: CAST(completed_tasks AS DECIMAL) / total_tasks

Type Error Quick Reference

Error Pattern Usual Cause Fix
operator does not exist: varchar = integer Comparing string to number Add quotes or cast
function sum(varchar) Aggregating a text column Use COUNT or CASE
invalid input syntax for type date Wrong date format Use 'YYYY-MM-DD'
Division returns 0 Integer division Cast to DECIMAL or NUMERIC
Aggregation & GROUP BY Errors (Pattern D)

Error messages: must appear in the GROUP BY clause or be used in an aggregate function, aggregate functions are not allowed in WHERE

These are the most common interview errors — they come up in nearly every GROUP BY problem.

D1. SELECT column not in GROUP BY

+

column "employees.employee_name" must appear in the GROUP BY clause or be used in an aggregate function

-- BROKEN SELECT department_id, employee_name, COUNT(*) FROM Employees GROUP BY department_id; -- <- employee_name is not grouped or aggregated

Fix: Either add it to GROUP BY or wrap it in an aggregate.

-- Option 1: Add to GROUP BY (if you want per-employee counts) SELECT department_id, employee_name, COUNT(*) FROM Employees GROUP BY department_id, employee_name; -- Option 2: Remove it (if you want per-department counts) SELECT department_id, COUNT(*) FROM Employees GROUP BY department_id;

D2. Using aggregate in WHERE instead of HAVING

+

aggregate functions are not allowed in WHERE

-- BROKEN SELECT department_id, COUNT(*) AS emp_count FROM Employees WHERE COUNT(*) > 5 -- <- aggregate not allowed in WHERE GROUP BY department_id;

Why: WHERE filters rows before grouping. HAVING filters groups after aggregation.

Fix:

SELECT department_id, COUNT(*) AS emp_count FROM Employees GROUP BY department_id HAVING COUNT(*) > 5;

D3. ORDER BY a non-selected, non-grouped column

+

column "employees.employee_name" must appear in the GROUP BY clause or be used in an aggregate function

-- BROKEN SELECT department_id, COUNT(*) AS emp_count FROM Employees GROUP BY department_id ORDER BY employee_name; -- <- not in GROUP BY or aggregate

Fix: ORDER BY a column that's in SELECT or wrap it in an aggregate (e.g., ORDER BY MAX(employee_name)).

SELECT department_id, COUNT(*) AS emp_count FROM Employees GROUP BY department_id ORDER BY COUNT(*) DESC;

The WHERE vs. HAVING Rule

WHERE
Filters ROWS
Runs BEFORE GROUP BY
Cannot use aggregates
e.g., salary > 50000
HAVING
Filters GROUPS
Runs AFTER GROUP BY
Can use aggregates
e.g., COUNT(*) > 5
NULL Traps (Pattern E)

No error message — the query runs but results are wrong. These are the most dangerous interview errors because you won't see an error; you have to know to check.

E1. COUNT(*) vs COUNT(column)

+

These return DIFFERENT numbers when NULLs exist

-- These return DIFFERENT numbers when NULLs exist SELECT COUNT(*) AS total_rows, -- counts ALL rows (5) COUNT(email) AS rows_with_email -- skips NULLs (3) FROM Customers;
customer_id email
1 a@test.com
2 NULL
3 b@test.com
4 NULL
5 c@test.com

COUNT(*) = 5, COUNT(email) = 3. If you use COUNT(email) when you meant "total customers," your result is silently wrong.

Fix: Use COUNT(*) for total rows. Use COUNT(column) only when you intentionally want to exclude NULLs.

E2. NULL in NOT IN

+

Returns 0 rows if any manager_id is NULL

-- BROKEN: Returns 0 rows if any manager_id is NULL SELECT * FROM Employees WHERE employee_id NOT IN (SELECT manager_id FROM Employees);

Why: If manager_id has even one NULL, NOT IN evaluates to UNKNOWN for every row, returning nothing.

Safe: NOT EXISTS handles NULLs correctly

SELECT * FROM Employees e WHERE NOT EXISTS ( SELECT 1 FROM Employees m WHERE m.manager_id = e.employee_id );

Or: Filter NULLs from the subquery

SELECT * FROM Employees WHERE employee_id NOT IN ( SELECT manager_id FROM Employees WHERE manager_id IS NOT NULL );

E3. NULL in arithmetic — SUM, AVG, and comparisons

+

NULL + 100 = NULL; NULL > 5 = NULL; AVG ignores NULLs

-- NULL + 100 = NULL (not 100) -- NULL > 5 = NULL (not TRUE or FALSE) -- AVG ignores NULLs: AVG(10, NULL, 20) = 15, not 10

Fix: Use COALESCE to set a default.

SELECT COALESCE(bonus, 0) + salary AS total_comp FROM Employees;

E4. NULL in WHERE != comparisons

+

Missing rows where status IS NULL

-- BROKEN: Misses rows where status IS NULL SELECT * FROM Orders WHERE status != 'cancelled';

Rows where status IS NULL are not returned — because NULL != 'cancelled' evaluates to NULL (not TRUE).

Fix: Explicitly include NULLs.

SELECT * FROM Orders WHERE status != 'cancelled' OR status IS NULL; -- Or use IS DISTINCT FROM (PostgreSQL-specific) SELECT * FROM Orders WHERE status IS DISTINCT FROM 'cancelled';

NULL Trap Checklist

Trap Symptom Fix
COUNT(col) vs COUNT(*) Row count lower than expected Use COUNT(*) for total rows
NOT IN with NULLs Zero rows returned Use NOT EXISTS
!= missing NULLs Fewer rows than expected Add OR col IS NULL
Arithmetic with NULL NULL results propagating Wrap in COALESCE(col, 0)
AVG ignoring NULLs Average seems too high/low Decide: treat NULL as 0 or exclude?
JOIN & Row Count Errors (Pattern F)

No error message — the query runs but produces too many or too few rows. The most common cause of wrong aggregations in interviews.

F1. Fan-out — row count inflates after JOIN

+

Expected: 100 customers. Got: 350 rows.

-- Expected: 100 customers. Got: 350 rows. SELECT c.customer_id, c.name, o.order_id FROM Customers c JOIN Orders o ON c.customer_id = o.customer_id;

Why: One customer can have multiple orders. The JOIN duplicates customer rows — one per order.

Diagnosis:

-- Check: how many orders per customer? SELECT customer_id, COUNT(*) FROM Orders GROUP BY customer_id ORDER BY 2 DESC;

Fix: Aggregate first, then join.

WITH order_counts AS ( SELECT customer_id, COUNT(*) AS order_count FROM Orders GROUP BY customer_id ) SELECT c.customer_id, c.name, oc.order_count FROM Customers c JOIN order_counts oc ON c.customer_id = oc.customer_id;

F2. Missing ON clause → Cartesian product

+

Returns customers × orders (every combination)

-- BROKEN: Returns customers × orders (every combination) SELECT c.name, o.order_date FROM Customers c, Orders o; -- <- implicit cross join, missing WHERE

Fix: Use explicit JOIN with ON clause.

SELECT c.name, o.order_date FROM Customers c INNER JOIN Orders o ON c.customer_id = o.customer_id;

F3. INNER JOIN silently drops rows

+

Expected all customers, but 20 are missing

-- Expected all customers, but 20 are missing SELECT c.customer_id, o.order_id FROM Customers c INNER JOIN Orders o ON c.customer_id = o.customer_id;

Why: INNER JOIN drops customers who have no orders. If the question says "all customers" or "including those with no orders," use LEFT JOIN.

Diagnosis:

-- How many customers have no orders? SELECT COUNT(*) FROM Customers c LEFT JOIN Orders o ON c.customer_id = o.customer_id WHERE o.customer_id IS NULL;

Fix: Use LEFT JOIN when you need all rows from the left table.

SELECT c.customer_id, c.name, o.order_id FROM Customers c LEFT JOIN Orders o ON c.customer_id = o.customer_id;

F4. Duplicate join key causing double-counting

+

SUM is 2x expected because the join duplicated rows

-- SUM is 2x expected because the join duplicated rows SELECT d.department_name, SUM(e.salary) FROM Departments d JOIN Employees e ON d.dept_id = e.dept_id JOIN Projects p ON e.employee_id = p.employee_id -- <- 1:many GROUP BY d.department_name;

Why: If an employee is on 3 projects, their salary gets summed 3 times.

Fix: Aggregate in a CTE before the second join, or use SUM(DISTINCT e.salary) if salaries are unique.

WITH emp_projects AS ( SELECT DISTINCT e.employee_id, e.salary, d.dept_id FROM Employees e JOIN Departments d ON e.dept_id = d.dept_id ) SELECT d.department_name, SUM(ep.salary) FROM Departments d JOIN emp_projects ep ON d.dept_id = ep.dept_id GROUP BY d.department_name;

JOIN Error Diagnostic Flow

Row count wrong after JOIN?
▼
TOO MANY ROWS
Check for duplicate keys (fan-out)
Missing ON clause (Cartesian product)
Fix: Aggregate before joining
TOO FEW ROWS
INNER JOIN dropping unmatched? → LEFT JOIN
WHERE filtering NULLs? → Move to ON
Fix: Check with LEFT JOIN + IS NULL
Window Function Errors (Pattern G)

Error messages: window functions are not allowed in WHERE, aggregate function calls cannot be nested

G1. Using a window function in WHERE

+

column "rn" does not exist

-- BROKEN SELECT employee_id, salary, ROW_NUMBER() OVER (ORDER BY salary DESC) AS rn FROM Employees WHERE rn <= 5; -- <- window function not available in WHERE

Fix: Window functions are computed after WHERE. Wrap in a CTE or subquery.

WITH ranked AS ( SELECT employee_id, salary, ROW_NUMBER() OVER (ORDER BY salary DESC) AS rn FROM Employees ) SELECT * FROM ranked WHERE rn <= 5;

G2. Nesting an aggregate inside a window function

+

aggregate function calls cannot be nested

-- BROKEN SELECT department_id, SUM(COUNT(*)) OVER (ORDER BY department_id) FROM Employees GROUP BY department_id;

Fix: Compute the aggregate in a CTE first, then apply the window.

WITH dept_counts AS ( SELECT department_id, COUNT(*) AS emp_count FROM Employees GROUP BY department_id ) SELECT department_id, SUM(emp_count) OVER (ORDER BY department_id) AS running_total FROM dept_counts;

G3. Wrong window frame — ROWS vs RANGE (silent error)

+

7-day rolling average averages 7 ROWS instead of 7 DAYS

-- Intended: 7-day rolling average -- Actual: averages over 7 ROWS, not 7 DAYS SELECT visited_on, AVG(amount) OVER (ORDER BY visited_on ROWS BETWEEN 6 PRECEDING AND CURRENT ROW) FROM Customer;

Why: If multiple rows share the same date, ROWS BETWEEN 6 PRECEDING counts 6 prior rows, not 6 prior days.

Fix: Pre-aggregate to one row per date, then use ROWS.

G4. Missing PARTITION BY — window spans entire table

+

Rank across ALL employees instead of per department

-- Intended: rank within each department -- Actual: ranks across ALL employees SELECT employee_id, department_id, RANK() OVER (ORDER BY salary DESC) AS dept_rank FROM Employees;

Fix: Add PARTITION BY.

RANK() OVER (PARTITION BY department_id ORDER BY salary DESC) AS dept_rank
Subquery Errors (Pattern H)

Error messages: subquery must return only one column, subquery used as an expression must return at most one row, subquery in FROM must have an alias

H1. Scalar subquery returns multiple rows

+

more than one row returned by a subquery used as an expression

-- BROKEN: subquery returns multiple department_ids SELECT employee_name FROM Employees WHERE department_id = (SELECT department_id FROM Departments WHERE location = 'NYC');

Fix: Use IN instead of = when the subquery returns multiple rows.

WHERE department_id IN (SELECT department_id FROM Departments WHERE location = 'NYC');

H2. Missing alias on derived table

+

subquery in FROM must have an alias

-- BROKEN SELECT * FROM (SELECT customer_id, COUNT(*) FROM Orders GROUP BY customer_id);

Fix: Always alias subqueries in FROM.

SELECT * FROM ( SELECT customer_id, COUNT(*) AS order_count FROM Orders GROUP BY customer_id ) AS order_summary;

H3. Correlated subquery referencing wrong scope

+

Alias e3 doesn't exist inside the inner subquery

-- BROKEN: e3 alias not visible inside the inner subquery SELECT e1.name FROM Employees e1 WHERE e1.salary > ( SELECT AVG(e2.salary) FROM Employees e2 WHERE e2.department_id = e3.department_id -- <- e3 doesn't exist );

Fix: Check that all correlated references point to the correct outer alias.

SELECT e1.name FROM Employees e1 WHERE e1.salary > ( SELECT AVG(e2.salary) FROM Employees e2 WHERE e2.department_id = e1.department_id -- <- reference outer e1 );
Division by Zero & Arithmetic Errors (Pattern I)

Error message: division by zero

I1. Division by zero in a ratio calculation

+

division by zero

-- BROKEN: total_tasks could be 0 SELECT project_id, completed_tasks / total_tasks AS completion_rate FROM Projects;

Fix: Use NULLIF to convert 0 to NULL (which makes the division return NULL instead of erroring).

SELECT project_id, completed_tasks / NULLIF(total_tasks, 0) AS completion_rate FROM Projects;

I2. Safe division pattern (return 0 instead of NULL)

+

COALESCE + NULLIF safe division pattern

SELECT project_id, COALESCE(completed_tasks::DECIMAL / NULLIF(total_tasks, 0), 0) AS completion_rate FROM Projects;

Pattern breakdown: NULLIF(total_tasks, 0) → returns NULL if zero → division returns NULL → COALESCE(..., 0) → converts NULL to 0.

I3. Integer division returning 0

+

3 / 5 = 0 instead of 0.6

-- PostgreSQL integer division: 3 / 5 = 0 (not 0.6) SELECT ROUND(3::DECIMAL / 5, 2); -- = 0.60

Interview Tip

When computing rates or percentages, always cast to DECIMAL first and use ROUND for clean output.

SQL Execution Order — Why It Matters

PostgreSQL executes SQL clauses in a specific order, not the order you write them. This is why some things fail and others work — understanding this order is key to debugging and interview success.

  1. FROM / JOIN — Tables are loaded and joined
  2. WHERE — Row-level filtering (before grouping)
  3. GROUP BY — Rows grouped into buckets
  4. HAVING — Group-level filtering (after grouping)
  5. WINDOW FUNCTIONS — Computed over grouped/filtered result
  6. SELECT — Columns chosen, aliases assigned
  7. DISTINCT — Duplicate rows removed
  8. ORDER BY — Results sorted
  9. LIMIT / OFFSET — Final row trimming

Let's look at why this order matters with specific error examples.

Error: Using a window function in WHERE
-- BROKEN: Tries to filter by ROW_NUMBER() in WHERE SELECT * FROM table WHERE ROW_NUMBER() OVER (PARTITION BY key_col ORDER BY id ASC) = 1;

Error: window functions are not allowed in WHERE

Why: WHERE (step 2) runs BEFORE window functions (step 5). The window hasn't been computed yet.

Fix: Wrap in CTE/subquery:

WITH ranked AS ( SELECT *, ROW_NUMBER() OVER (PARTITION BY key_col ORDER BY id ASC) AS rn FROM table ) SELECT * FROM ranked WHERE rn = 1;
Error: Using a SELECT alias in WHERE
SELECT salary * 12 AS annual_salary FROM Employees WHERE annual_salary > 100000;

Error: column "annual_salary" does not exist

Why: WHERE (step 2) runs before SELECT (step 6), so the alias doesn't exist yet.

Fix: Repeat the expression or use a CTE.

SELECT salary * 12 AS annual_salary FROM Employees WHERE salary * 12 > 100000;
Error: Using aggregate in WHERE
SELECT department_id, COUNT(*) AS emp_count FROM Employees WHERE COUNT(*) > 5 GROUP BY department_id;

Error: aggregate functions are not allowed in WHERE

Why: WHERE (step 2) runs before GROUP BY (step 3). Groups haven't been formed yet.

Fix: Use HAVING (step 4) which runs after GROUP BY.

SELECT department_id, COUNT(*) AS emp_count FROM Employees GROUP BY department_id HAVING COUNT(*) > 5;
Why ORDER BY CAN use aliases (it works!)
SELECT salary * 12 AS annual_salary FROM Employees ORDER BY annual_salary; -- This WORKS!

Why it works: ORDER BY (step 8) runs AFTER SELECT (step 6), so the alias exists.

Error: DISTINCT before ORDER BY surprise
SELECT DISTINCT department_id FROM Employees ORDER BY salary; -- ERROR in standard SQL

Error: ORDER BY items must appear in the select list if DISTINCT is specified

Why: DISTINCT (step 7) removes duplicates before ORDER BY (step 8), but if ORDER BY uses a column not in SELECT, the result would be non-deterministic.

Fix: Either add the column to SELECT or don't use ORDER BY on non-selected columns.

SELECT DISTINCT department_id, salary FROM Employees ORDER BY salary;

Interview Tip

When you get an error about "not available" or "doesn't exist," think through the execution order. Say out loud: "WHERE runs in step 2, but the window function runs in step 5, so that's why it doesn't work."

Code Review Checklist

When reviewing someone else's SQL in an interview, scan for these issues in order:

Pass 1 — Structure (5 seconds)

Check What to Look For
Clause order SELECT → FROM → JOIN → WHERE → GROUP BY → HAVING → ORDER BY → LIMIT
Table aliases Every table has an alias; aliases are used consistently
Indentation Subqueries and CTEs are properly indented for readability

Pass 2 — Logic (30 seconds)

Check What to Look For
JOIN type Should it be LEFT JOIN instead of INNER JOIN? Does the question say "all" or "including"?
GROUP BY completeness Every non-aggregated SELECT column appears in GROUP BY
WHERE vs HAVING Are aggregates used in WHERE? They need to be in HAVING
NULL handling Any NOT IN subqueries? Any != that should include IS NULL?
Alias scope Is a SELECT alias used in WHERE? (Not valid in standard SQL)

Pass 3 — Data Correctness (30 seconds)

Check What to Look For
Fan-out Will the JOIN produce more rows than expected?
COUNT(*) vs COUNT(col) Which one matches the intent?
Integer division Will a ratio return 0 instead of a decimal?
Division by zero Is there a NULLIF or CASE guard?
Date format ISO 8601? Or ambiguous MM/DD vs DD/MM?
DISTINCT necessity Is DISTINCT masking a bad join instead of fixing the root cause?

Interview Tip

Narrate your review out loud. Say: "First I'll check the structure... clause order looks correct. Now the logic — I see an INNER JOIN, but the question says 'all customers,' so this should be a LEFT JOIN." This shows your process.

Debugging Workflow Under Pressure

When you get a broken query in an interview, follow these 5 steps:

Step 1: READ the error message
Say it out loud. Identify the category.
▼
Step 2: LOCATE the problem
Go to the LINE number. Look at the caret.
▼
Step 3: ISOLATE the cause
Comment out sections. Run simpler versions.
Does SELECT * FROM table work? Add back one clause.
▼
Step 4: FIX the root cause
Don't patch symptoms. Fix the actual problem.
(DISTINCT is often a patch, not a fix)
▼
Step 5: VERIFY the fix
Check row count. Check edge cases. Check NULLs.
"Let me verify: I expect N rows because..."

Isolation Techniques

Technique When to Use
Comment out a JOIN Isolate which join causes fan-out
Replace SELECT * with SELECT COUNT(*) Quick row count check
Add LIMIT 10 See sample output before debugging logic
SELECT DISTINCT test If DISTINCT fixes the count, you have a join duplication problem
Run the subquery alone Does it return what you expect?

What to Say Out Loud

  • "The error says [X], which means [Y]. Let me check line [N]."
  • "I'm going to isolate the problem by commenting out the second JOIN."
  • "The row count is higher than expected — I think there's a fan-out. Let me check for duplicate keys."
  • "I'll verify by checking: I expect [N] rows because [reason]."

The #1 rule: Never silently stare at a query. Talk through your process. Even if you're unsure, narrating your thought process scores points.

Common Interview Traps

These are errors interviewers plant deliberately to see if you catch them:

Trap What the Interviewer Planted What They Want You to Say
INNER JOIN when LEFT JOIN needed Question says "all customers" but query uses INNER JOIN "This should be LEFT JOIN since we need all customers, including those with no orders."
COUNT(*) when COUNT(col) needed COUNT includes rows that should be excluded (NULLs) "COUNT(*) counts all rows. If we want only non-NULL values, we should use COUNT(email)."
Missing GROUP BY column A column in SELECT isn't in GROUP BY "employee_name isn't in the GROUP BY — this will error. We need to add it or remove it."
NOT IN with NULLable column Subquery could return NULLs, causing zero results "If manager_id has NULLs, NOT IN will return nothing. I'd use NOT EXISTS instead."
Integer division Rate/percentage returns 0 "This is integer division — 3/5 = 0. I need to cast to DECIMAL first."
Fan-out join JOIN duplicates rows, inflating a SUM or COUNT "This JOIN creates a 1:many relationship. I should aggregate in a CTE first, then join."
WHERE instead of HAVING Aggregate function used in WHERE clause "Aggregate functions can't go in WHERE — they need to be in HAVING, which runs after GROUP BY."
DISTINCT masking bad join DISTINCT hides a join duplication problem "The DISTINCT is suspicious — it might be masking a fan-out. Let me check the join keys."
Missing NULL check in != WHERE status != 'cancelled' misses NULL status rows "This won't include rows where status is NULL. I'd add OR status IS NULL."

Final Tip

In a debugging interview, the process matters as much as the answer. Read the error, classify it, fix the root cause, and verify. Show that you're methodical, not just lucky.
