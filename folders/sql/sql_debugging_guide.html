Key Insight

Errors fall into two buckets — hard errors (the query won't run) and silent errors (the query runs but returns wrong results). Silent errors are harder and more common in interviews.

How to Read a PostgreSQL Error

PostgreSQL error messages follow a consistent structure. Knowing where to look saves you from guessing.

ERROR: column "department_name" must appear in the GROUP BY clause or be used in an aggregate function LINE 3: department_name, ^ DETAIL: ... HINT: Add department_name to the GROUP BY clause.

Anatomy of the Error

Part What It Tells You Where to Look
ERROR: The main error type and description Read this first — it's the classification
LINE N: The exact line number where the error was detected Jump to this line in your query
^ (caret) Points to the exact character position The problem is at or just before the caret
DETAIL: Additional context about the cause Not always present; read when available
HINT: PostgreSQL's suggested fix Often exactly right — don't ignore it

The 3-Second Read

When you see an error in an interview, read it in this order:

  1. ERROR line — What category of problem is this? (syntax? type? reference?)
  2. LINE number — Where in the query?
  3. HINT — Does PostgreSQL already know the fix?

Interview Tip

Read the error message out loud to the interviewer. It shows you're systematic, not guessing. Say: "The error says column X must appear in the GROUP BY clause, on line 3 — so I need to either add it to GROUP BY or wrap it in an aggregate."

Syntax Errors

Error messages: syntax error at or near "...", unexpected token

These are the most common errors — a missing comma, misplaced keyword, or unclosed parenthesis.

A1. Missing comma between SELECT columns

+

syntax error at or near "employee_name"

-- BROKEN SELECT employee_id employee_name -- <- missing comma after employee_id FROM Employees;
ERROR: syntax error at or near "employee_name" LINE 3: employee_name ^

Fix: Add the comma. Verify: Query runs and returns expected columns.

SELECT employee_id, employee_name FROM Employees;

A2. Using a reserved keyword as an alias

+

syntax error at or near "order"

-- BROKEN SELECT COUNT(*) AS order, -- <- "order" is a reserved keyword customer_id FROM Orders GROUP BY customer_id;

Fix: Quote the alias or choose a different name.

SELECT COUNT(*) AS "order", -- quoted (works but awkward) COUNT(*) AS order_count -- better: just rename it FROM Orders GROUP BY customer_id;

A3. Misplaced or missing keyword

+

syntax error at or near "INNER"

-- BROKEN: WHERE before JOIN SELECT e.name, d.department_name FROM Employees e WHERE e.salary > 50000 INNER JOIN Departments d ON e.dept_id = d.dept_id;

Why: SQL clause order is FROM → JOIN → WHERE → GROUP BY → HAVING → ORDER BY → LIMIT.

Fix:

SELECT e.name, d.department_name FROM Employees e INNER JOIN Departments d ON e.dept_id = d.dept_id WHERE e.salary > 50000;

A4. Unclosed parenthesis

+

syntax error at or near ";"

-- BROKEN SELECT * FROM Orders WHERE status IN ('active', 'pending'; -- <- missing closing )

Fix: Count your parentheses. The caret points to the `;` because PostgreSQL was still expecting `)`.

SELECT * FROM Orders WHERE status IN ('active', 'pending');

Reference Errors

Error messages: column "X" does not exist, relation "X" does not exist, column reference "X" is ambiguous

B1. Ambiguous column in a JOIN

+

column reference "customer_id" is ambiguous

-- BROKEN SELECT customer_id, name, order_date -- <- customer_id exists in both tables FROM Customers c JOIN Orders o ON c.customer_id = o.customer_id;

Fix: Prefix every column with its table alias.

SELECT c.customer_id, c.name, o.order_date FROM Customers c JOIN Orders o ON c.customer_id = o.customer_id;

B2. Using a SELECT alias in WHERE

+

column "annual_salary" does not exist

-- BROKEN SELECT salary * 12 AS annual_salary FROM Employees WHERE annual_salary > 100000; -- <- alias not available in WHERE

Why: PostgreSQL evaluates WHERE before SELECT, so the alias doesn't exist yet. Repeat the expression or use a CTE.

Option 1: Repeat the expression

SELECT salary * 12 AS annual_salary FROM Employees WHERE salary * 12 > 100000;

Option 2: CTE (cleaner for complex expressions)

WITH emp AS ( SELECT *, salary * 12 AS annual_salary FROM Employees ) SELECT * FROM emp WHERE annual_salary > 100000;

B3. Referencing a column from a table not in FROM

+

missing FROM-clause entry for table "d"

-- BROKEN: forgot to join the Departments table SELECT e.name, d.department_name FROM Employees e WHERE e.salary > 50000;

Fix: Either add the JOIN or remove the reference.

SELECT e.name, d.department_name FROM Employees e INNER JOIN Departments d ON e.dept_id = d.dept_id WHERE e.salary > 50000;

Type Errors

Error messages: operator does not exist: varchar = integer, cannot cast type, invalid input syntax for type

C1. Comparing a string column to an integer

+

operator does not exist: character varying = integer

-- BROKEN: zip_code is VARCHAR but compared to integer SELECT * FROM Customers WHERE zip_code = 90210;

Fix: Match the type — use a string literal.

SELECT * FROM Customers WHERE zip_code = '90210';

C2. Aggregating a non-numeric column

+

function sum(character varying) does not exist

-- BROKEN SELECT SUM(status) FROM Orders; -- status is VARCHAR

Fix: You probably want COUNT not SUM, or you need CASE to convert to numeric first.

-- Count occurrences SELECT COUNT(*) FROM Orders WHERE status = 'active'; -- Or sum a derived numeric value SELECT SUM(CASE WHEN status = 'active' THEN 1 ELSE 0 END) FROM Orders;

C3. Date format mismatch

+

Ambiguous date format causes unpredictable results

-- BROKEN: ambiguous date format SELECT * FROM Orders WHERE order_date = '03/04/2024'; -- Is this March 4 or April 3? Depends on locale settings.

Fix: Always use ISO 8601 format ('YYYY-MM-DD').

SELECT * FROM Orders WHERE order_date = '2024-03-04';

C4. Integer division returning 0 instead of decimal

+

Silent error: 3 / 5 = 0, not 0.6

-- BROKEN (silent error — query runs but result is wrong) SELECT completed_tasks / total_tasks AS completion_rate FROM Projects; -- If both are integers: 3 / 5 = 0, not 0.6

Fix: Cast one operand to a decimal type.

SELECT completed_tasks::DECIMAL / total_tasks AS completion_rate FROM Projects; -- Or: CAST(completed_tasks AS DECIMAL) / total_tasks

C5. ROUND() fails on double precision — PostgreSQL strict typing

+

function round(double precision, integer) does not exist

This is one of the most common surprises in PostgreSQL. The ROUND(value, decimal_places) function only accepts numeric as its first argument — not double precision or real.

-- BROKEN: timestamp is float/double precision on many platforms -- AVG() of double precision returns double precision SELECT machine_id, ROUND(AVG(processing_time), 3) AS processing_time FROM ( SELECT machine_id, process_id, MAX(CASE WHEN activity_type = 'end' THEN timestamp END) - MIN(CASE WHEN activity_type = 'start' THEN timestamp END) AS processing_time FROM Activity GROUP BY machine_id, process_id ) AS t GROUP BY machine_id; -- ERROR: function round(double precision, integer) does not exist -- HINT: No function matches the given name and argument types.

Why this happens: PostgreSQL defines two overloads of ROUND():

SignatureWhat it does
ROUND(numeric)Rounds to nearest integer
ROUND(numeric, integer)Rounds to N decimal places

There is no ROUND(double precision, integer). If your value is double precision (common when subtracting float columns or using AVG() on floats), PostgreSQL cannot find a matching function.

Fix: Cast to numeric before rounding.

-- CORRECT: cast to numeric SELECT machine_id, ROUND(AVG(processing_time)::numeric, 3) AS processing_time FROM ( SELECT machine_id, process_id, MAX(CASE WHEN activity_type = 'end' THEN timestamp END) - MIN(CASE WHEN activity_type = 'start' THEN timestamp END) AS processing_time FROM Activity GROUP BY machine_id, process_id ) AS t GROUP BY machine_id;

Other functions with the same strict typing:

FunctionRequires numericFix
ROUND(val, N)Yes — two-argument formROUND(val::numeric, N)
TRUNC(val, N)Yes — two-argument formTRUNC(val::numeric, N)
MOD(a, b)YesMOD(a::numeric, b::numeric)
a / b (integer)Returns integer, not decimala::numeric / b
MySQL vs PostgreSQL: MySQL's ROUND() accepts any numeric type — you'll never hit this error there. This is purely a PostgreSQL strictness. LeetCode, HackerRank, and DataLemur all use PostgreSQL, so you will encounter this in practice problems.

C6. Subquery missing alias — mandatory in PostgreSQL

+

subquery in FROM must have an alias

Every derived table (subquery used in FROM or JOIN) must have an alias in PostgreSQL. This is also required by the SQL standard, though some databases are more lenient.

-- BROKEN: no alias on subquery SELECT machine_id, ROUND(AVG(processing_time)::numeric, 3) FROM ( SELECT machine_id, process_id, MAX(CASE WHEN activity_type = 'end' THEN timestamp END) - MIN(CASE WHEN activity_type = 'start' THEN timestamp END) AS processing_time FROM Activity GROUP BY machine_id, process_id ) -- <-- missing alias! GROUP BY machine_id; -- ERROR: subquery in FROM must have an alias

Fix: Add AS alias_name after the closing parenthesis.

-- CORRECT: alias added SELECT machine_id, ROUND(AVG(processing_time)::numeric, 3) FROM ( SELECT machine_id, process_id, MAX(CASE WHEN activity_type = 'end' THEN timestamp END) - MIN(CASE WHEN activity_type = 'start' THEN timestamp END) AS processing_time FROM Activity GROUP BY machine_id, process_id ) AS t -- <-- alias required GROUP BY machine_id;

The alias also matters when referencing columns. If your outer query joins multiple subqueries, you must qualify column names with the alias:

-- Joining two subqueries — aliases are essential for disambiguation SELECT a.dept_id, a.total_sales, b.total_returns FROM ( SELECT dept_id, SUM(amount) AS total_sales FROM Sales GROUP BY dept_id ) AS a JOIN ( SELECT dept_id, SUM(amount) AS total_returns FROM Returns GROUP BY dept_id ) AS b ON a.dept_id = b.dept_id;
Rule of thumb: Any time you write a subquery in FROM or JOIN, immediately add AS t (or a descriptive alias) after the closing parenthesis. Make it a habit — PostgreSQL will always require it, and using meaningful aliases like AS sales_summary makes your query more readable.

Aggregation Errors

Error messages: must appear in the GROUP BY clause or be used in an aggregate function, aggregate functions are not allowed in WHERE

These are the most common interview errors — they come up in nearly every GROUP BY problem.

D1. SELECT column not in GROUP BY

+

column "employees.employee_name" must appear in the GROUP BY clause or be used in an aggregate function

-- BROKEN SELECT department_id, employee_name, COUNT(*) FROM Employees GROUP BY department_id; -- <- employee_name is not grouped or aggregated

Fix: Either add it to GROUP BY or wrap it in an aggregate.

-- Option 1: Add to GROUP BY (if you want per-employee counts) SELECT department_id, employee_name, COUNT(*) FROM Employees GROUP BY department_id, employee_name; -- Option 2: Remove it (if you want per-department counts) SELECT department_id, COUNT(*) FROM Employees GROUP BY department_id;

D2. Using aggregate in WHERE instead of HAVING

+

aggregate functions are not allowed in WHERE

-- BROKEN SELECT department_id, COUNT(*) AS emp_count FROM Employees WHERE COUNT(*) > 5 -- <- aggregate not allowed in WHERE GROUP BY department_id;

Why: WHERE filters rows before grouping. HAVING filters groups after aggregation.

Fix:

SELECT department_id, COUNT(*) AS emp_count FROM Employees GROUP BY department_id HAVING COUNT(*) > 5;

D3. ORDER BY a non-selected, non-grouped column

+

column "employees.employee_name" must appear in the GROUP BY clause or be used in an aggregate function

-- BROKEN SELECT department_id, COUNT(*) AS emp_count FROM Employees GROUP BY department_id ORDER BY employee_name; -- <- not in GROUP BY or aggregate

Fix: ORDER BY a column that's in SELECT or wrap it in an aggregate (e.g., ORDER BY MAX(employee_name)).

SELECT department_id, COUNT(*) AS emp_count FROM Employees GROUP BY department_id ORDER BY COUNT(*) DESC;

The WHERE vs. HAVING Rule

WHERE
Filters ROWS
Runs BEFORE GROUP BY
Cannot use aggregates
e.g., salary > 50000
HAVING
Filters GROUPS
Runs AFTER GROUP BY
Can use aggregates
e.g., COUNT(*) > 5
NULL Errors

No error message — the query runs but results are wrong. These are the most dangerous interview errors because you won't see an error; you have to know to check.

E1. COUNT(*) vs COUNT(column)

+

These return DIFFERENT numbers when NULLs exist

-- These return DIFFERENT numbers when NULLs exist SELECT COUNT(*) AS total_rows, -- counts ALL rows (5) COUNT(email) AS rows_with_email -- skips NULLs (3) FROM Customers;
customer_id email
1 a@test.com
2 NULL
3 b@test.com
4 NULL
5 c@test.com

COUNT(*) = 5, COUNT(email) = 3. If you use COUNT(email) when you meant "total customers," your result is silently wrong.

Fix: Use COUNT(*) for total rows. Use COUNT(column) only when you intentionally want to exclude NULLs.

E2. NULL in NOT IN

+

Returns 0 rows if any manager_id is NULL

-- BROKEN: Returns 0 rows if any manager_id is NULL SELECT * FROM Employees WHERE employee_id NOT IN (SELECT manager_id FROM Employees);

Why: If manager_id has even one NULL, NOT IN evaluates to UNKNOWN for every row, returning nothing.

Safe: NOT EXISTS handles NULLs correctly

SELECT * FROM Employees e WHERE NOT EXISTS ( SELECT 1 FROM Employees m WHERE m.manager_id = e.employee_id );

Or: Filter NULLs from the subquery

SELECT * FROM Employees WHERE employee_id NOT IN ( SELECT manager_id FROM Employees WHERE manager_id IS NOT NULL );

E3. NULL in arithmetic — SUM, AVG, and comparisons

+

NULL + 100 = NULL; NULL > 5 = NULL; AVG ignores NULLs

-- NULL + 100 = NULL (not 100) -- NULL > 5 = NULL (not TRUE or FALSE) -- AVG ignores NULLs: AVG(10, NULL, 20) = 15, not 10

Fix: Use COALESCE to set a default.

SELECT COALESCE(bonus, 0) + salary AS total_comp FROM Employees;

E4. NULL in WHERE != comparisons

+

Missing rows where status IS NULL

-- BROKEN: Misses rows where status IS NULL SELECT * FROM Orders WHERE status != 'cancelled';

Rows where status IS NULL are not returned — because NULL != 'cancelled' evaluates to NULL (not TRUE).

Fix: Explicitly include NULLs.

SELECT * FROM Orders WHERE status != 'cancelled' OR status IS NULL; -- Or use IS DISTINCT FROM (PostgreSQL-specific) SELECT * FROM Orders WHERE status IS DISTINCT FROM 'cancelled';

NULL Trap Checklist

Trap Symptom Fix
COUNT(col) vs COUNT(*) Row count lower than expected Use COUNT(*) for total rows
NOT IN with NULLs Zero rows returned Use NOT EXISTS
!= missing NULLs Fewer rows than expected Add OR col IS NULL
Arithmetic with NULL NULL results propagating Wrap in COALESCE(col, 0)
AVG ignoring NULLs Average seems too high/low Decide: treat NULL as 0 or exclude?
JOIN Errors

No error message — the query runs but produces too many or too few rows. The most common cause of wrong aggregations in interviews.

F1. Fan-out — row count inflates after JOIN

+

Expected: 100 customers. Got: 350 rows.

-- Expected: 100 customers. Got: 350 rows. SELECT c.customer_id, c.name, o.order_id FROM Customers c JOIN Orders o ON c.customer_id = o.customer_id;

Why: One customer can have multiple orders. The JOIN duplicates customer rows — one per order.

Diagnosis:

-- Check: how many orders per customer? SELECT customer_id, COUNT(*) FROM Orders GROUP BY customer_id ORDER BY 2 DESC;

Fix: Aggregate first, then join.

WITH order_counts AS ( SELECT customer_id, COUNT(*) AS order_count FROM Orders GROUP BY customer_id ) SELECT c.customer_id, c.name, oc.order_count FROM Customers c JOIN order_counts oc ON c.customer_id = oc.customer_id;

F2. Missing ON clause → Cartesian product

+

Returns customers × orders (every combination)

-- BROKEN: Returns customers × orders (every combination) SELECT c.name, o.order_date FROM Customers c, Orders o; -- <- implicit cross join, missing WHERE

Fix: Use explicit JOIN with ON clause.

SELECT c.name, o.order_date FROM Customers c INNER JOIN Orders o ON c.customer_id = o.customer_id;

F3. INNER JOIN silently drops rows

+

Expected all customers, but 20 are missing

-- Expected all customers, but 20 are missing SELECT c.customer_id, o.order_id FROM Customers c INNER JOIN Orders o ON c.customer_id = o.customer_id;

Why: INNER JOIN drops customers who have no orders. If the question says "all customers" or "including those with no orders," use LEFT JOIN.

Diagnosis:

-- How many customers have no orders? SELECT COUNT(*) FROM Customers c LEFT JOIN Orders o ON c.customer_id = o.customer_id WHERE o.customer_id IS NULL;

Fix: Use LEFT JOIN when you need all rows from the left table.

SELECT c.customer_id, c.name, o.order_id FROM Customers c LEFT JOIN Orders o ON c.customer_id = o.customer_id;

F4. Duplicate join key causing double-counting

+

SUM is 2x expected because the join duplicated rows

-- SUM is 2x expected because the join duplicated rows SELECT d.department_name, SUM(e.salary) FROM Departments d JOIN Employees e ON d.dept_id = e.dept_id JOIN Projects p ON e.employee_id = p.employee_id -- <- 1:many GROUP BY d.department_name;

Why: If an employee is on 3 projects, their salary gets summed 3 times.

Fix: Aggregate in a CTE before the second join, or use SUM(DISTINCT e.salary) if salaries are unique.

WITH emp_projects AS ( SELECT DISTINCT e.employee_id, e.salary, d.dept_id FROM Employees e JOIN Departments d ON e.dept_id = d.dept_id ) SELECT d.department_name, SUM(ep.salary) FROM Departments d JOIN emp_projects ep ON d.dept_id = ep.dept_id GROUP BY d.department_name;

Window Function Errors

Error messages: window functions are not allowed in WHERE, aggregate function calls cannot be nested

G1. Using a window function in WHERE

+

column "rn" does not exist

-- BROKEN SELECT employee_id, salary, ROW_NUMBER() OVER (ORDER BY salary DESC) AS rn FROM Employees WHERE rn <= 5; -- <- window function not available in WHERE

Fix: Window functions are computed after WHERE. Wrap in a CTE or subquery.

WITH ranked AS ( SELECT employee_id, salary, ROW_NUMBER() OVER (ORDER BY salary DESC) AS rn FROM Employees ) SELECT * FROM ranked WHERE rn <= 5;

G2. Nesting an aggregate inside a window function

+

aggregate function calls cannot be nested

-- BROKEN SELECT department_id, SUM(COUNT(*)) OVER (ORDER BY department_id) FROM Employees GROUP BY department_id;

Fix: Compute the aggregate in a CTE first, then apply the window.

WITH dept_counts AS ( SELECT department_id, COUNT(*) AS emp_count FROM Employees GROUP BY department_id ) SELECT department_id, SUM(emp_count) OVER (ORDER BY department_id) AS running_total FROM dept_counts;

G3. Wrong window frame — ROWS vs RANGE (silent error)

+

7-day rolling average averages 7 ROWS instead of 7 DAYS

-- Intended: 7-day rolling average -- Actual: averages over 7 ROWS, not 7 DAYS SELECT visited_on, AVG(amount) OVER (ORDER BY visited_on ROWS BETWEEN 6 PRECEDING AND CURRENT ROW) FROM Customer;

Why: If multiple rows share the same date, ROWS BETWEEN 6 PRECEDING counts 6 prior rows, not 6 prior days.

Fix: Pre-aggregate to one row per date, then use ROWS.

G4. Missing PARTITION BY — window spans entire table

+

Rank across ALL employees instead of per department

-- Intended: rank within each department -- Actual: ranks across ALL employees SELECT employee_id, department_id, RANK() OVER (ORDER BY salary DESC) AS dept_rank FROM Employees;

Fix: Add PARTITION BY.

RANK() OVER (PARTITION BY department_id ORDER BY salary DESC) AS dept_rank
Subquery Errors

Error messages: subquery must return only one column, subquery used as an expression must return at most one row, subquery in FROM must have an alias

H1. Scalar subquery returns multiple rows

+

more than one row returned by a subquery used as an expression

-- BROKEN: subquery returns multiple department_ids SELECT employee_name FROM Employees WHERE department_id = (SELECT department_id FROM Departments WHERE location = 'NYC');

Fix: Use IN instead of = when the subquery returns multiple rows.

WHERE department_id IN (SELECT department_id FROM Departments WHERE location = 'NYC');

H2. Missing alias on derived table

+

subquery in FROM must have an alias

-- BROKEN SELECT * FROM (SELECT customer_id, COUNT(*) FROM Orders GROUP BY customer_id);

Fix: Always alias subqueries in FROM.

SELECT * FROM ( SELECT customer_id, COUNT(*) AS order_count FROM Orders GROUP BY customer_id ) AS order_summary;

H3. Correlated subquery referencing wrong scope

+

Alias e3 doesn't exist inside the inner subquery

-- BROKEN: e3 alias not visible inside the inner subquery SELECT e1.name FROM Employees e1 WHERE e1.salary > ( SELECT AVG(e2.salary) FROM Employees e2 WHERE e2.department_id = e3.department_id -- <- e3 doesn't exist );

Fix: Check that all correlated references point to the correct outer alias.

SELECT e1.name FROM Employees e1 WHERE e1.salary > ( SELECT AVG(e2.salary) FROM Employees e2 WHERE e2.department_id = e1.department_id -- <- reference outer e1 );
Arithmetic Errors

Error message: division by zero

I1. Division by zero in a ratio calculation

+

division by zero

-- BROKEN: total_tasks could be 0 SELECT project_id, completed_tasks / total_tasks AS completion_rate FROM Projects;

Fix: Use NULLIF to convert 0 to NULL (which makes the division return NULL instead of erroring).

SELECT project_id, completed_tasks / NULLIF(total_tasks, 0) AS completion_rate FROM Projects;

I2. Safe division pattern (return 0 instead of NULL)

+

COALESCE + NULLIF safe division pattern

SELECT project_id, COALESCE(completed_tasks::DECIMAL / NULLIF(total_tasks, 0), 0) AS completion_rate FROM Projects;

Pattern breakdown: NULLIF(total_tasks, 0) → returns NULL if zero → division returns NULL → COALESCE(..., 0) → converts NULL to 0.

I3. Integer division returning 0

+

3 / 5 = 0 instead of 0.6

-- PostgreSQL integer division: 3 / 5 = 0 (not 0.6) SELECT ROUND(3::DECIMAL / 5, 2); -- = 0.60

Interview Tip

When computing rates or percentages, always cast to DECIMAL first and use ROUND for clean output.

Execution Order Errors

PostgreSQL executes SQL clauses in a specific order, not the order you write them. This is why some things fail and others work — understanding this order is key to debugging and interview success.

  1. FROM / JOIN — Tables are loaded and joined
  2. WHERE — Row-level filtering (before grouping)
  3. GROUP BY — Rows grouped into buckets
  4. HAVING — Group-level filtering (after grouping)
  5. WINDOW FUNCTIONS — Computed over grouped/filtered result
  6. SELECT — Columns chosen, aliases assigned
  7. DISTINCT — Duplicate rows removed
  8. ORDER BY — Results sorted
  9. LIMIT / OFFSET — Final row trimming

Let's look at why this order matters with specific error examples.

Error: Using a window function in WHERE
-- BROKEN: Tries to filter by ROW_NUMBER() in WHERE SELECT * FROM table WHERE ROW_NUMBER() OVER (PARTITION BY key_col ORDER BY id ASC) = 1;

Error: window functions are not allowed in WHERE

Why: WHERE (step 2) runs BEFORE window functions (step 5). The window hasn't been computed yet.

Fix: Wrap in CTE/subquery:

WITH ranked AS ( SELECT *, ROW_NUMBER() OVER (PARTITION BY key_col ORDER BY id ASC) AS rn FROM table ) SELECT * FROM ranked WHERE rn = 1;
Error: Using a SELECT alias in WHERE
SELECT salary * 12 AS annual_salary FROM Employees WHERE annual_salary > 100000;

Error: column "annual_salary" does not exist

Why: WHERE (step 2) runs before SELECT (step 6), so the alias doesn't exist yet.

Fix: Repeat the expression or use a CTE.

SELECT salary * 12 AS annual_salary FROM Employees WHERE salary * 12 > 100000;
Error: Using aggregate in WHERE
SELECT department_id, COUNT(*) AS emp_count FROM Employees WHERE COUNT(*) > 5 GROUP BY department_id;

Error: aggregate functions are not allowed in WHERE

Why: WHERE (step 2) runs before GROUP BY (step 3). Groups haven't been formed yet.

Fix: Use HAVING (step 4) which runs after GROUP BY.

SELECT department_id, COUNT(*) AS emp_count FROM Employees GROUP BY department_id HAVING COUNT(*) > 5;
Why ORDER BY CAN use aliases (it works!)
SELECT salary * 12 AS annual_salary FROM Employees ORDER BY annual_salary; -- This WORKS!

Why it works: ORDER BY (step 8) runs AFTER SELECT (step 6), so the alias exists.

Error: DISTINCT before ORDER BY surprise
SELECT DISTINCT department_id FROM Employees ORDER BY salary; -- ERROR in standard SQL

Error: ORDER BY items must appear in the select list if DISTINCT is specified

Why: DISTINCT (step 7) removes duplicates before ORDER BY (step 8), but if ORDER BY uses a column not in SELECT, the result would be non-deterministic.

Fix: Either add the column to SELECT or don't use ORDER BY on non-selected columns.

SELECT DISTINCT department_id, salary FROM Employees ORDER BY salary;
The Big Insight: Execution Order Is Why We Need Subqueries & CTEs

Every error above shares the same root cause: you tried to use a result that hasn't been computed yet at that point in execution. The fix is always the same pattern — create an intermediate result first, then use it.

The One Rule

We use subqueries or CTEs whenever SQL needs an intermediate result first before the next clause can reference it. They create a "checkpoint" — a temporary table where earlier steps are already done.

Think of each step in the execution order as a visibility boundary. A clause can only see what the steps before it have produced. When you need something from a later step, you have to wrap the earlier computation in a subquery so it finishes first.

Example: DENSE_RANK() — Why One Query Can't Do It
-- BROKEN: rank is a window function alias — WHERE can't see it SELECT id, name, salary, departmentId, DENSE_RANK() OVER(PARTITION BY departmentId ORDER BY salary DESC) AS rank FROM employee WHERE rank < 3;

Error: column "rank" does not exist

Trace through the execution order to see exactly why:

StepWhat happensIs rank available?
1. FROMLoad the employee tableNo
2. WHEREWHERE rank < 3 — tries to filterNo — ERROR here
3. GROUP BY(not used)No
4. HAVING(not used)No
5. WINDOWDENSE_RANK() computed hereYes — but too late for WHERE
6. SELECTAlias rank assignedYes

WHERE runs at step 2. The window function doesn't run until step 5. That's a 3-step gap. You can't reach forward in time.

The fix — create an intermediate result:

-- Step 1: Compute the rank (subquery finishes all 6 steps internally) -- Step 2: NOW filter it in the outer query's WHERE SELECT * FROM ( SELECT id, name, salary, departmentId, DENSE_RANK() OVER(PARTITION BY departmentId ORDER BY salary DESC) AS rank FROM employee ) t WHERE rank < 3;

The subquery runs its own complete execution cycle (FROM → SELECT), producing a result table where rank already exists as a real column. The outer query's WHERE can now see it because FROM (step 1) loaded that finished result.

CTE version (same logic, easier to read):

WITH ranked AS ( SELECT id, name, salary, departmentId, DENSE_RANK() OVER(PARTITION BY departmentId ORDER BY salary DESC) AS rank FROM employee ) SELECT * FROM ranked WHERE rank < 3;
Where to Place a Subquery — and Why

A subquery can appear in different clauses, and where you put it determines what problem it solves. The placement follows directly from the execution order.

Subquery in FROM — "Compute first, then use"

When: You need to filter, join, or aggregate results that require a prior computation (window functions, aggregates, transforms).

Why here: FROM runs at step 1. By placing a subquery in FROM, its entire execution cycle completes first, producing a derived table. All later clauses (WHERE, GROUP BY, etc.) can see the result.

-- Need: Top 3 earners per department -- Problem: Can't filter DENSE_RANK() in WHERE -- Solution: Compute rank in FROM subquery, filter in outer WHERE SELECT * FROM ( SELECT *, DENSE_RANK() OVER(PARTITION BY dept ORDER BY salary DESC) AS rnk FROM employees ) ranked WHERE rnk <= 3;

Use for: Window function filtering, multi-step aggregations, any time you need to "finish a calculation first"

Subquery in WHERE — "Filter rows using another table's data"

When: You need to filter rows based on values that come from a different query — essentially asking "does this row match something computed elsewhere?"

Why here: WHERE runs at step 2 (row-level filtering). The subquery runs its own complete cycle and returns values that WHERE can compare against.

-- Need: Employees in departments located in NYC -- The department IDs come from a different table/query SELECT name, salary FROM employees WHERE dept_id IN ( SELECT dept_id FROM departments WHERE location = 'NYC' );

Scalar vs. multi-row:

-- Scalar (returns one value) → use = WHERE salary > (SELECT AVG(salary) FROM employees) -- Multi-row (returns many values) → use IN, ANY, EXISTS WHERE dept_id IN (SELECT dept_id FROM departments WHERE ...) -- Correlated (references outer query) → use EXISTS WHERE EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.id)

Use for: Filtering against lookup values, existence checks, comparisons against aggregates

Subquery in SELECT — "Add a computed column from elsewhere"

When: You want to include a value from another table or calculation as an extra column, without joining.

Why here: SELECT runs at step 6. The subquery must return exactly one value (scalar) because it becomes a single cell in each row.

-- Need: Each employee's salary compared to their department average SELECT name, salary, (SELECT AVG(salary) FROM employees e2 WHERE e2.dept_id = e1.dept_id) AS dept_avg FROM employees e1;

Constraint: Must return exactly one row and one column (scalar). If it returns multiple rows, you get: more than one row returned by a subquery used as an expression

Use for: Adding lookup values, computing ratios against totals, correlated calculations

Subquery in HAVING — "Filter groups using another computation"

When: You need to filter grouped results based on a value from another query.

Why here: HAVING runs at step 4 (after GROUP BY). You can't use WHERE for this because WHERE runs before grouping.

-- Need: Departments where headcount is above the company average headcount SELECT dept_id, COUNT(*) AS headcount FROM employees GROUP BY dept_id HAVING COUNT(*) > ( SELECT AVG(dept_count) FROM ( SELECT COUNT(*) AS dept_count FROM employees GROUP BY dept_id ) t );

Use for: Comparing group-level metrics against computed thresholds

The Decision Pattern: When Do I Need a Subquery or CTE?

Ask yourself this question: "Does the clause I'm writing need a result that hasn't been computed yet at this step?"

If you need to... But the problem is... Place subquery in...
Filter by a window function result WHERE runs before WINDOW (step 2 vs 5) FROM — compute the window first
Filter by a SELECT alias WHERE runs before SELECT (step 2 vs 6) FROM — or repeat the expression
Filter rows by values from another table You need a lookup, not a join WHERE — with IN, EXISTS, or =
Filter groups by a computed threshold The threshold comes from another query HAVING — subquery returns the threshold
Add a column from another table A join would cause fan-out SELECT — scalar correlated subquery
Aggregate an already-aggregated result Can't nest aggregates: SUM(COUNT(*)) FROM — aggregate in subquery, then aggregate again
Join against a filtered/transformed dataset You need to prepare data before joining FROM — or CTE for readability
CTE vs. Subquery — When to Use Which

CTEs and FROM-subqueries solve the same problem (create an intermediate result). The difference is readability and reuse.

Subquery CTE (WITH)
Readability Nests inside the query — harder to follow when deep Named, sequential steps — reads top to bottom
Reuse Must duplicate if needed in multiple places Define once, reference multiple times
Best for Simple one-off lookups in WHERE or SELECT Multi-step transformations, window function filtering
Performance Optimizer can usually inline it PostgreSQL 12+ inlines CTEs too (same performance)
-- Same logic, two styles: -- SUBQUERY STYLE (fine for simple cases) SELECT * FROM ( SELECT *, ROW_NUMBER() OVER(ORDER BY salary DESC) AS rn FROM employees ) t WHERE rn = 1; -- CTE STYLE (better for multi-step or reuse) WITH ranked AS ( SELECT *, ROW_NUMBER() OVER(ORDER BY salary DESC) AS rn FROM employees ) SELECT * FROM ranked WHERE rn = 1;

Rule of thumb: If you need more than one intermediate step, or you reference the same intermediate result twice, use a CTE. Otherwise either works.

Multi-Step Example: Why CTEs Chain Naturally

Some problems require multiple intermediate results. Each CTE becomes one step in a pipeline — and the execution order explains why each step is necessary.

-- Problem: Find departments where the top earner makes more than -- twice the company-wide average salary -- Step 1: Get company-wide average (need aggregate first) WITH company_avg AS ( SELECT AVG(salary) AS avg_sal FROM employees ), -- Step 2: Get top earner per department (need window function first) dept_top AS ( SELECT dept_id, salary, ROW_NUMBER() OVER(PARTITION BY dept_id ORDER BY salary DESC) AS rn FROM employees ), -- Step 3: Filter to just the #1 earner (need rn from step 2) top_earners AS ( SELECT dept_id, salary FROM dept_top WHERE rn = 1 ) -- Step 4: Compare against company average (need both prior results) SELECT t.dept_id, t.salary AS top_salary, c.avg_sal FROM top_earners t CROSS JOIN company_avg c WHERE t.salary > 2 * c.avg_sal;

Each CTE exists because the next step needs a result that isn't available yet at that point in execution. You couldn't write this as a single flat query — the execution order won't allow it.

The Mental Model

Think of subqueries and CTEs as "time machines" for SQL execution order. They let you compute something at step 5 or 6, then travel back to step 1 or 2 where the outer query can use it. Every time you hit a wall — "this clause can't see that result yet" — the answer is: wrap it in a subquery or CTE so it finishes first.

Interview Tip

When you get an error about "not available" or "doesn't exist," think through the execution order. Say out loud: "WHERE runs in step 2, but the window function runs in step 5, so that's why it doesn't work. I need to compute the rank first in a CTE, then filter it."

Common Interview Traps

These are errors interviewers plant deliberately to see if you catch them. Each trap includes a collapsible example showing the buggy query, what's wrong, and how to fix it.

1. INNER JOIN When LEFT JOIN Needed

▼

Question says "all customers" but query uses INNER JOIN, silently dropping customers with no orders.

The Setup: "Show all customers and their total orders."

-- Buggy query SELECT c.name, COUNT(o.id) AS total_orders FROM customers c JOIN orders o ON c.id = o.customer_id GROUP BY c.name;

The Problem: JOIN (INNER JOIN) excludes customers with zero orders. "All customers" means we need every customer, even those with no matches.

-- Fixed query SELECT c.name, COUNT(o.id) AS total_orders FROM customers c LEFT JOIN orders o ON c.id = o.customer_id GROUP BY c.name;

What to say: "This should be LEFT JOIN since we need all customers, including those with no orders."

2. COUNT(*) When COUNT(column) Needed

▼

COUNT(*) counts all rows including NULLs, inflating results when you only want non-NULL values.

The Setup: "How many customers have an email address?"

-- Buggy query SELECT COUNT(*) AS customers_with_email FROM customers;

The Problem: COUNT(*) counts every row, including those where email is NULL. You're counting all customers, not just those with emails.

-- Fixed query SELECT COUNT(email) AS customers_with_email FROM customers;

What to say: "COUNT(*) counts all rows. If we want only non-NULL values, we should use COUNT(email)."

3. Missing GROUP BY Column

▼

A column in SELECT isn't in GROUP BY — PostgreSQL will error, but some databases silently return arbitrary values.

The Setup: "Show each department's average salary and the employee name."

-- Buggy query SELECT department, employee_name, AVG(salary) FROM employees GROUP BY department;

The Problem: employee_name is in SELECT but not in GROUP BY. PostgreSQL will throw an error. In MySQL (non-strict), it silently picks an arbitrary name.

-- Fixed: either add to GROUP BY or remove it SELECT department, AVG(salary) AS avg_salary FROM employees GROUP BY department;

What to say: "employee_name isn't in the GROUP BY — this will error. We need to add it or remove it."

4. NOT IN With NULLable Column

▼

If the subquery returns any NULL, NOT IN returns zero rows — a silent and devastating bug.

The Setup: "Find employees who are not managers."

-- Buggy query SELECT name FROM employees WHERE id NOT IN ( SELECT manager_id FROM employees );

The Problem: If any manager_id is NULL, NOT IN evaluates every comparison as UNKNOWN, and the entire WHERE clause returns no rows.

-- Fixed: use NOT EXISTS SELECT e.name FROM employees e WHERE NOT EXISTS ( SELECT 1 FROM employees m WHERE m.manager_id = e.id );

What to say: "If manager_id has NULLs, NOT IN will return nothing. I'd use NOT EXISTS instead."

5. Integer Division

▼

Dividing two integers returns an integer in PostgreSQL — 3/5 gives 0, not 0.6.

The Setup: "Calculate the approval rate (approved / total)."

-- Buggy query SELECT COUNT(CASE WHEN status = 'approved' THEN 1 END) / COUNT(*) AS approval_rate FROM applications;

The Problem: Both COUNTs return integers. In PostgreSQL, integer / integer = integer, so 3/5 = 0.

-- Fixed: cast to decimal SELECT COUNT(CASE WHEN status = 'approved' THEN 1 END)::DECIMAL / COUNT(*) AS approval_rate FROM applications;

What to say: "This is integer division — 3/5 = 0. I need to cast to DECIMAL first."

6. Fan-Out Join

▼

A 1:many JOIN duplicates the "1" side rows, inflating SUM or COUNT results.

The Setup: "Show each customer's total order amount and number of support tickets."

-- Buggy query SELECT c.name, SUM(o.amount) AS total_orders, COUNT(t.id) AS ticket_count FROM customers c JOIN orders o ON c.id = o.customer_id JOIN tickets t ON c.id = t.customer_id GROUP BY c.name;

The Problem: The double JOIN creates a cross product between orders and tickets for each customer. If a customer has 3 orders and 2 tickets, you get 6 rows — inflating both SUM and COUNT.

-- Fixed: aggregate in CTEs first WITH order_totals AS ( SELECT customer_id, SUM(amount) AS total_orders FROM orders GROUP BY customer_id ), ticket_counts AS ( SELECT customer_id, COUNT(*) AS ticket_count FROM tickets GROUP BY customer_id ) SELECT c.name, o.total_orders, t.ticket_count FROM customers c LEFT JOIN order_totals o ON c.id = o.customer_id LEFT JOIN ticket_counts t ON c.id = t.customer_id;

What to say: "This JOIN creates a 1:many relationship. I should aggregate in a CTE first, then join."

7. WHERE Instead of HAVING

▼

Using an aggregate function in WHERE instead of HAVING — WHERE runs before GROUP BY, so aggregates don't exist yet.

The Setup: "Find departments with more than 5 employees."

-- Buggy query SELECT department, COUNT(*) AS emp_count FROM employees WHERE COUNT(*) > 5 GROUP BY department;

The Problem: WHERE executes before GROUP BY in SQL's execution order. Aggregates like COUNT(*) don't exist yet at the WHERE stage.

-- Fixed: use HAVING SELECT department, COUNT(*) AS emp_count FROM employees GROUP BY department HAVING COUNT(*) > 5;

What to say: "Aggregate functions can't go in WHERE — they need to be in HAVING, which runs after GROUP BY."

8. DISTINCT Masking a Bad Join

▼

Adding DISTINCT to "fix" duplicate results — it hides the real problem: a fan-out join that's producing too many rows.

The Setup: "List each customer's name and their product."

-- "Fixed" with DISTINCT — but this masks the real bug SELECT DISTINCT c.name, p.product_name FROM customers c JOIN orders o ON c.id = o.customer_id JOIN order_items oi ON o.id = oi.order_id JOIN products p ON oi.product_id = p.id;

The Problem: The DISTINCT was added because the query returned duplicates. But the duplicates came from a many-to-many join — a customer who ordered the same product twice creates duplicate rows. DISTINCT "fixes" the output but hides the underlying data issue. If you later add SUM(oi.quantity), the duplicates will inflate results.

-- Better: understand why duplicates exist SELECT c.name, p.product_name, SUM(oi.quantity) AS total_qty FROM customers c JOIN orders o ON c.id = o.customer_id JOIN order_items oi ON o.id = oi.order_id JOIN products p ON oi.product_id = p.id GROUP BY c.name, p.product_name;

What to say: "The DISTINCT is suspicious — it might be masking a fan-out. Let me check the join keys."

9. Missing NULL Check in != Comparison

▼

WHERE status != 'cancelled' silently excludes rows where status is NULL — three-valued logic strikes again.

The Setup: "Find all orders that weren't cancelled."

-- Buggy query SELECT * FROM orders WHERE status != 'cancelled';

The Problem: In SQL's three-valued logic, NULL != 'cancelled' evaluates to UNKNOWN (not TRUE), so rows with NULL status are excluded. This is a silent error — the query runs fine but misses rows.

-- Fixed: handle NULLs explicitly SELECT * FROM orders WHERE status != 'cancelled' OR status IS NULL;

Alternative using COALESCE:

SELECT * FROM orders WHERE COALESCE(status, 'unknown') != 'cancelled';

What to say: "This won't include rows where status is NULL. I'd add OR status IS NULL."

Final Tip

In a debugging interview, the process matters as much as the answer. Read the error, classify it, fix the root cause, and verify. Show that you're methodical, not just lucky.

Row-Level vs Group-Level Operations

One of the most common SQL misunderstandings — especially in interviews — is confusing row-level operations with group-level operations. This distinction is fundamental to how SQL processes data and explains why certain queries return NULL or errors when you expect a result.

The Core Rule

SQL evaluates expressions one row at a time unless you explicitly tell it to combine rows with an aggregate function (SUM, MAX, MIN, AVG, COUNT) or a window function. A CASE expression, arithmetic, string functions, and comparison operators are all row-level — they see only the current row, never other rows in the group.

The Problem: CASE Cannot Look Across Rows

Imagine you have a factory process table where each process has a start row and an end row. You want the completion time (end - start) per process. A natural first attempt is:

-- BROKEN: CASE sees one row at a time, not both rows SELECT machine_id, process_id, (CASE WHEN activity_type = 'end' THEN timestamp END - CASE WHEN activity_type = 'start' THEN timestamp END) AS completion_time FROM Activity GROUP BY machine_id, process_id;

This returns NULL for every row. Here's exactly why.

SQL processes the CASE expression on each row before grouping collapses anything. On the start row, the first CASE evaluates to NULL (because activity_type is not 'end'), and the subtraction becomes NULL - 0.712 = NULL. On the end row, the second CASE evaluates to NULL, giving 1.520 - NULL = NULL. Neither row can see the other row's timestamp.

Row-by-Row Trace (machine_id=0, process_id=0)

Row activity_type CASE 'end' CASE 'start' Subtraction Result
1 start NULL 0.712 NULL - 0.712 NULL
2 end 1.520 NULL 1.520 - NULL NULL

Each CASE hits NULL on one side because it can only see the current row's activity_type — not the other row in the group. And anything minus NULL is NULL.

The Fix: Aggregate Functions Bridge Rows

The solution is to wrap each CASE inside an aggregate function. The aggregate collapses all rows in the group into one value, which is what lets you grab the end timestamp and the start timestamp from different rows and subtract them:

-- CORRECT: MAX/MIN collapse the group into one value per side SELECT machine_id, process_id, MAX(CASE WHEN activity_type = 'end' THEN timestamp END) - MAX(CASE WHEN activity_type = 'start' THEN timestamp END) AS completion_time FROM Activity GROUP BY machine_id, process_id;

How MAX Bridges the Rows (machine_id=0, process_id=0)

Step What Happens Values Seen Result
1 CASE 'end' on row 1 (start) NULL —
2 CASE 'end' on row 2 (end) 1.520 —
3 MAX collapses group MAX(NULL, 1.520) 1.520
4 CASE 'start' produces MAX(0.712, NULL) 0.712
5 Subtraction 1.520 - 0.712 0.808

MAX ignores NULLs, so it picks the one non-NULL value from each group. This is the standard "conditional aggregation" pattern — CASE filters within the row, the aggregate combines across rows.

Note that MAX and MIN give the same result here because each (machine_id, process_id) has exactly one start and one end. In cases with duplicates, you'd choose the aggregate that matches the business logic.

The Complete Classification: Which SQL Operations Are Row-Level vs Group-Level?

This isn't unique to CASE. The same row-level vs group-level distinction applies to every SQL expression:

Row-Level (sees ONE row at a time)

CASE WHEN Conditional logic per row
Arithmetic (+, -, *, /) Computes on current row's columns
COALESCE / NULLIF NULL handling per row
String functions UPPER(), CONCAT(), SUBSTRING() etc.
Date functions DATE_TRUNC(), EXTRACT(), AGE()
CAST / type conversion Converts the current row's value
Comparison operators =, !=, >, <, LIKE, IN, BETWEEN

Group-Level (sees ALL rows in the group)

COUNT() Counts rows in group
SUM() Adds values across group
AVG() Averages values across group
MAX() / MIN() Picks extreme value from group
STRING_AGG() Concatenates values from group
ARRAY_AGG() Collects values into array
BOOL_AND() / BOOL_OR() Boolean aggregates

Window Functions: Row-Level Output, Group-Level Awareness

Window functions are a special third category. They can see across rows (like aggregates) but they don't collapse the group — they return one value per row. This makes them row-level in output but group-level in awareness.

LAG() / LEAD() See previous/next row without collapsing
ROW_NUMBER() / RANK() Assign position relative to other rows
SUM() OVER (...) Running total without collapsing rows
FIRST_VALUE() / NTH_VALUE() Grab a specific row's value from the window
More Examples of the Same Mistake

The CASE problem above isn't unique. The same row-level misunderstanding appears in several common patterns:

Example 2: Arithmetic across rows fails without aggregation

-- BROKEN: trying to subtract this month from last month in the same row SELECT month, revenue - /* there's no "previous row's revenue" accessible here */ FROM monthly_sales;

Arithmetic is row-level. To reference another row's value, you need either a self-join or a window function:

-- CORRECT: LAG() is a window function that reaches the previous row SELECT month, revenue, revenue - LAG(revenue) OVER (ORDER BY month) AS mom_change FROM monthly_sales;

Example 3: String concatenation across rows needs an aggregate

-- BROKEN: CONCAT is row-level — it can't combine values from multiple rows SELECT department_id, CONCAT(employee_name, ', ') AS team FROM Employees GROUP BY department_id;

Error: column "employee_name" must appear in the GROUP BY clause or be used in an aggregate function

CONCAT works on a single row's values. To combine names from multiple rows in a group, you need the group-level STRING_AGG:

-- CORRECT: STRING_AGG is an aggregate that combines values across the group SELECT department_id, STRING_AGG(employee_name, ', ' ORDER BY employee_name) AS team FROM Employees GROUP BY department_id;

Example 4: COALESCE can't fix a cross-row problem

-- BROKEN: COALESCE is row-level — it picks the first non-NULL in THIS row SELECT user_id, COALESCE( CASE WHEN event = 'login' THEN timestamp END, CASE WHEN event = 'logout' THEN timestamp END ) AS event_time FROM user_events;

COALESCE picks the first non-NULL value, but both CASE expressions are still evaluated on the same row. If the row is a 'login', the second CASE is NULL — COALESCE just returns the login timestamp. It doesn't reach across to a different row. The underlying data still needs an aggregate or window function to bridge rows.

The Mental Model

Think of SQL processing in three layers:

Layer What It Does Can See Examples
Row-Level Transforms one row at a time Only columns in the current row CASE, +, UPPER(), COALESCE()
Group-Level Collapses many rows into one All rows in the GROUP BY bucket SUM(), MAX(), COUNT(), STRING_AGG()
Window-Level Looks across rows without collapsing Rows in the OVER() partition/frame LAG(), RANK(), SUM() OVER()

Whenever you need to combine values from different rows, ask yourself: do I need to collapse the group (use an aggregate) or keep all rows (use a window function)? If you're using only row-level operations (CASE, arithmetic, string functions), you're limited to what's on the current row.

Interview Quick Check

If your query is subtracting, comparing, or combining values that live on different rows, and you haven't used an aggregate or window function, your result will either be NULL or an error. The pattern to remember: CASE filters within rows; aggregates bridge across rows.
