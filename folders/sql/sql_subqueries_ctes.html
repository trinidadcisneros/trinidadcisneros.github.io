SQL Subqueries & CTEs: When and Where to Use Them

Understanding intermediate results — from execution order to subquery placement to CTE pipelines

6 topics · PostgreSQL · Intermediate

Every time SQL can't do something in one query, it's because of execution order. A clause needs a result from a later step. The fix is always the same: create an intermediate result first with a subquery or CTE, then use it. This guide explains why they exist, where to use them, and when to choose CTEs instead.
SQL Execution Order — The Foundation

PostgreSQL executes SQL clauses in a fixed order, not the order you write them. This is the root cause of every subquery you'll ever write.

  1. FROM / JOIN — Tables are loaded and joined
  2. WHERE — Row-level filtering (before grouping)
  3. GROUP BY — Rows grouped into buckets
  4. HAVING — Group-level filtering (after grouping)
  5. WINDOW FUNCTIONS — Computed over grouped/filtered result
  6. SELECT — Columns chosen, aliases assigned
  7. DISTINCT — Duplicate rows removed
  8. ORDER BY — Results sorted
  9. LIMIT / OFFSET — Final row trimming
The Visibility Boundary Concept

Each step in the execution order only sees what the previous steps have produced. Once a step finishes, later steps can use its result. But earlier steps can't reach forward in time.

Think of it as a pipeline: each stage passes its output to the next stage. If a later stage needs something the earlier stage can't provide, you hit an error.

The DENSE_RANK() Example: A 3-Step Gap

This query fails:

-- BROKEN: Tries to filter by DENSE_RANK() in WHERE SELECT id, name, salary, departmentId, DENSE_RANK() OVER(PARTITION BY departmentId ORDER BY salary DESC) AS rank FROM employee WHERE rank < 3;

Error: column "rank" does not exist

Here's why, step-by-step:

Step What Happens Is rank Available?
1. FROM Load the employee table No
2. WHERE WHERE rank < 3 — tries to filter No — ERROR here
3-4. GROUP BY / HAVING (not used) No
5. WINDOW DENSE_RANK() computed here Yes — but too late for WHERE
6. SELECT Alias rank assigned Yes

WHERE runs at step 2. The window function doesn't run until step 5. That's a 3-step gap. You can't reference something that hasn't been computed yet.

The Fix: Create an Intermediate Result

Wrap the computation in a subquery so it finishes first:

-- Step 1: Compute rank in subquery (FROM runs step 1, completes all 6 steps internally) -- Step 2: NOW filter it in the outer WHERE SELECT * FROM ( SELECT id, name, salary, departmentId, DENSE_RANK() OVER(PARTITION BY departmentId ORDER BY salary DESC) AS rank FROM employee ) t WHERE rank < 3;

The subquery runs its own complete execution cycle, producing a table where rank already exists as a real column. The outer query's WHERE (step 1) loads that finished result, so it can see rank.

CTE version (same logic, more readable):

WITH ranked AS ( SELECT id, name, salary, departmentId, DENSE_RANK() OVER(PARTITION BY departmentId ORDER BY salary DESC) AS rank FROM employee ) SELECT * FROM ranked WHERE rank < 3;

The One Rule

We use subqueries or CTEs whenever SQL needs an intermediate result first before the next clause can reference it. They create a "checkpoint" where earlier steps are already done.

Where to Place a Subquery — and Why

The placement of your subquery directly follows the execution order:

Subquery in FROM — "Compute first, then use"

▼

When: You need to filter, join, or aggregate results that require a prior computation (window functions, aggregates, transforms).

Why here: FROM runs at step 1. By placing a subquery in FROM, its entire execution cycle completes first, producing a derived table. All later clauses (WHERE, GROUP BY, etc.) can see the result.

-- Need: Top 3 earners per department -- Problem: Can't filter DENSE_RANK() in WHERE -- Solution: Compute rank in FROM subquery, filter in outer WHERE SELECT * FROM ( SELECT *, DENSE_RANK() OVER(PARTITION BY dept ORDER BY salary DESC) AS rnk FROM employees ) ranked WHERE rnk <= 3;

Use for: Window function filtering, multi-step aggregations, reshaping data

Subquery in WHERE — "Filter rows using another query"

▼

When: You need to filter rows based on values from a different query — "does this row match something computed elsewhere?"

Why here: WHERE runs at step 2. The subquery runs its own complete cycle and returns values that WHERE can compare against.

-- Scalar (one value) — use = SELECT name, salary FROM employees WHERE salary > (SELECT AVG(salary) FROM employees) -- Multi-row (many values) — use IN WHERE dept_id IN (SELECT dept_id FROM departments WHERE location = 'NYC') -- Existence check — use EXISTS WHERE EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.id)

Use for: Filtering against lookup values, existence checks, comparisons against aggregates

Subquery in SELECT — "Add a computed column"

▼

When: You want to include a value from another table or calculation as an extra column, without joining.

Why here: SELECT runs at step 6. The subquery must return exactly one value (scalar) because it becomes a single cell in each row.

-- Each employee's salary compared to their department average SELECT name, salary, (SELECT AVG(salary) FROM employees e2 WHERE e2.dept_id = e1.dept_id) AS dept_avg FROM employees e1;

Constraint: Must return exactly one row and one column (scalar). Multiple rows = error.

Use for: Adding lookup values, computing ratios against totals, correlated calculations

Scalar Subqueries with =

Compare a single value to another computed value:

-- Find teams that scored above average SELECT home_team_api_id FROM Match WHERE home_team_goal > (SELECT AVG(home_team_goal) FROM Match);

The subquery (SELECT AVG(...)) returns a single number. The outer WHERE compares each row's home_team_goal against it.

Multi-Row Subqueries with IN

Filter rows where a column matches any value in a list returned by a subquery:

-- Teams in the British league (country_id = 1729) SELECT team_long_name, team_short_name AS abbr FROM Team WHERE team_api_id IN ( SELECT home_team_api_id FROM Match WHERE country_id = 1729 );

The subquery returns many team IDs. IN checks if each Team.team_api_id is in that list.

Filtering Based on Calculations

Combine a subquery with math:

-- Teams that scored 2x the average in 2013/2014 SELECT home_team_api_id FROM Match WHERE season = '2013/2014' AND home_team_goal >= 2 * (SELECT AVG(home_team_goal) FROM Match);

The subquery computes the average, then the outer query multiplies it by 2 and compares.

Correlated Subqueries

A correlated subquery references columns from the outer query:

-- Find employees earning above their department's average SELECT e1.name, e1.salary, e1.dept_id FROM employees e1 WHERE e1.salary > ( SELECT AVG(e2.salary) FROM employees e2 WHERE e2.dept_id = e1.dept_id -- References outer query );

The inner query executes once per outer row, comparing each employee to their department's average.

EXISTS for Existence Checks

Check if a row exists in another table without returning the actual data:

-- Customers who placed at least one order SELECT c.customer_id, c.name FROM customers c WHERE EXISTS ( SELECT 1 FROM orders o WHERE o.customer_id = c.customer_id );

EXISTS returns TRUE/FALSE. It's more efficient than IN when you just need to check existence.

ALL and ANY Operators

Compare a value against all or any results from a subquery:

-- Salary greater than ALL department managers' salaries SELECT name, salary FROM employees WHERE salary > ALL ( SELECT salary FROM employees WHERE role = 'manager' ) -- Salary equal to ANY department's average WHERE salary = ANY ( SELECT AVG(salary) FROM employees GROUP BY dept_id )
NOT IN Pitfall with NULL

Gotcha: NOT IN fails silently if the subquery contains NULL:

-- BROKEN if dept_id list contains NULL SELECT name FROM employees WHERE dept_id NOT IN (SELECT dept_id FROM departments WHERE active = true); -- FIXED: Use NOT EXISTS or exclude NULLs WHERE NOT EXISTS ( SELECT 1 FROM departments d WHERE d.dept_id = e.dept_id AND d.active = false )

Why? In SQL, NULL compared to anything (even != ) returns unknown, not TRUE. NOT IN with NULL always returns no rows.

Scalar Subqueries as Computed Columns

Add a column that comes from another query:

-- Compare each league's average to overall average SELECT l.name AS league, ROUND(AVG(m.home_team_goal + m.away_team_goal), 2) AS avg_goals, (SELECT ROUND(AVG(home_team_goal + away_team_goal), 2) FROM Match WHERE season = '2012/2013') AS overall_avg FROM League l LEFT JOIN Match m ON l.country_id = m.country_id WHERE season = '2012/2013' GROUP BY league ORDER BY avg_goals DESC LIMIT 5;
league avg_goals overall_avg
Netherlands Eredivisie 3.15 2.77
Belgium Jupiler League 2.93 2.77
Germany 1. Bundesliga 2.93 2.77

The subquery runs once and returns the same value for every row — the overall average. It's placed in SELECT (step 6) so it can use the same filtered dataset as the main query.

Comparing Individual to Aggregate

Calculate the difference between each row's value and a computed aggregate:

-- How much each league's average differs from the overall SELECT l.name AS league, ROUND(AVG(m.home_team_goal + m.away_team_goal), 2) AS avg_goals, ROUND(AVG(m.home_team_goal + m.away_team_goal) - (SELECT AVG(home_team_goal + away_team_goal) FROM Match WHERE season = '2012/2013'), 2) AS diff FROM League l LEFT JOIN Match m ON l.country_id = m.country_id WHERE season = '2012/2013' GROUP BY league;
league avg_goals diff
Netherlands Eredivisie 3.15 0.38
Belgium Jupiler League 2.93 0.16
France Ligue 1 2.54 -0.23
Percentage-of-Total Pattern

Calculate what percentage each group represents of a fixed total:

-- What % of total users registered for each contest? SELECT r.contest_id, ROUND( (COUNT(DISTINCT r.user_id)::numeric / (SELECT COUNT(DISTINCT user_id) FROM Users) ) * 100, 2 ) AS percentage FROM Register r GROUP BY r.contest_id ORDER BY percentage DESC;
contest_id percentage
208 100.00
209 100.00
215 66.67
207 33.33

Key insight: The denominator (total user count) comes from a different table. The subquery in SELECT provides the fixed divisor. The ::numeric cast prevents integer division from truncating to 0.

Important Constraints

A SELECT subquery must return exactly one row and one column. If it returns:

  • Multiple rows: Error "more than one row returned by a subquery used as an expression"
  • Multiple columns: Syntax error
  • Zero rows (NULL): That cell becomes NULL (usually acceptable)

Always use aggregates (AVG, MAX, COUNT, etc.) or LIMIT 1 to ensure exactly one value is returned.

Derived Tables / Inline Views

A FROM subquery (also called a derived table or inline view) lets you treat a query result as a table:

-- Top 3 teams by home goals average in 2011/2012 SELECT team, home_avg FROM ( SELECT t.team_long_name AS team, AVG(m.home_team_goal) AS home_avg FROM Match m LEFT JOIN Team t ON m.home_team_api_id = t.team_api_id WHERE season = '2011/2012' GROUP BY team ) AS subquery ORDER BY home_avg DESC LIMIT 3;
team home_avg
FC Barcelona 3.842105
Real Madrid CF 3.684211
PSV 3.352941

Important: The subquery must have an alias (AS subquery). It's required syntax.

Why FROM Subqueries Are Needed

Three common scenarios:

Pre-aggregate and reshape data

▼

You need to aggregate first (e.g., average per team), then filter or sort the aggregated results:

SELECT team, avg_goals FROM ( SELECT t.team_long_name AS team, AVG(m.home_team_goal) AS avg_goals FROM Match m LEFT JOIN Team t ON m.home_team_api_id = t.team_api_id GROUP BY team ) derived WHERE avg_goals > 2.5 ORDER BY avg_goals DESC;

If you tried this without a FROM subquery, WHERE would fail (aggregates can't be in WHERE). GROUP BY creates the aggregates, but WHERE runs before GROUP BY.

Filter by window functions

▼

Compute a window function, then filter by it:

SELECT * FROM ( SELECT id, name, salary, ROW_NUMBER() OVER (ORDER BY salary DESC) AS rank FROM employees ) ranked WHERE rank <= 10;

Window functions (step 5) run after WHERE (step 2), so they can't be filtered directly in WHERE. Wrap in a FROM subquery to compute them first.

Complex multi-step calculations

▼

Build a result incrementally by nesting subqueries:

SELECT * FROM ( SELECT country, date, home_team_goal, away_team_goal, (home_team_goal + away_team_goal) AS total_goals FROM Match m LEFT JOIN Country c ON m.country_id = c.id ) match_totals WHERE total_goals >= 10;

The inner subquery adds the total_goals column. The outer query filters by it. This step-by-step approach is clearer than nesting everything in one WHERE clause.

Joining Subqueries

Treat a subquery result as a table and join it to other tables:

-- Which countries had matches with 10+ goals? SELECT c.name AS country_name, COUNT(subquery.id) AS matches FROM Country c INNER JOIN ( SELECT country_id, id FROM Match WHERE (home_team_goal + away_team_goal) >= 10 ) AS subquery ON c.id = subquery.country_id GROUP BY country_name ORDER BY matches DESC;
country_name matches
Spain 5
England 4
Netherlands 2

The FROM subquery filters matches with 10+ goals. The outer query joins this filtered set to the Country table, counting matches per country.

Multiple FROM Subqueries

Join multiple subqueries together:

SELECT a.id, a.name, b.score, c.rank FROM (SELECT id, name FROM users) a JOIN (SELECT user_id, score FROM scores) b ON a.id = b.user_id JOIN (SELECT user_id, rank FROM rankings) c ON a.id = c.user_id;

Each subquery is aliased (a, b, c) and treated as a full table in the joins.

Using Subqueries Across Multiple Clauses

The most powerful queries use subqueries in FROM, WHERE, and SELECT together:

-- Average goals by stage in 2015/2016, showing which stages exceed overall average SELECT subquery.stage, ROUND(subquery.avg_goals, 2) AS avg_goal, (SELECT AVG(home_team_goal + away_team_goal) FROM Match WHERE season = '2015/2016' ) AS overall_avg FROM ( SELECT stage, AVG(home_team_goal + away_team_goal) AS avg_goals FROM Match WHERE season = '2015/2016' GROUP BY stage ) AS subquery WHERE subquery.avg_goals > ( SELECT AVG(home_team_goal + away_team_goal) FROM Match WHERE season = '2015/2016' );
stage avg_goal overall_avg
7 2.81 2.75466
8 3.05 2.75466
13 3.02 2.75466
17 3.00 2.75466
38 3.52 2.75466

Breaking this down:

  • FROM subquery: Aggregates goals by stage for the 2015/2016 season
  • WHERE subquery: Filters stages where avg_goals > overall average (same subquery repeats)
  • SELECT subquery: Adds the overall average as a reference column
Complex Analysis Pattern

Find employees earning above their department's average, and show how much above:

SELECT e.name, e.salary, dept_summary.dept_avg, (e.salary - dept_summary.dept_avg) AS above_avg FROM employees e JOIN ( SELECT dept_id, AVG(salary) AS dept_avg FROM employees GROUP BY dept_id ) dept_summary ON e.dept_id = dept_summary.dept_id WHERE e.salary > dept_summary.dept_avg ORDER BY above_avg DESC;

The FROM subquery creates a table of department averages. The outer query joins it back to employees, filters for above-average earners, and calculates the difference.

When to Use Multiple Subqueries vs CTEs

Multiple subqueries work, but they can become unreadable when you nest more than 2-3 levels deep. At that point, switch to CTEs.

Multiple subqueries (3 levels deep)

▼
SELECT * FROM ( SELECT * FROM ( SELECT * FROM ( SELECT id, name FROM employees WHERE salary > 100000 ) t1 WHERE name LIKE 'A%' ) t2 WHERE id < 500 ) t3;

Hard to read. Lots of nested parentheses. Hard to debug.

Same logic with CTEs (much clearer)

▼
WITH high_earners AS ( SELECT id, name FROM employees WHERE salary > 100000 ), names_with_a AS ( SELECT * FROM high_earners WHERE name LIKE 'A%' ), final_filter AS ( SELECT * FROM names_with_a WHERE id < 500 ) SELECT * FROM final_filter;

Each step is named and readable. Easy to see the pipeline. Much easier to debug.

What Is a CTE?

CTE stands for Common Table Expression. It's a temporary named result set that you can reference in the main query, like a subquery but much more readable.

Basic syntax:

WITH cte_name AS ( SELECT ... FROM ... ) SELECT * FROM cte_name;
CTE vs Subquery Comparison
Aspect Subquery CTE
Readability Hard (nested, lots of parens) Easy (named, top-down)
Reusability Single use in one place Reference multiple times
Debugging Hard to isolate steps Easy to test each CTE alone
Performance Same Same (or better with CTE materialization hints)
Multiple levels Quickly becomes unreadable Clean even with many steps
Basic CTE Example
-- Find top 3 earners per department WITH dept_avg AS ( SELECT dept_id, AVG(salary) AS avg_salary FROM employees GROUP BY dept_id ) SELECT e.name, e.salary, e.dept_id, d.avg_salary FROM employees e JOIN dept_avg d ON e.dept_id = d.dept_id WHERE e.salary > d.avg_salary ORDER BY e.salary DESC;

What's happening:

  1. WITH dept_avg AS (...) — Define a temporary table called dept_avg that contains department averages
  2. The main SELECT runs and can reference dept_avg just like a real table
  3. dept_avg only exists for the duration of this query
Multi-Step CTE Pipelines

Chain multiple CTEs together, each building on the previous one:

WITH company_avg AS ( SELECT AVG(salary) AS overall_avg FROM employees ), dept_top AS ( SELECT dept_id, ROW_NUMBER() OVER (PARTITION BY dept_id ORDER BY salary DESC) AS rank, name, salary FROM employees ), top_earners AS ( SELECT d.dept_id, d.name, d.salary, c.overall_avg, (d.salary - c.overall_avg) AS above_company_avg FROM dept_top d CROSS JOIN company_avg c WHERE rank = 1 ) SELECT * FROM top_earners ORDER BY above_company_avg DESC;

Pipeline:

  1. company_avg: Calculate overall company salary average
  2. dept_top: Rank employees within each department
  3. top_earners: Join the two above to find top earner per dept + company average
  4. Final SELECT: Return the results

Each CTE can reference all previous CTEs. The final SELECT can reference any of them.

When to Use CTE vs Subquery
Use CTE if: Use Subquery if:
Need multiple steps (2+) Single step needed
Using the same intermediate result twice+ Using result only once
Nesting 3+ levels deep Simple nesting (1-2 levels)
Want code to be easy to read/debug Performance is absolutely critical
Collaborating (CTEs are self-documenting) Ad-hoc, throwaway query
Recursive CTEs (Brief Intro)

A recursive CTE references itself, useful for hierarchical data:

-- Find all reports under a manager (employee hierarchy) WITH RECURSIVE org_chart AS ( -- Base case: start with the CEO SELECT id, name, manager_id, 1 AS level FROM employees WHERE manager_id IS NULL UNION ALL -- Recursive case: find direct reports SELECT e.id, e.name, e.manager_id, oc.level + 1 FROM employees e INNER JOIN org_chart oc ON e.manager_id = oc.id WHERE oc.level < 10 -- Prevent infinite loops ) SELECT * FROM org_chart ORDER BY level, name;

Structure:

  1. Base case (SELECT before UNION ALL): Starting point (CEO with no manager)
  2. Recursive case (SELECT after UNION ALL): Join employees to org_chart itself to find one level down
  3. Termination: Keep recursing until WHERE condition fails or max recursion depth hit

Recursive CTEs are advanced — use them for trees/hierarchies, not for most regular queries.

Naming CTEs Clearly

Good CTE names document the pipeline:

-- GOOD: Each step's purpose is clear WITH monthly_sales AS ( SELECT DATE_TRUNC('month', order_date) AS month, SUM(amount) AS total FROM orders GROUP BY month ), sales_with_growth AS ( SELECT month, total, LAG(total) OVER (ORDER BY month) AS prev_month, (total - LAG(total) OVER (ORDER BY month)) / LAG(total) OVER (ORDER BY month) AS growth_rate FROM monthly_sales ), high_growth_months AS ( SELECT * FROM sales_with_growth WHERE growth_rate > 0.1 ) SELECT * FROM high_growth_months;

vs.

-- BAD: No idea what t1, t2, t3 do WITH t1 AS (...), t2 AS (...), t3 AS (...) SELECT * FROM t3;

Best Practice

Use descriptive CTE names (monthly_sales, not t1). Each name should describe what data the CTE produces. This makes complex queries self-documenting and much easier to maintain.

CTE vs. Subquery — The Complete Comparison

CTEs and subqueries both let you build intermediate results inside a query. But they behave differently in terms of readability, performance, reuse, and when you should reach for each one. This table breaks it all down.

What Are They?

  CTE (Common Table Expression) Subquery
Definition A named temporary result set defined at the top of a query using WITH ... AS. Think of it as giving a name to a query so you can refer to it later — like saving a recipe step before moving on to the next. A query nested inside another query, placed directly where you need the result — in the WHERE, FROM, SELECT, or HAVING clause. Think of it as asking a quick side-question in the middle of your main question.
Syntax
WITH active_users AS ( SELECT * FROM users WHERE status = 'active' ) SELECT * FROM active_users;
SELECT * FROM ( SELECT * FROM users WHERE status = 'active' ) AS active_users;
Analogy Like prep work in cooking — you dice all your vegetables first, label the bowls, then assemble the dish step by step. Like doing math in your head — you solve the inner part on the fly while working through the bigger problem.

Head-to-Head Comparison

Dimension CTE Subquery
Readability Excellent. Each step is named and separated. You read top-to-bottom like a story: "First get active users, then count their orders, then rank them." Gets messy fast. Nested subqueries force you to read inside-out. At 2+ levels deep, it becomes hard to follow.
Reusability A CTE can be referenced multiple times in the same query. Define it once, use it wherever you need it. Must be copy-pasted if you need the same result in multiple places — duplicating logic and increasing error risk.
Performance In PostgreSQL, the optimizer usually inlines CTEs (treats them like subqueries) since v12. In older versions or with MATERIALIZED, the CTE result is computed once and stored in memory — helpful if the intermediate result is expensive and reused. The optimizer can "see inside" subqueries and merge them with the outer query for better execution plans. In some databases, this gives subqueries a slight edge for simple, one-time-use cases.
Debugging Easy. You can run each CTE independently to check its output — just copy the CTE definition and run it as a standalone SELECT. Harder. To test an inner subquery, you have to extract it manually, which gets tedious with deep nesting.
Recursion Supports WITH RECURSIVE for trees, hierarchies, and graph traversal. This is a unique CTE capability. Cannot recurse. If you need hierarchical queries, you must use a CTE (or application-level loops).
Scope Visible to the entire main query (and to CTEs defined after it in the same WITH block). Only visible to the exact clause it's placed in. A subquery in WHERE can't be referenced in SELECT.
Maintainability Changes are easy — update the CTE definition in one place and every reference picks up the change. If the same subquery appears in multiple places, you must update each copy individually.

When to Use Each — Use Case Guide

Use Case Best Choice Why
Simple filter: "employees earning above average" Subquery One line in WHERE — a CTE would be overkill. WHERE salary > (SELECT AVG(salary) FROM employees) is clear and concise.
Multi-step pipeline: "monthly revenue → growth rate → flag high-growth months" CTE Each step builds on the previous one. CTEs make this a readable 3-step recipe instead of 3 levels of nesting.
Reuse the same result: "compare each department to company average" CTE The company average is needed in both SELECT and HAVING. With a CTE, compute it once; with subqueries, you'd duplicate the logic.
Existence check: "customers who placed an order this year" Subquery WHERE EXISTS (SELECT 1 FROM orders WHERE ...) is the standard pattern — compact and efficient.
Derived table: "join against an aggregated result" Either If it's a single join, a FROM subquery works fine. If you join it multiple times or the query is already complex, use a CTE.
Recursive/hierarchical data: "org chart, category trees" CTE Only CTEs support WITH RECURSIVE. Subqueries simply cannot do this.
Quick ad-hoc exploration in a terminal Subquery When you're just poking around data interactively, inline subqueries are faster to type and you don't need maintainability.
Production query that a team maintains CTE Named steps serve as built-in documentation. A new team member can read monthly_sales and immediately know what that part does.
Performance-critical query on a large dataset Test both Use EXPLAIN ANALYZE to compare. In PostgreSQL 12+, CTEs and subqueries usually have identical plans. In older versions or other databases, subqueries may optimize better.

When NOT to Use Each

Don't Use a CTE When... Don't Use a Subquery When...
The subquery is a one-liner used once — wrapping SELECT AVG(salary) FROM employees in a CTE adds unnecessary ceremony. You need the same intermediate result in more than one place — copy-pasting the same subquery is a maintenance trap.
You're writing a quick throwaway query in a terminal — the overhead of naming steps isn't worth it. You're nesting 3+ levels deep — at that point, the query becomes unreadable. Refactor into CTEs.
Your database doesn't support CTEs (rare — MySQL 8.0+, PostgreSQL, SQL Server, Oracle all support them). You need recursion — subqueries can't reference themselves. Only WITH RECURSIVE can.
You're using an older PostgreSQL (< v12) and performance matters — older versions materialize CTEs by default, which can be slower. Multiple people will maintain the query — unnamed subqueries buried in WHERE or FROM are harder for others to understand.

Real-World Example: Same Problem, Both Ways

Question: "Find employees who earn more than their department's average salary, and show how much more they earn."

Using a subquery (inline approach):

SELECT e.name, e.department, e.salary, e.salary - dept_avg.avg_sal AS above_average FROM employees e JOIN ( SELECT department, AVG(salary) AS avg_sal FROM employees GROUP BY department ) AS dept_avg ON e.department = dept_avg.department WHERE e.salary > dept_avg.avg_sal ORDER BY above_average DESC;

Using a CTE (named-step approach):

WITH dept_averages AS ( SELECT department, AVG(salary) AS avg_sal FROM employees GROUP BY department ) SELECT e.name, e.department, e.salary, e.salary - da.avg_sal AS above_average FROM employees e JOIN dept_averages da ON e.department = da.department WHERE e.salary > da.avg_sal ORDER BY above_average DESC;

Same Result, Different Experience

Both queries produce identical output and, in PostgreSQL 12+, identical execution plans. The difference is human — the CTE version tells you what dept_averages is before you see it used. In the subquery version, you have to read the inner query first, then mentally label it yourself. For a simple case like this, either works. As complexity grows, that naming advantage compounds.
