Key Insight: Hard Errors vs. Silent Errors
Hard Errors (you see a traceback): Easy to catch during testing. Stop execution. Examples: TypeError, KeyError, ValueError.

Silent Errors (code runs, result is wrong): Harder to catch—no traceback to alert you. Must inspect data with .shape, .head(), .dtypes. Examples: merge fan-out, dtype coercion, NaN propagation. Interview focus: Interviewers love testing if you check dimensions and dtypes before declaring code correct.
Reading Tracebacks

The Golden Rule: Read Bottom-Up

Python tracebacks look scary. They're not. They tell a linear story of where your code broke. Always read the last 3 lines first.

The 3-Second Read

  1. Error Type (last line): What went wrong? TypeError, KeyError, ValueError?
  2. Error Message (last line): Why did it go wrong? This is gold.
  3. The Code Line (in the traceback): Which line of your code caused it?

Real Example Traceback

Traceback (most recent call last): File "analysis.py", line 42, in <module> result = df['name'] + 5 ~~~~~~~~~~~~^~~ TypeError: unsupported operand type(s) for +: 'str' and 'int'

Labeled Breakdown

  • Traceback (most recent call last): — Start here, then read DOWN.
  • File "analysis.py", line 42 — Your code, line 42.
  • result = df['name'] + 5 — The exact code that broke.
  • TypeError: — Error type (not a KeyError, not a ValueError).
  • unsupported operand type(s) for +: 'str' and 'int' — The why: you tried to add a string to an int.

Interview Tip: Read Errors Out Loud
In a real interview, say the error message out loud after you see it. Don't stare silently.

Bad: Stare at the screen for 10 seconds.
Good: "I see a TypeError on line 42. It says I'm trying to add a string to an integer. That's because the 'name' column is text, not numeric."

This shows confidence and gives the interviewer insight into your thinking.
Type Errors

You tried to do something with incompatible types.

A1: String + Integer
▼

Trying to add an integer to a string column. This means your code crashes when trying to combine text and numbers in the same operation.

Error:
TypeError: unsupported operand type(s) for +: 'str' and 'int'
Broken Code:
import pandas as pd df = pd.DataFrame({'name': ['Alice', 'Bob'], 'age': [30, 25]}) result = df['name'] + 5 # Trying to add int to string column
Explanation:

You're treating a string column like a numeric column. Pandas preserves dtypes strictly.

Fix:
# If you meant to concatenate: convert to string result = df['name'] + df['age'].astype(str) # If you meant to add: convert name to numeric result = pd.to_numeric(df['name'], errors='coerce') + 5
Interview Strategy
1. Point it out: "Trying to add an integer to a string column"
2. Explain why: "Pandas preserves column data types strictly — you can't mix string and numeric operations"
3. Propose the fix: "Convert the string to numeric with pd.to_numeric(), or convert the number to string with .astype(str)"
4. Verify: "Check the result column exists and has the expected type and values"
A2: Wrong Argument Type to Function
▼

Function signature expects different argument types. Your function call fails because it received data in the wrong format.

Error:
TypeError: merge() got an unexpected keyword argument
Explanation:

The function signature expects certain arg types. You passed something it doesn't accept.

Fix:
# Read the function signature import pandas as pd help(pd.merge) # Correct usage: df_left.merge(df_right, left_on='id2', right_on='id', how='outer')
Interview Strategy
1. Point it out: "A function received an argument it doesn't accept or wrong type for that argument"
2. Explain why: "Function signatures are strict about parameter names and types"
3. Propose the fix: "Check the function docs; either rename the parameter or pass the right type"
4. Verify: "The function call now succeeds and returns expected output"
A3: Calling .columns as Function
▼

.columns and .index are attributes, not methods. Adding parentheses to a property turns it into a failed function call.

Error:
TypeError: 'Index' object is not callable
Broken Code:
cols = df.columns() # Wrong: .columns is an attribute
Fix:
cols = df.columns # Correct: no parentheses
Interview Strategy
1. Point it out: "Using .columns() with parentheses instead of .columns"
2. Explain why: ".columns is a property (attribute), not a method, so parentheses try to call it as a function"
3. Propose the fix: "Remove the parentheses: df.columns instead of df.columns()"
4. Verify: "df.columns now returns the column names as expected"
A4: Unsupported Operation Between Types
▼

Trying to perform an operation on incompatible types. Your code crashes because Pandas doesn't know how to combine or compare values of different kinds.

Error:
TypeError: unsupported operand type(s) for -: 'str' and 'str'
Fix:
# Check dtype first print(df.dtypes) # Convert to numeric if needed df['amount'] = pd.to_numeric(df['amount_str'])
Interview Strategy
1. Point it out: "Trying to perform math or comparison on incompatible types"
2. Explain why: "Operations like + and * are defined for numeric types but not for dates + strings"
3. Propose the fix: "Convert both operands to compatible types before the operation"
4. Verify: "The operation succeeds and produces sensible results"
Key & Index Errors

You tried to access a column or row that doesn't exist.

B1: Column Name Typo
▼

Column doesn't exist; maybe a typo in the name. A single character off in a column name and Pandas can't find your data.

Error:
KeyError: 'naem'
Broken Code:
df = pd.DataFrame({'name': ['Alice', 'Bob'], 'age': [30, 25]}) print(df['naem']) # Typo: 'naem' instead of 'name'
Fix:
# Always check column names first print(df.columns) # Use the correct name print(df['name'])
Interview Strategy
1. Point it out: "Referencing a column that doesn't exist (typo, case mismatch, extra space)"
2. Explain why: "Pandas matches column names exactly — even 'age' and 'Age' are different"
3. Propose the fix: "Print df.columns to see exact names; fix the typo or use df.rename() if needed"
4. Verify: "The column access now works without KeyError"
B2: Column Changed After Rename or Merge
▼

Column name changed; you're using the old name. Your code references a column name that no longer exists because a previous step changed it.

Error:
KeyError: 'user_id'
Fix:
# Always check columns after transformations df = df.rename(columns={'user_id': 'customer_id'}) print(df.columns) # Now 'customer_id' exists # For merge: specify suffixes df = df_orders.merge(df_users, on='id', suffixes=('_order', '_user'))
Interview Strategy
1. Point it out: "A column was renamed or deleted in a previous step, but you're still using the old name"
2. Explain why: "Once a column is renamed or deleted, the old name no longer exists"
3. Propose the fix: "Check what renamed/merged columns actually are called; use df.columns to verify"
4. Verify: "The column access works with the correct (new) name"
B3: Using String Label with iloc
▼

iloc uses integer positions; .loc uses labels. Mixing up label-based (.loc) and position-based (.iloc) access crashes your lookup.

Error:
TypeError or KeyError
Broken Code:
df = pd.DataFrame({'a': [1, 2, 3], 'b': [4, 5, 6]}) value = df.iloc['a'] # Wrong: iloc expects integer position
Fix:
# Use .loc for labels value = df.loc[:, 'a'] # Or use .iloc with integer position value = df.iloc[:, 0] # First column
Interview Strategy
1. Point it out: "Using a column name (label) with iloc, which expects integer positions"
2. Explain why: ".iloc is position-based, .loc is name-based — they're mutually exclusive"
3. Propose the fix: "Use .loc['name_str'] for labels or .iloc[0] for positions — not mixed"
4. Verify: "You get the correct cell/column value"
B4: MultiIndex or Hierarchical Columns
▼

Accessing columns in a MultiIndex DataFrame. Standard column access fails because multi-level headers require tuple notation to reach the right level.

Fix:
# Access with tuple value = df[('A', 'x')] # Check structure print(df.columns)
Interview Strategy
1. Point it out: "After groupby with multiple aggregations, column names become tuples"
2. Explain why: "MultiIndex columns let Pandas store hierarchical column names"
3. Propose the fix: "Flatten columns: df.columns = ['_'.join(str(c).strip() for c in col) for col in df.columns]"
4. Verify: "Column names are now simple strings, not tuples"
Value Errors

The value you provided doesn't match the operation's requirements.

C1: Length Mismatch When Assigning Column
▼

New column has different length than DataFrame. You're trying to attach a list of 50 values to a table with 100 rows — Pandas doesn't know how to fill the gap.

Error:
ValueError: Length of values (5) does not match length of index (10)
Fix:
# Make sure values match DataFrame length new_values = [10, 20, 30, 40, 50] # 5 values for 5 rows df['amount'] = new_values # Or use a Series with matching index df['amount'] = pd.Series([10, 20, 30, 40, 50], index=df.index)
Interview Strategy
1. Point it out: "Trying to assign data with different row count than DataFrame"
2. Explain why: "All columns in a DataFrame must have the same length"
3. Propose the fix: "Ensure the data being assigned has exactly df.shape[0] rows"
4. Verify: "Assignment succeeds and new column contains correct values"
C2: Cannot Convert String to Float
▼

String contains special characters preventing conversion. Hidden characters like dollar signs or commas prevent numbers from being recognized as numbers.

Error:
ValueError: could not convert string to float: '$1,234.56'
Fix:
# Remove non-numeric characters first df['price'] = df['price_str'].str.replace('$', '').str.replace(',', '') df['price'] = pd.to_numeric(df['price']) # Or use errors='coerce' df['price'] = pd.to_numeric(df['price_str'], errors='coerce')
Interview Strategy
1. Point it out: "Strings contain non-numeric characters (like $, commas, %) that prevent conversion"
2. Explain why: "Float only understands 123 or 123.45, not '$123.45' or '100%'"
3. Propose the fix: "Clean the strings first: remove $, commas, % before pd.to_numeric()"
4. Verify: "pd.to_numeric() succeeds and all values are numeric"
C3: Pivot Duplicates
▼

Pivot has duplicate index values. Multiple rows share the same key combination, and Pandas doesn't know which value to put in the cell — so it refuses.

Error:
ValueError: Index contains duplicate entries, cannot reshape
Fix:
# Aggregate duplicates first df = df.groupby(['date', 'product'])['sales'].sum().reset_index() pivot = df.pivot(index='date', columns='product', values='sales') # Or use pivot_table (handles duplicates) pivot = df.pivot_table(index='date', columns='product', values='sales', aggfunc='sum')
Interview Strategy
1. Point it out: "Multiple rows share the same (index, column) combination"
2. Explain why: "Pivot assumes each (row, column) pair is unique"
3. Propose the fix: "Add aggfunc parameter: pivot(aggfunc='sum') or aggregate first"
4. Verify: "Pivot completes and result shape makes sense"
C4: Concat Mismatched Index
▼
Fix:
# Reset index to avoid overlap result = pd.concat([df1, df2], ignore_index=True)
Interview Strategy
1. Point it out: "Combining DataFrames with different columns creates NaN-filled gaps"
2. Explain why: "Concat aligns on column names; missing values in one table show as NaN"
3. Propose the fix: "Check column names with df1.columns and df2.columns; rename as needed"
4. Verify: "Result has expected columns and NaN is only where intended"
Copy Warning Errors

You're modifying a view instead of a copy.

D1: Chained Indexing
▼

SettingWithCopyWarning from chained indexing. Your data update is ambiguous — Pandas can't tell if you're modifying the original or a temporary copy, so your change may silently fail.

Warning:
SettingWithCopyWarning: A value is trying to be set on a copy of a slice from a DataFrame.
Broken Code:
df[df['salary'] > 55000]['salary'] = df[df['salary'] > 55000]['salary'] + 1000 # WARNING!
Fix:
# Use .loc[] for unambiguous assignment df.loc[df['salary'] > 55000, 'salary'] += 1000
Interview Strategy
1. Point it out: "Using `df[condition]['col'] = value` where the assignment silently fails"
2. Explain why: "Chained indexing creates a temporary copy that Pandas doesn't connect to the original"
3. Propose the fix: "Use .loc[] instead: `df.loc[condition, 'col'] = value`"
4. Verify: "Check the original df — the value is actually changed"
D2: Modifying Slice Without .copy()
▼

Attempting to modify a filtered view. Changes to your filtered data may accidentally modify the original DataFrame, or may not work at all.

Broken Code:
subset = df[df['a'] > 2] # Creates a view subset['b'] = subset['b'] * 2 # Trying to modify the view
Fix:
# Use .copy() for explicit copy subset = df[df['a'] > 2].copy() subset['b'] = subset['b'] * 2 # Or use .loc[] directly on original df df.loc[df['a'] > 2, 'b'] = df.loc[df['a'] > 2, 'b'] * 2
Interview Strategy
1. Point it out: "Assigning to a filtered DataFrame without .copy() triggers SettingWithCopyWarning"
2. Explain why: "Pandas can't tell if you intend to modify the original or just the filtered view"
3. Propose the fix: "Add .copy() after filtering: filtered = df[condition].copy()"
4. Verify: "The warning disappears and assignments work as intended"
D3: Assigning to Filtered DataFrame
▼

Filtering a DataFrame may return a "view" instead of a copy — changes to it are ambiguous and may not stick.

What are .loc and .copy()?

.loc[] is Pandas' way of saying "go directly to this exact spot in the original DataFrame and change it there." Think of it like editing a document in place — you're making changes to the real thing, not a photocopy. When you write df.loc[df['x'] > 2, 'y'] = 999, you're telling Pandas: "find rows where x is greater than 2, and in those rows, set y to 999 — directly on the original data."

.copy() creates a completely independent clone of your data. Think of it like making a photocopy of a page — you can scribble all over the copy without affecting the original. When you write filtered = df[df['x'] > 2].copy(), you get a standalone DataFrame that you can modify freely without any risk of accidentally changing the original.

The problem happens when you filter without either of these tools. Pandas might give you a "view" (a window into the original) or a "copy" (an independent clone) — and you can't predict which. This ambiguity is what triggers the SettingWithCopyWarning.

Fix:
# Always use .copy() or .loc[] filtered = df[df['x'] > 2].copy() filtered['y'] = 999 # Or modify original df with .loc[] df.loc[df['x'] > 2, 'y'] = 999
Interview Strategy
1. Point it out: "Assigning to a filtered DataFrame triggers SettingWithCopyWarning or fails silently"
2. Explain why: "Filtering may return a view; Pandas doesn't know if you want to change the original"
3. Propose the fix: "Use .loc[] to modify in place, or .copy() to make an independent clone"
4. Verify: "Check the original df — the change did or didn't propagate as intended"
Merge Errors

This is where silent data corruption happens.

E1: Fan-Out — More Rows After Merge
▼

Row count increased unexpectedly after merge. Duplicate keys caused a Cartesian product — your 1,000-row table silently became 50,000 rows, inflating every downstream calculation.

Silent Error: Row count increased due to duplicate keys. Fix:
# Check key uniqueness BEFORE merging print(df_products['product_id'].value_counts()) # Aggregate duplicates before merge df_products_clean = df_products.drop_duplicates(subset=['product_id']) result = df_products_clean.merge(df_purchases, on='product_id') # Verify row count print(len(result))
Interview Strategy
1. Point it out: "Row count exploded after merge — more rows than either input"
2. Explain why: "Duplicate keys create every combination: 3 left rows × 4 right rows = 12 output rows"
3. Propose the fix: "Check for duplicates with .drop_duplicates(subset=['key']); deduplicate before merge"
4. Verify: "Row count is closer to expected; aggregations (SUM, COUNT) look reasonable"
E2: NaN in Join Keys (Silent Mismatch)
▼

NaN values don't match, even to other NaN. Rows with missing keys silently drop from your merge because NaN ≠ NaN — you lose data without any error message.

Silent Error: Result has fewer rows than expected. Fix:
# Check for NaN in join keys print(df_left['id'].isna().sum()) # Fill NaN with a sentinel value before merging df_left['id'] = df_left['id'].fillna(-999) df_right['id'] = df_right['id'].fillna(-999) result = df_left.merge(df_right, on='id')
Interview Strategy
1. Point it out: "Rows with NaN in the merge key disappeared from the result"
2. Explain why: "NaN != NaN, so rows with missing keys never match across tables"
3. Propose the fix: "Fill NaN before merge with df['key'].fillna(value), or handle separately"
4. Verify: "Missing-key rows are now in the result with NaN for unmatched columns"
E3: Dtype Mismatch in Join Keys
▼

Left key is int, right key is float; no match. The keys look identical to you but are different types to Pandas — your merge returns zero matches.

Silent Error: Merge result has 0 rows. Fix:
# Check dtypes BEFORE merge print(df_left.dtypes) print(df_right.dtypes) # Convert to same dtype df_left['id'] = df_left['id'].astype('int64') df_right['id'] = df_right['id'].astype('int64') result = df_left.merge(df_right, on='id')
Interview Strategy
1. Point it out: "Merge returned no matches despite the keys looking the same"
2. Explain why: "123 (int) and '123' (str) are completely different to Pandas"
3. Propose the fix: "Convert both keys to the same type: astype(int) or astype(str)"
4. Verify: "Merge result now has the expected number of matches"
E4: Overlapping Column Names
▼

Result has confusing _x and _y suffixes. Both DataFrames have a column called 'name', so Pandas renames them to 'name_x' and 'name_y' — breaking downstream code.

Fix:
# Specify suffixes explicitly result = df_orders.merge(df_customers, on='id', suffixes=('_order', '_customer')) print(result.columns)
Interview Strategy
1. Point it out: "Merge renamed columns to amount_x and amount_y, breaking downstream code"
2. Explain why: "Both tables have 'amount', so Pandas renames to avoid collision"
3. Propose the fix: "Rename columns before merge or use suffixes parameter: suffixes=('_left', '_right')"
4. Verify: "Column names are now as expected and downstream code works"
Shape Errors

Confusion about rows vs columns or Series vs DataFrame.

F1: DataFrame vs Series (Single vs Double Brackets)
▼

Result has unexpected dimensions (1D vs 2D). You expected a table but got a single column, or vice versa — follow-up operations crash because the shape is wrong.

Example:
df = pd.DataFrame({'a': [1, 2, 3], 'b': [4, 5, 6]}) # Single brackets: returns a Series (1D) series = df['a'] print(series.shape) # (3,) # Double brackets: returns a DataFrame (2D) df_slice = df[['a']] print(df_slice.shape) # (3, 1)
Fix:
# If you want a DataFrame with one column df_one_col = df[['a']] # If you want a Series series = df['a']
Interview Strategy
1. Point it out: "Code expects a DataFrame (2D table) but got a Series (1D list)"
2. Explain why: "df['col'] returns a Series; df[['col']] returns a DataFrame"
3. Propose the fix: "Use double brackets df[['col']] to keep DataFrame structure"
4. Verify: "Result is 2D and operations expecting a table now work"
F2: axis=0 vs axis=1 Confusion
▼

Applied function to wrong dimension. You dropped all your rows when you meant to drop a column, or vice versa.

Example:
import numpy as np df = pd.DataFrame({'a': [1, 2, 3], 'b': [4, 5, 6]}) # axis=0: operate on rows (sum each column) result = df.apply(np.sum, axis=0) # axis=1: operate on columns (sum each row) result = df.apply(np.sum, axis=1)
Fix:
# Be explicit about axis # axis=0: rows (operate on each column separately) # axis=1: columns (operate on each row separately) result = df.apply(np.sum, axis=1) # Sum across rows
Interview Strategy
1. Point it out: "Used wrong axis parameter — dropped rows instead of columns or vice versa"
2. Explain why: "axis=0 drops rows, axis=1 drops columns, but the parameter name is confusing"
3. Propose the fix: "Use named params instead: df.drop(columns=['col']) or df.drop(index=0)"
4. Verify: "Shape changed only in the intended direction"
F3: Boolean Indexing Returns Series
▼

Your boolean filter returned a flat Series instead of a DataFrame. Follow-up operations expecting a table will break.

Example:
df = pd.DataFrame({'x': [1, 2, 3], 'y': [10, 20, 30]}) # Single column: returns Series single = filtered['y'] # If you need DataFrame: single_df = filtered[['y']] # Returns DataFrame
Interview Strategy
1. Point it out: "Boolean filter returned a Series instead of a DataFrame"
2. Explain why: "Single-bracket filtering returns a Series; double-bracket returns a DataFrame"
3. Propose the fix: "Use df[[condition_series]] or convert to DataFrame: result.to_frame()"
4. Verify: "Result is 2D and can be used as a table"
F4: Transposing Confusion
▼

Rows and columns got swapped — your 1000 rows became 1000 columns, making everything downstream fail.

Example:
df = pd.DataFrame({'a': [1, 2, 3], 'b': [4, 5, 6]}) # Original: 3 rows, 2 cols print(df.shape) # (3, 2) # Transposed: 2 rows, 3 cols df_T = df.T print(df_T.shape) # (2, 3)
Interview Strategy
1. Point it out: "Rows and columns got swapped — making everything downstream fail"
2. Explain why: ".T transposes the DataFrame completely, swapping rows and columns"
3. Propose the fix: "Make sure you actually want to transpose; or transpose back with .T again"
4. Verify: "Downstream operations work with the new shape"
Silent Data Errors

Code runs, no error, but your data is quietly wrong.

G1: dtype Coercion (int Becomes float with NaN)
▼

Int column automatically becomes float when NaN introduced. Your user IDs silently change from 1, 2, 3 to 1.0, 2.0, 3.0 — breaking joins and string comparisons downstream.

Silent Error: int column automatically becomes float. Example:
import numpy as np df = pd.DataFrame({'count': [1, 2, 3, 4, 5]}) print(df['count'].dtype) # int64 # Add a NaN somewhere df.loc[2, 'count'] = np.nan print(df['count'].dtype) # float64 (changed!)
Fix:
# Use nullable integer type df['count'] = df['count'].astype('Int64') # Note capital 'I' # Or fill NaN before operations df['count'] = df['count'].fillna(-1).astype('int64')
Interview Strategy
1. Point it out: "Integer column became float after an operation"
2. Explain why: "Pandas converts int to float to represent NaN values"
3. Propose the fix: "Use nullable Int64: df['col'] = df['col'].astype('Int64')"
4. Verify: ".dtype shows Int64 and downstream joins work"
G2: Object dtype Hiding Mixed Types
▼

Column has mixed types (strings and ints). Your column looks normal but contains a mix of "123" and 123 — math operations silently fail or produce wrong results.

Silent Error: Column has mixed types. Example:
df = pd.DataFrame({'id': [1, '2', 3, '4']}) print(df['id'].dtype) # object (not int)
Fix:
# Check dtype print(df.dtypes) # Convert all values to same type df['id'] = pd.to_numeric(df['id'], errors='coerce')
Interview Strategy
1. Point it out: "Column is object dtype with mixed strings and numbers, causing .sum() to concatenate"
2. Explain why: "object dtype can hold anything; .sum() defaults to string concatenation if it sees any text"
3. Propose the fix: "Check df['col'].apply(type) to find the mixed types; clean and convert to numeric"
4. Verify: ".dtype is now numeric and .sum() produces a number"
G3: NaN Propagation in Operations
▼

NaN in calculations propagates to entire result. One missing value in your data poisons the entire calculation — your sum, mean, or total becomes NaN.

Silent Error: NaN propagates to results. Fix:
# Fill NaN before operations result = df['a'].fillna(0) + df['b'] # Or use skipna in aggregations total = df.sum(skipna=True) # Ignores NaN
Interview Strategy
1. Point it out: "One NaN value in a calculation chain poisoned all downstream results"
2. Explain why: "NaN + anything = NaN, so a single missing value propagates through the entire chain"
3. Propose the fix: "Fill NaN before calculations: df['col'].fillna(0) or use skipna=True in .sum()"
4. Verify: "Results are now numeric instead of all NaN"
G4: String Accessor on Non-String Columns
▼
Example:
df = pd.DataFrame({'id': [1, 2, 3]}) result = df['id'].str.upper() # Error: id is int, not string
Fix:
# Convert to string first result = df['id'].astype(str).str.upper()
Interview Strategy
1. Point it out: "Calling .str.upper() on a column that isn't actually string type"
2. Explain why: ".str accessor only works on object dtype (string) columns"
3. Propose the fix: "Convert to string first: df['col'] = df['col'].astype(str)"
4. Verify: ".str accessor methods now work without error"
G5: Groupby Dropping NaN Groups
▼

Rows where the group key is NaN silently disappear from your groupby results — and your totals won't add up.

Silent Error: NaN groups are silently dropped. Fix:
# Include NaN group result = df.groupby('category', dropna=False)['value'].sum() print(len(result)) # Now includes NaN group

Common Interview Traps

Interviewers will intentionally plant bugs. Here are the top traps:

Chained Indexing
▼

Assignment via chained indexing produces SettingWithCopyWarning. This means your data update may silently fail — the change you think you made never actually sticks.

What's Happening:

When you write df[df['x']>5]['y']=10, Pandas first filters to create a temporary object, then tries to assign to it. But that temporary object might be a "view" (a window into the original) or a "copy" (an independent clone). Pandas doesn't know which one it gave you, so it warns you the assignment is ambiguous.

What They Want to Hear:

"This creates a view, not a copy. We should use .loc[] instead."

Why the Fix Works:

.loc[] talks directly to the original DataFrame in a single operation — there's no intermediate copy or view. Pandas knows exactly what you want to modify, so the assignment is guaranteed to work.

The Fix:
df.loc[df['x'] > 5, 'y'] = 10 # Unambiguous
Interview Strategy
1. Point it out: "When you write df[df['x']>5]['y']=10, Pandas creates a temporary filtered view, then tries to assign to it, but that temporary view might not be connected to the original DataFrame"
2. Explain why: ".loc[] talks directly to the original DataFrame, so there's no ambiguity about which copy gets modified"
3. Propose the fix: "Use .loc[] instead: df.loc[df['x'] > 5, 'y'] = 10"
4. Verify: "Check the original df — the value is actually changed"
Merge Fan-Out
▼

Duplicate keys on both sides produce Cartesian product. Your row count explodes — a 100-row table can become 10,000 rows, throwing off every downstream calculation.

What's Happening:

When both sides of a merge have duplicate keys, Pandas creates every possible combination. If the left table has 3 rows with key "A" and the right has 4 rows with key "A", you get 3×4 = 12 rows for that key alone. This silently inflates your dataset without any error.

What They Want to Hear:

"I need to check key uniqueness before merging. Let me aggregate duplicates or use .drop_duplicates() first."

Why the Fix Works:

Deduplicating ensures each key appears only once on at least one side. With unique keys, each row matches at most one partner, so the merge produces a clean result — no explosion.

Interview Strategy
1. Point it out: "If both sides of your merge have duplicate keys, Pandas creates every possible combination. 3 rows matching 4 rows becomes 12 rows"
2. Explain why: "Deduplicating or aggregating first ensures each key appears once, so the merge is clean"
3. Propose the fix: "Deduplicate before merge with .drop_duplicates(subset=['key'])"
4. Verify: "Row count matches expected; aggregations (SUM, COUNT) look reasonable"
NaN in Groupby
▼

Groupby has NaN values that silently get dropped. Rows with missing group keys vanish from your results — your totals no longer add up.

What's Happening:

By default, Pandas skips NaN values when grouping. If 20 of your 100 rows have a NaN category, those 20 rows simply disappear from all group calculations. Your group totals won't match the overall total.

What They Want to Hear:

"NaN values are skipped by groupby. If we need them, use .groupby('category', dropna=False) or handle explicitly."

Why the Fix Works:

dropna=False tells Pandas to treat NaN as its own group rather than ignoring it. Every row now belongs to some group, so your totals stay consistent and no data silently disappears.

Interview Strategy
1. Point it out: "By default, Pandas skips NaN values when grouping. If 20 of your 100 rows have a NaN category, those 20 rows simply vanish"
2. Explain why: "dropna=False tells Pandas to create a group for NaN values, so all rows are accounted for"
3. Propose the fix: "Use .groupby(..., dropna=False) to include NaN as its own group"
4. Verify: "The sum of group totals now matches the overall total"
Integer Column with NaN
▼

Assigning NaN to int column silently becomes float64. Your user IDs suddenly look like 1.0, 2.0, 3.0 — and downstream joins break because "1" ≠ "1.0".

What's Happening:

Standard Python integers can't represent "missing." When you introduce a NaN into an integer column, Pandas switches the entire column to float64. Now every value gets a decimal point — 1 becomes 1.0, 2 becomes 2.0. This silently breaks string comparisons, joins, and display formatting.

What They Want to Hear:

"Int columns can't have NaN. Either use nullable Int64, or handle NaN with .fillna() and keep as int."

Why the Fix Works:

Pandas' nullable Int64 (capital I) can hold both integers and NaN without converting to float. Your values stay clean (1, 2, 3, NaN) and joins work correctly.

Interview Strategy
1. Point it out: "When you introduce a NaN into an integer column, Pandas silently converts the entire column to float64. Now your user IDs look like 1.0, 2.0, 3.0"
2. Explain why: "Pandas' nullable Int64 (capital I) can hold both integers and NaN without converting to float"
3. Propose the fix: "Convert to Int64: df['id'] = df['id'].astype('Int64')"
4. Verify: "Joins work again and .dtype shows Int64"
inplace=True Return Value
▼

Assigning inplace=True return value results in None. Your DataFrame disappears — the variable now points to nothing, and the next line crashes.

What's Happening:

When you use inplace=True, the method modifies the DataFrame directly and returns None. If you also assign the result (df = df.drop('col', inplace=True)), you're setting df to None. The drop worked, but you lost your reference to the DataFrame.

What They Want to Hear:

"inplace=True returns None. Either use inplace=True without assignment, or assign the result of the regular operation."

Why the Fix Works:

Picking one pattern avoids the contradiction. df.drop('col', inplace=True) modifies df directly (no assignment needed). Or df = df.drop('col') returns a new DataFrame that you assign. Either way, df stays valid.

Wrong:
df = df.drop('column', inplace=True) # df becomes None!
Interview Strategy
1. Point it out: "inplace=True modifies the DataFrame directly and returns None. Assigning that None back to df destroys the variable"
2. Explain why: "You're combining two patterns that contradict each other — inplace mutation and reassignment"
3. Propose the fix: "Either df.drop('col', inplace=True) without assignment, or df = df.drop('col') without inplace"
4. Verify: "df is not None and the column is actually removed"
Missing .copy()
▼

Modifying a filtered slice without .copy(). Your changes might accidentally alter the original DataFrame, or they might not stick at all — the behavior is unpredictable.

What's Happening:

When you filter a DataFrame (subset = df[df['a']>2]), Pandas might give you a view (a window into the original data) or a copy (an independent clone). If it's a view, modifying subset also changes df. If it's a copy, your changes to subset are lost. You can't predict which one you'll get.

What They Want to Hear:

"This modifies a view. We need .copy() or use .loc[]."

Why the Fix Works:

.copy() forces Pandas to create an independent clone, so your modifications are guaranteed to stay on the subset without affecting the original. Or .loc[] operates directly on the original, removing all ambiguity.

Interview Strategy
1. Point it out: "Filtering a DataFrame gives you a view — a window into the original data. Modifying this view is ambiguous"
2. Explain why: ".copy() creates an independent clone, so modifications don't affect the original"
3. Propose the fix: "Add .copy(): filtered = df[condition].copy()"
4. Verify: "The warning is gone and original df is untouched"
Wrong Merge Type
▼

Using how='inner' when you meant how='left'. Rows from your primary table silently disappear — customers with no orders vanish from your report.

What's Happening:

An inner merge only keeps rows where the key exists in BOTH DataFrames. If a customer has no orders, that customer disappears entirely. You expected 1,000 customers but got 800 — the 200 with no orders were silently dropped.

What They Want to Hear:

"Inner merge only keeps matching rows. For a left join preserving all source rows, use how='left'."

Why the Fix Works:

A left merge keeps every row from the left (primary) DataFrame. Where there's no match on the right, Pandas fills in NaN. This preserves your full customer list and makes the "no orders" case visible rather than hidden.

Interview Strategy
1. Point it out: "An inner merge only keeps rows where the key exists in BOTH DataFrames. Customers with no orders silently disappear"
2. Explain why: "A left merge preserves every row from the left DataFrame, filling in NaN where there's no match"
3. Propose the fix: "Use how='left' instead of how='inner'"
4. Verify: "Row count matches expected; all left rows are present"
axis Confusion
▼

Using axis=0 when you meant axis=1. You accidentally delete rows instead of columns (or vice versa) — and the error is silent if the label exists on both axes.

What's Happening:

In Pandas, axis=0 means "operate along rows" (drop a row) and axis=1 means "operate along columns" (drop a column). The naming is counter-intuitive. If you meant to drop a column but used axis=0, Pandas tries to drop a row with that label instead.

What They Want to Hear:

"axis=0 is rows, axis=1 is columns. For clarity, use df.drop(columns=['col']) or df.drop(index=0)."

Why the Fix Works:

Named parameters (columns= or index=) remove the ambiguity entirely. You never have to remember which axis number is which — the parameter name says exactly what you're dropping.

Interview Strategy
1. Point it out: "axis=0 means 'operate along rows', axis=1 means 'operate along columns' — drop(axis=0) drops a ROW"
2. Explain why: "Using named parameters like columns=['col'] or index=[0] removes the ambiguity"
3. Propose the fix: "Use df.drop(columns=['col']) or df.drop(index=[0]) instead of axis"
4. Verify: "Shape changed only in the intended dimension"
Dtype Mismatch in Merge
▼

Left key is int64, right key is float64; merge returns 0 rows. Your join silently produces an empty result because the keys look the same but are different types to Pandas.

What's Happening:

Your left table has user_id as integer (123) and right table has it as string ("123"). They look identical when printed, but Pandas treats them as completely different types. Since no integer equals a string, the merge finds zero matches and returns an empty DataFrame.

What They Want to Hear:

"Join keys must have the same dtype. Convert: df['id'] = df['id'].astype('int64') before merging."

Why the Fix Works:

Converting both keys to the same type ensures Pandas can compare them correctly. Once the types match, the merge finds the matches it was missing.

Interview Strategy
1. Point it out: "Your left table has user_id as integer (123) and right table as string ('123'). They look the same but are completely different types"
2. Explain why: "Converting both keys to the same type ensures they can be compared correctly"
3. Propose the fix: "Convert both: df1['key'] = df1['key'].astype(str)"
4. Verify: "Merge result now has more rows (closer to expected)"
Silent dtype Coercion
▼

Applying numeric function to string column. Your calculations return wrong answers or silently skip values because the column looks numeric but is stored as text.

What's Happening:

A column that looks numeric (1, 2, 3) might actually be stored as strings ("1", "2", "3") with dtype "object." Functions like .mean() silently skip string columns, so you get no error — just a missing or wrong result.

What They Want to Hear:

"Always check .dtypes and use pd.to_numeric() or .astype() before math operations."

Why the Fix Works:

pd.to_numeric() converts string representations of numbers into actual numeric types. Once the dtype is correct, all math operations work as expected.

Interview Strategy
1. Point it out: "A column that looks numeric might be stored as strings (object dtype). Functions like .mean() silently skip those values"
2. Explain why: "Checking .dtypes and using pd.to_numeric() ensures data is in the right format"
3. Propose the fix: "Check df.dtypes; use pd.to_numeric(df['col'], errors='coerce')"
4. Verify: ".dtype is now numeric and .mean() produces a number"
Overlapping Column Names
▼

Merge without suffixes; result has _x and _y everywhere. Your downstream code references "amount" but the column is now "amount_x" — nothing works.

What's Happening:

Both DataFrames have a column called "amount." Pandas can't keep two columns with the same name, so it silently renames them to "amount_x" and "amount_y." Every downstream reference to "amount" now breaks.

What They Want to Hear:

"Specify suffixes=('_left', '_right') or rename columns before merging for clarity."

Why the Fix Works:

Renaming columns before the merge (e.g., "order_amount" and "return_amount") or using descriptive suffixes makes the result self-documenting. Downstream code can reference meaningful names instead of guessing what _x and _y mean.

Interview Strategy
1. Point it out: "Both DataFrames have a column called 'amount.' After merge, they become amount_x and amount_y, breaking downstream code"
2. Explain why: "Renaming columns before merging prevents the cryptic _x/_y naming"
3. Propose the fix: "Rename before merge or use suffixes: merge(..., suffixes=('_left', '_right'))"
4. Verify: "Downstream code uses the new column names"
Pandas Version Differences
▼

Code uses .append() which was removed in Pandas 2.0. Code that worked for years on one machine crashes on another — version-dependent methods are a hidden time bomb.

What's Happening:

Methods like .append() worked for years but were removed in Pandas 2.0. Code that ran perfectly on your colleague's older environment crashes on your updated one. The error says the method doesn't exist, which is confusing when you know it used to work.

What They Want to Hear:

"Check Pandas version and use pd.concat() instead of deprecated .append()."

Why the Fix Works:

pd.concat() is the officially supported replacement that works across all modern Pandas versions. It handles edge cases better than the old .append() method.

Interview Strategy
1. Point it out: "Methods like .append() worked for years but were removed in Pandas 2.0. Code that ran on your colleague's machine crashes on yours"
2. Explain why: "Using pd.concat() is the officially supported replacement that works across all modern versions"
3. Propose the fix: "Replace .append() with pd.concat(), .sort() with .sort_values()"
4. Verify: "Code runs on multiple Pandas versions"
