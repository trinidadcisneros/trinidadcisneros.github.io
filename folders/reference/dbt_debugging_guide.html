Key Insight: dbt Errors Bubble Up

The error hierarchy is sequential. dbt always checks YAML first, then Jinja, then SQL. If you see a Jinja error, YAML is valid. If you see a SQL error, YAML and Jinja are valid.

Example flow: YAML error → Fix indentation → Jinja error → Fix ref() → SQL error → Fix column name → Test failure → Fix data issue.

How to Read dbt Error Output

Anatomy of a dbt Cloud Error

dbt errors occur at multiple layers. Understanding which layer failed is the first step to fixing the problem.

The dbt Error Hierarchy

Errors propagate upward through this stack:

  1. YAML Parsing — dbt reads schema.yml and models (must be valid YAML)
  2. Jinja Compilation — dbt renders Jinja templates and resolves ref()/source() calls
  3. SQL Compilation — dbt generates final SQL and sends to warehouse
  4. Database Execution — warehouse executes SQL and may return SQL errors
  5. Test Execution — dbt runs tests against the model data

If a model fails at step 1 (YAML), it never reaches step 2. If it fails at step 2 (Jinja), the compiled SQL is never generated.

Real Example: Dissecting a dbt Error

ERROR in model my_first_dbt_model (models/example/my_first_dbt_model.sql): Compilation Error in model my_first_dbt_model (models/example/my_first_dbt_model.sql) ('str' object does not support item assignment) error in macro render (macros/generate_alias_explore.sql): 'str' object does not support item assignment

Labeled Parts:

  • ERROR in model: The file that failed (models/example/my_first_dbt_model.sql)
  • Compilation Error: This is a Jinja/macro error during compilation, not a database error
  • Error message: 'str' object does not support item assignment (indicates bad Jinja syntax)
  • Macro name: error in macro render (tells you the exact macro where the error occurred)

Types of dbt Errors

Error Level What It Means Where to Look Example
YAML Parsing Error Invalid YAML syntax in schema.yml or dbt_project.yml dbt logs show "Error reading model definition" tabs instead of spaces, wrong nesting
Compilation Error Jinja template error, undefined ref/source, macro issue dbt compile output, check Jinja logic and macro calls ref('nonexistent_model'), missing closing %}
SQL Runtime Error Database rejected the SQL (invalid syntax, missing column, permission denied) dbt Cloud Logs panel, warehouse query history Column does not exist, type mismatch, division by zero
Test Failure Data in model violates test assertion dbt test output, shows which rows failed unique constraint violated, NULL values found
DAG/Dependency Error Circular reference or unresolved dependency dbt parse output, use dbt DAG to inspect model A refs B, B refs A

Interview Tip: dbt-Level vs Warehouse-Level Errors

dbt-level errors stop the process before SQL is sent to the warehouse (YAML parsing, Jinja compilation, ref/source resolution). Look at dbt logs.

Warehouse-level errors occur during SQL execution or test evaluation. The SQL is valid dbt SQL but the warehouse rejects it. Check warehouse query history and error messages.

To distinguish: if dbt Cloud shows a red error in the Logs panel BEFORE it mentions the warehouse, it's a dbt-level error. If it shows "executing SQL" and then fails, it's a warehouse error.

Pattern A: YAML & Configuration Errors

A1: Indentation Error (Tabs vs Spaces)

▼

YAML indentation must be consistent spaces, not tabs

Error Message:

Invalid yaml structure: expected <block end>, but found '<block mapping start>'

Broken YAML (models/schema.yml):

version: 2 models: - name: my_model columns: - name: id # Used tab instead of 4 spaces! data_type: integer

Explanation: dbt requires YAML indentation to be consistent (typically 2 or 4 spaces). If you mix tabs and spaces, or use inconsistent spacing, the YAML parser fails.

Fix:

version: 2 models: - name: my_model columns: - name: id data_type: integer

Use spaces only, 2 or 4 consistently. Most editors have a setting to show/replace tabs.

A2: Missing Required Field

▼

Model definition must include required fields like name

Error Message:

Error in model definition (models/schema.yml): Missing required field 'name'

Broken YAML (models/schema.yml):

version: 2 models: - columns: # Missing 'name' field! - name: id

Explanation: Every model definition must have a 'name' field. Same for sources, columns, and tests.

Fix:

version: 2 models: - name: my_model columns: - name: id

A3: Duplicate Model/Source Names

▼

Model names must be unique across the project

Error Message:

Error: dbt found two definitions of model 'my_model'

Broken YAML (models/schema.yml):

version: 2 models: - name: my_model description: First definition - name: my_model # Duplicate! description: Second definition

Explanation: dbt model names must be unique within a project. If you define the same model twice (perhaps across two schema.yml files), dbt will error.

Fix: Rename one of the duplicates or merge their definitions into a single model block:

version: 2 models: - name: my_model description: Unified description columns: - name: id

A4: Invalid Test Configuration

▼

Test name doesn't match built-in tests or custom test file

Error Message:

Error: Test 'invalid_test_name' does not exist

Broken YAML (models/schema.yml):

version: 2 models: - name: my_model columns: - name: id tests: - invalid_test_name # Typo! - unique

Explanation: You referenced a test that doesn't exist (either typo in name or test not in project). dbt has built-in tests: 'unique', 'not_null', 'accepted_values', 'relationships'.

Fix:

version: 2 models: - name: my_model columns: - name: id tests: - unique - not_null
Pattern B: Compilation Errors (Jinja/ref/source)

B1: ref() to Non-Existent Model

▼

Model name in ref() doesn't match any model in the project

Error Message:

ERROR: 'nonexistent_model' does not exist in this dbt project!

Broken Code (models/marts/fact_orders.sql):

SELECT o.order_id, c.customer_name FROM {{ ref('nonexistent_model') }} o -- Typo in model name JOIN {{ ref('customers') }} c ON o.customer_id = c.customer_id

Explanation: You referenced a model in ref() that doesn't exist. Common causes: typo, model deleted, model in wrong folder.

Fix:

FROM {{ ref('stg_orders') }} o -- Correct model name

B2: source() Referencing Undefined Source

▼

Source not defined in schema.yml or source name/table mismatch

Error Message:

ERROR: source 'raw.nonexistent_table' does not exist in this dbt project!

Broken Code (models/staging/stg_orders.sql):

SELECT order_id, customer_id FROM {{ source('raw', 'nonexistent_table') }} -- Typo in source name

Explanation: You referenced a source that is not defined in schema.yml. The source definition must exist and match the source_name and table_name.

Fix:

FROM {{ source('raw_data', 'orders') }} -- Correct source and table name

B3: Jinja Syntax Error

▼

Missing closing brackets or mismatched Jinja delimiters

Error Message:

ERROR: unexpected '}'

Broken Code (models/marts/fact_orders.sql):

SELECT order_id, {{ 'amount' | upper }} -- Missing closing }} FROM {{ ref('orders') }}

Explanation: Jinja uses {{ }} for variable interpolation and {% %} for control flow. Missing closing delimiters or mismatched brackets cause parse errors.

Fix:

SELECT order_id, {{ 'amount' | upper }} -- Added closing }} FROM {{ ref('orders') }}

B4: Macro Not Found or Wrong Arguments

▼

Macro doesn't exist in project or wrong number of arguments

Error Message:

ERROR: macro 'generate_alias' does not exist

Broken Code (models/staging/stg_orders.sql):

{{ config(alias = generate_alias(customer_id)) }} -- Macro typo or missing SELECT * FROM {{ ref('raw_orders') }}

Explanation: You called a macro that doesn't exist or passed wrong number of arguments. Check macros/ folder.

Fix:

{{ config(alias = generate_alias('customer_id')) }}

B5: Circular Reference

▼

Model A depends on Model B and Model B depends on Model A

Error Message:

ERROR: Circular dependency detected: model_a -> model_b -> model_a

Broken Code:

-- models/staging/model_a.sql SELECT * FROM {{ ref('model_b') }} -- models/staging/model_b.sql SELECT * FROM {{ ref('model_a') }} -- Circular!

Explanation: Model A depends on Model B, and Model B depends on Model A. dbt cannot resolve this DAG.

Fix: Break the cycle by removing one dependency. Introduce an intermediate model or refactor the logic.

Pattern C: Database/SQL Runtime Errors

C1: Column Does Not Exist

▼

Warehouse cannot find the column you're referencing in SQL

Error Message:

ERROR: column "customer_id" does not exist

Broken Code (models/marts/fact_orders.sql):

SELECT order_id, customer_id, -- This column doesn't exist in the source order_amount FROM {{ ref('stg_orders') }}

Explanation: The column you're trying to select doesn't exist in the upstream model or source. Check the actual columns in the source.

Fix:

SELECT order_id, cust_id, -- Correct column name order_amount FROM {{ ref('stg_orders') }}

C2: Type Mismatch in JOIN

▼

Joining columns with different data types

Error Message:

ERROR: cannot perform INNER JOIN on columns of type integer and varchar

Broken Code (models/marts/fact_orders.sql):

SELECT o.order_id, c.customer_name FROM {{ ref('stg_orders') }} o JOIN {{ ref('stg_customers') }} c ON o.customer_id = c.customer_id_str -- int vs varchar

Explanation: o.customer_id is integer, c.customer_id_str is varchar. Databases require matching types for joins.

Fix:

ON cast(o.customer_id as varchar) = c.customer_id_str

C3: Division by Zero

▼

Dividing by a column that can be zero or NULL

Error Message:

ERROR: division by zero

Broken Code (models/marts/fact_revenue.sql):

SELECT order_id, revenue / units_sold as price_per_unit -- units_sold can be 0 FROM {{ ref('stg_orders') }}

Explanation: If units_sold is 0 or NULL, division fails. Use NULLIF to prevent division by zero.

Fix:

revenue / nullif(units_sold, 0) as price_per_unit

C4: Permission Denied

▼

dbt role doesn't have SELECT permission on source table

Error Message:

ERROR: permission denied for schema raw_data

Explanation: The dbt database user doesn't have SELECT permission on the source table or schema.

Fix:

GRANT SELECT ON SCHEMA raw_data TO dbt_user;
Pattern D: Test Failures

Key Concept: Test Failures = Data Problems

When a test fails, your model code is valid but your data violates the test assertion. Tests check data quality, not code syntax.

D1: Unique Test Failed

▼

Column has duplicate values when it should be unique

Error Message:

ERROR: Unique violation on model fact_orders column order_id: 2 duplicates found

Test Definition (models/schema.yml):

models: - name: fact_orders columns: - name: order_id tests: - unique -- Claims order_id is unique

Root Cause: Either the upstream data has duplicates, or your model is not deduplicating correctly.

Fix: Add deduplication to your model or trace the duplicate upstream:

SELECT order_id, row_number() over (order by order_id) as rn FROM {{ ref('stg_orders') }} WHERE rn = 1 -- Keep only first occurrence

D2: Not Null Test Failed

▼

Column has NULL values when it should be NOT NULL

Error Message:

ERROR: Not null violation on model fact_orders column customer_id: 15 nulls found

Test Definition (models/schema.yml):

columns: - name: customer_id tests: - not_null

Root Cause: Source data has NULLs or your model logic isn't filtering them out.

Fix: Filter or coalesce NULLs in your model:

SELECT order_id, coalesce(customer_id, -1) as customer_id -- Replace NULL with -1 FROM {{ ref('stg_orders') }} WHERE customer_id is not null -- Or filter NULLs

D3: Accepted Values Test Failed

▼

Column contains values not in the accepted list

Error Message:

ERROR: Accepted values violation on model fact_orders column status: Invalid value 'pending' (not in [completed, cancelled])

Test Definition (models/schema.yml):

columns: - name: status tests: - accepted_values: values: ['completed', 'cancelled']

Root Cause: Source data contains unexpected status values.

Fix: Filter or normalize the status values:

SELECT order_id, case when status in ('completed', 'cancelled') then status else 'unknown' end as status FROM {{ ref('stg_orders') }}

D4: Relationships Test Failed

▼

Foreign key values don't exist in referenced table

Error Message:

ERROR: Relationships violation on model fact_orders column customer_id: 5 values not found in dim_customers.customer_id

Test Definition (models/schema.yml):

columns: - name: customer_id tests: - relationships: to: ref('dim_customers') field: customer_id

Root Cause: Source data has customer_ids that don't exist in dim_customers. This is a data quality issue upstream.

Fix: Filter orphan foreign keys or ensure data consistency:

SELECT o.order_id, o.customer_id FROM {{ ref('stg_orders') }} o INNER JOIN {{ ref('dim_customers') }} c ON o.customer_id = c.customer_id -- Only keep matching rows
Pattern E: Dependency & DAG Errors

E1: Orphan Model (Not Referenced)

▼

Model exists but is never used by any other model or test

Issue: You have a model that is never used by any downstream model. This wastes compute.

Solution: Either reference the model with ref() in another model, or delete it if it's not needed:

-- Add to another model SELECT * FROM {{ ref('orphan_model') }}

E2: Unresolved Selector

▼

dbt run --select doesn't match any models

Error Message:

ERROR: No models match the selection criteria: nonexistent_model

Fix: Check the correct model name:

dbt run --select fact_orders -- Use correct model name dbt run --select tag:daily -- Or use tags

E3: Missing Package Dependency

▼

Macro from a package is used but package not installed

Error Message:

ERROR: macro dbt_utils.get_search_path not found

Fix: Add the package to packages.yml and run dbt deps:

packages: - package: dbt-labs/dbt_utils version: 1.0.0

Then run:

dbt deps
Pattern F: Incremental Model Issues

F1: Duplicates on Incremental Run

▼

Table has duplicate rows after incremental run

Issue: On incremental run, new data is appended but unique_key is not set or is wrong.

Broken Code (models/fact_orders.sql):

{{ config( materialized='incremental' ) }} SELECT * FROM {{ source('raw', 'orders') }} {% if is_incremental() %} WHERE order_date >= ( SELECT max(order_date) FROM {{ this }} ) {% endif %}

Fix: Set unique_key so dbt knows which rows to update/delete:

{{ config( materialized='incremental', unique_key='order_id' ) }}

F2: Schema Change Not Reflected

▼

New column added but old table not updated with new schema

Issue: You added a column to your model, but the incremental table still has the old schema.

Fix: Use --full-refresh to rebuild the table from scratch:

dbt run --select fact_orders --full-refresh

F3: is_incremental() Logic Error

▼

Logic that depends on is_incremental() returns wrong results

Issue: On first run, the destination table doesn't exist, so MAX(order_date) returns NULL. The WHERE clause becomes WHERE order_date >= NULL, which filters everything out.

Broken Code (models/fact_orders.sql):

{{ config(materialized='incremental') }} SELECT * FROM {{ source('raw', 'orders') }} {% if NOT is_incremental() %} -- This evaluates to TRUE on first run! WHERE order_date >= ( SELECT MAX(order_date) FROM {{ this }} ) {% endif %}

Fix: Use dbt's built-in is_incremental() macro correctly:

{{ config( materialized='incremental', unique_key='order_id' ) }} SELECT order_id, customer_id, order_amount FROM {{ source('raw', 'orders') }} {% if is_incremental() %} WHERE order_date >= ( SELECT MAX(order_date) FROM {{ this }} ) {% endif %}

is_incremental() returns True only if the table exists and dbt run --incremental is used. On first run, it's False, so all data is loaded.

F4: When to Use --full-refresh

▼

Full refresh rebuilds incremental table from scratch

Use dbt run --full-refresh when:

  • Schema changed (new column added or removed)
  • unique_key changed
  • Incremental logic is broken and you need to rebuild from scratch
  • Historical data needs to be reloaded

Example:

# Run all incremental models with full refresh dbt run --full-refresh # Run specific model with full refresh dbt run --select fact_orders --full-refresh
Pattern G: Source Freshness & Environment Issues

G1: Source Freshness Failure

▼

Source table hasn't been updated within the freshness threshold

Error Message:

Source 'raw.orders' has freshness warning: last loaded 2 days ago (threshold: 24 hours)

Source Definition (models/sources.yml):

version: 2 sources: - name: raw tables: - name: orders freshness: warn_after: {count: 24, period: hour} loaded_at_field: loaded_timestamp

What It Means: The source table hasn't been updated in more than 24 hours. The data might be stale.

Fix:

1. Check if the upstream pipeline (that loads raw.orders) is running. 2. Adjust the freshness threshold if 24 hours is too strict: warn_after: {count: 48, period: hour} # Allow 48 hours 3. Or remove the freshness check if not needed.

G2: Environment Variable Not Set

▼

dbt Cloud job missing environment variable

Error Message:

ERROR: Undefined variable 'my_env_var' in dbt Cloud job

Broken Code (models/fact_orders.sql):

SELECT * FROM {{ source('raw', 'orders') }} WHERE load_date > '{{ env_var("START_DATE") }}' -- Environment variable not set!

Fix:

1. Set the variable in dbt Cloud job settings: - Go to dbt Cloud → Job Settings → Environment Variables - Add: START_DATE = 2024-01-01 2. Or set in dbt_project.yml: vars: START_DATE: 2024-01-01 3. Use with default value for safety: WHERE load_date > '{{ env_var("START_DATE", "2024-01-01") }}'

G3: Profile/Target Mismatch

▼

Target defined in profiles.yml doesn't exist

Error Message:

ERROR: Target 'prod' not found in profiles.yml

Broken ~/.dbt/profiles.yml:

my_project: target: prod # Set to prod outputs: dev: # Only 'dev' defined, 'prod' missing! type: postgres host: localhost

Fix: Define the 'prod' target:

my_project: target: dev # Or use 'prod' if it's defined below outputs: dev: type: postgres host: localhost prod: type: postgres host: prod-warehouse.com

In dbt Cloud: Profiles are managed by dbt Cloud, not locally. Set the target in Job Settings → Environment → Target name.

G4: Package Dependency Conflicts

▼

Package requires dbt version newer than installed

Error Message:

ERROR: Package version conflict: dbt_utils requires dbt >= 1.3.0, but you have dbt 1.2.0

Broken packages.yml:

packages: - package: dbt-labs/dbt_utils version: 1.0.0 # Requires dbt >= 1.3.0

Fix:

1. Upgrade dbt: pip install --upgrade dbt-core 2. Or downgrade the package: packages: - package: dbt-labs/dbt_utils version: 0.9.0 # Compatible with dbt 1.2.0 3. Or remove the package if not needed.
Code Review Checklist for dbt

When reviewing dbt code, use this three-pass checklist. Each pass focuses on a different aspect of code quality.

Pass 1: Structure

Check the organization, naming, and dependency declarations.

Check What to Look For Red Flag
Naming Convention Model names are lowercase, snake_case, descriptive Names like my_model, temp, table1
Folder Organization Staging in staging/, marts in marts/, intermediate in intermediate/ Models scattered randomly, no clear structure
ref() Usage All dependencies use ref('model_name') to reference other dbt models Hardcoded table names like schema.table or "raw"."orders"
source() Usage Raw data referenced via source('source_name', 'table_name') from schema.yml Hardcoded SELECT * FROM raw.my_table without source definition
No Hardcoded Schema Model doesn't reference hardcoded schema names (except in comments) FROM my_schema.orders instead of FROM {{ source(...) }}

Pass 2: Logic

Check the SQL logic and data transformations.

Check What to Look For Red Flag
JOIN Clarity Joins use explicit keys, no cross joins, proper join types CROSS JOIN without clear reason, implied joins in WHERE clause
Filtering Logic WHERE clauses are clear and use indexes where possible WHERE NOT IN (subquery) when ANTI JOIN is clearer
NULL Handling Code explicitly handles NULLs (COALESCE, WHERE IS NOT NULL) Silent NULLs, unexpected NULL propagation
Type Consistency Joins and filters use same data types Joining varchar to integer without CAST

Pass 3: Quality & Tests

Check the tests and metadata.

Check What to Look For Red Flag
Test Coverage Key columns have unique, not_null, or relationships tests 0 tests on the model
Descriptions Models and columns have clear descriptions Missing or vague descriptions
No Data Loss Model output row count >= input row count (unless filtering intended) Unexplained loss of rows, JOINs that reduce volume
Config Settings Materialization, tags, and database settings are intentional Unnecessary table materialization, missing unique_key on incremental
Debugging Workflow in dbt Cloud

When you encounter a dbt error, follow this 5-step workflow to systematically debug and fix it.

  1. Read the Error Message Carefully
    Look for the error type (YAML, Jinja, SQL, test). dbt tells you which file and which line failed. Note the layer where it failed.
  2. Classify the Error Using the Decision Tree
    Is it Pattern A (YAML)? Pattern B (Jinja)? Pattern C (SQL)? This narrows down where to look.
  3. Find the Exact Problem Location
    Open the file dbt specified. Check the exact line number. Look for syntax errors, typos, or logic issues.
  4. Apply the Fix
    Use the Pattern Library to find the exact issue and fix. Test locally before pushing to dbt Cloud.
  5. Verify the Fix
    Run dbt run again. If tests fail, trace the data upstream. If it passes, commit and push.

Quick Debugging Commands

# Compile only (parse YAML, Jinja) — stops at first error dbt compile # Parse only (parse YAML) — stops if YAML is invalid dbt parse # Run a single model to isolate the error dbt run --select my_model # Run with logging to see dbt's internal decisions dbt run --debug # Run in dry-run mode (compile SQL but don't execute) dbt run --dry-run # Check if dbt can parse your project dbt parse # View generated SQL for a model dbt show --select my_model

Debugging in dbt Cloud

Step 1: View the run logs in dbt Cloud. Look for red error text.

Step 2: Check which layer failed (before or after "executing SQL").

Step 3: Click on the model name to see the compiled SQL.

Step 4: If SQL execution error, check the warehouse query history for the exact error.

Step 5: Fix the code locally, test with dbt run, then commit and re-trigger the job.

Common Interview Traps

During a technical interview, the interviewer may intentionally plant bugs in the code to test your debugging skills. Here are common traps and what to say.

Trap 1: Off-by-One Error in Incremental Logic

▼

Incremental model loses one day of data on each run

Buggy Code (models/fact_daily_revenue.sql):

{{ config(materialized='incremental', unique_key='date') }} SELECT date(order_timestamp) as date, sum(amount) as daily_revenue FROM {{ source('raw', 'orders') }} {% if is_incremental() %} WHERE date > ( -- BUG: Should be >= not > SELECT max(date) FROM {{ this }} ) {% endif %} GROUP BY date

What You Should Say:

"I notice the WHERE clause uses > instead of >=. This means on each incremental run, we exclude the last day's data from the previous run. The fix is to use >= so we recalculate the last day (in case new orders came in) but don't skip it entirely."

Fix:

WHERE date >= ( -- Use >= to recalculate last day SELECT max(date) FROM {{ this }} )

Trap 2: Silent NULL Join Loss

▼

Model output has fewer rows than expected due to NULLs in join key

Buggy Code (models/marts/fact_orders_with_customer.sql):

SELECT o.order_id, o.order_amount, c.customer_name FROM {{ ref('stg_orders') }} o INNER JOIN {{ ref('stg_customers') }} c ON o.customer_id = c.customer_id -- BUG: If customer_id is NULL, join fails

What You Should Say:

"In SQL, NULL = NULL evaluates to NULL, not TRUE. So orders with NULL customer_id will not match any customer row and will be silently dropped from the INNER JOIN. I'd check if stg_orders has NULL customer_ids and either filter them out or use a LEFT JOIN and handle the NULLs."

Fix Option 1 (Filter NULLs):

WHERE o.customer_id is not null

Fix Option 2 (LEFT JOIN to preserve rows):

LEFT JOIN {{ ref('stg_customers') }} c ON o.customer_id = c.customer_id

Trap 3: Test Passes but Data is Wrong

▼

Test definition is too weak to catch the actual bug

Buggy Test (models/schema.yml):

models: - name: fact_revenue columns: - name: order_amount tests: - relationships: -- BUG: Doesn't check if amount is positive to: ref('stg_orders') field: order_id

What You Should Say:

"The relationships test only checks that order_ids exist in stg_orders. It doesn't check if order_amount is positive or non-NULL. If the model accidentally has negative revenue or NULLs, the test will pass but the business data is wrong. I'd add a not_null test and possibly a custom test for positive values."

Fix:

columns: - name: order_amount tests: - not_null - relationships: to: ref('stg_orders') field: order_id - accepted_values: -- Or custom test for > 0 values: ['positive']

Trap 4: Jinja Default That Breaks in Prod

▼

Code works in dev but fails in prod due to missing variable

Buggy Code (models/incremental_model.sql):

{{ config(materialized='incremental') }} SELECT * FROM {{ source('raw', 'orders') }} {% if is_incremental() %} WHERE created_at > '{{ var("start_date", now()) }}' -- BUG: now() in default! {% endif

What You Should Say:

"The default value for start_date is now(), which means on first run, the WHERE clause will be WHERE created_at > [current timestamp]. This will load zero rows on the first incremental run. The fix is to use a static default like '2020-01-01' or to make the variable required."

Fix:

WHERE created_at > '{{ var("start_date", "2020-01-01") }}' -- Static default

Trap 5: Hardcoded Schema in Dynamic Environment

▼

Code has hardcoded dev schema name, breaks in prod

Buggy Code (models/staging/stg_orders.sql):

SELECT * FROM "dev_raw_data"."orders" -- BUG: Hardcoded dev schema

What You Should Say:

"The schema is hardcoded as dev_raw_data. When this code runs in prod, it will try to read from the dev schema instead of prod_raw_data. The fix is to define a source() in sources.yml and use {{ source(...) }} instead."

Fix (models/sources.yml):

sources: - name: raw_data database: '{{ env_var("DBT_SCHEMA_PREFIX") }}_raw' tables: - name: orders

Fix (models/staging/stg_orders.sql):

SELECT * FROM {{ source('raw_data', 'orders') }}
